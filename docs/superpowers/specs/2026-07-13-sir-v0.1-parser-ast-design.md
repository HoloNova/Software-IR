# SIR v0.1 Parser 与 AST 设计

状态：第二轮工程实现完成（`clean verify`，41 tests）  
日期：2026-07-13  
上位规范：`SIR v0.1 最小语言设计`

## 1. 第二轮目标

本轮冻结并设计：

- UTF-8 源文件和词法规则；
- Base SIR v0.1 的 ANTLR4 Grammar；
- 表达式优先级；
- Java 21 AST；
- SourceSpan 和确定性 AstNodeId；
- Parser API；
- 词法、语法诊断与有限错误恢复；
- Parser/AST 测试矩阵。

本轮不实现：

- Symbol Resolution；
- Type Check；
- Workflow 语义验证；
- Semantic Model；
- Lowering 和 Generator；
- Extension 内容解析；
- Change SIR；
- Project Symbol Graph。

Parser 只回答“文本能否形成合法语法结构”。`Ref<User>` 中的 `User` 是否存在、`return` 类型是否正确，都属于后续阶段。

## 2. 源文件和词法规则

### 2.1 编码与换行

- 源文件编码固定为 UTF-8；
- 允许 UTF-8 BOM，Parser API 在送入 ANTLR 前移除；公开 SourceSpan 的 offset、line、column 均相对于移除 BOM 后的规范化文本；
- 接受 `LF` 和 `CRLF`；
- Canonical Form 统一输出 `LF`；
- 空格、Tab 和换行在字符串外只用于分隔 Token；
- Tab 不参与语义，诊断显示列时按一个 Unicode code point 计算。

### 2.2 标识符

词法形式：

```text
[A-Za-z_][A-Za-z0-9_]*
```

第一轮不允许中文标识符和其他 Unicode 标识符，中文只能出现在字符串和注释中。这样可以降低 Java 名称映射、大小写和规范化风险。

命名风格属于后续 Validation，而不是 Lexer：

- Software、Entity、Input、Error、Capability：PascalCase；
- Field 和 Workflow 变量：camelCase；
- Enum Member：UPPER_SNAKE_CASE。

### 2.3 关键字

所有关键字区分大小写，并且不能作为用户标识符：

```text
sir software metadata displayName namespace target
language framework persistence database build interface declarations
enum entity persistent identity generated auto uuid field where
input error capability actor output fails requires authenticated
atomic readonly expose command query workflow validate else load by
as find item create update persist return Optional List Ref
true false and or not now unit
```

Primitive 名称暂不作为 Lexer 关键字，而作为普通类型名称进入 AST，后续 Type Resolver 判断其是否为内建类型。
`java`、`spring_boot`、`mybatis_plus`、`mysql`、`maven`、`rest` 是 Target 槽位值，不是 Lexer 关键字；Grammar 以 `IDENT` 接收，再由版本化兼容性检查决定是否支持。

### 2.4 数字

只支持：

```text
整数：0、21、123
小数：0.01、10.5
负数：由一元负号和正数字面量组成，例如 -1、-0.5
```

不支持：

- 前导正号；
- 科学计数法；
- 十六进制；
- 数字分隔符；
- `.5` 或 `5.`；
- 非零整数的前导零，例如 `01`。

点数字是单个原子 Token，数字内部不允许插入空格、换行或注释，因此 `0 . 01` 与 `0./*x*/01` 均非法。Lexer 保留数字原文；AST Builder 使用 `BigInteger` 和 `BigDecimal` 解析，不能使用 `double`。

### 2.5 字符串

字符串使用双引号：

```text
"校园二手交易系统"
```

允许的转义：

```text
\"  \\  \n  \r  \t  \b  \f
```

不允许未转义换行。源文件本身固定为 UTF-8，因此 Unicode 字符直接书写，禁止 `\uXXXX` 形成第二种等价字符串。AST 同时保存解码后的值和 SourceSpan；不要求保存字符串的原始引号形式。

### 2.6 Boolean、Date 和 DateTime

- Boolean 字面量只有 `true` 和 `false`；
- v0.1 不提供 Date/DateTime 文本字面量；
- `now()` 是唯一内建调用，返回类型由后续 Type Checker 判定为 DateTime；
- Date/DateTime 可以作为字段类型，也可以来自输入、加载对象或 `now()`；
- 如果未来需要固定日期字面量，将通过版本升级加入，不能暂时借用 String。

### 2.7 注释

支持：

```text
// 单行注释

/* 多行注释 */
```

多行注释不嵌套。注释不进入 AST，但 TokenStream 可以保留隐藏通道，以便未来格式化工具读取。

### 2.8 Field 多约束

每个 Field 最多出现一个 `where`，多个约束使用逗号：

```text
field title: String where notBlank, length(1, 100);
```

不允许重复 `where`：

```text
field title: String where notBlank where length(1, 100);
```

约束名称和适用类型由后续 Validator 检查。

## 3. 语法结构决定

### 3.1 固定区块顺序

Base SIR 固定为：

```text
sir
→ software
→ metadata
→ target
→ declarations
```

Capability 内部固定为：

```text
actor?
→ input?
→ output
→ fails*
→ requires*
→ expose
→ workflow
```

固定顺序不是业务语义，而是为了减少等价写法和 SLM 输出空间。

### 3.2 Parser 与 Validator 的边界

Grammar 只强制结构性事实：

- 区块是否存在；
- 分隔符和括号；
- 步骤形状；
- 表达式结构；
- Target 固定槽位和顺序。

后续 Validator 强制：

- 重复名称；
- 命名风格；
- 类型是否存在；
- Constraint 是否适用于字段类型；
- Capability requirement 冲突；
- query 是否 readonly；
- Workflow 是否返回；
- 变量、字段和 Error 引用是否合法。

Parser 阶段额外执行不依赖符号表的 `HeaderCompatibilityCheck`：当前实现只接受 SIR `0.1`，并只接受 `java 21 / spring_boot / mybatis_plus / mysql / maven / rest`。版本或目标组合不支持时不构建 AST，分别产生 `SIR-VERSION-001` 或 `SIR-TARGET-001`。Target 值在 Grammar 中保持为名称，因此以后注册新适配器不需要修改 Lexer。

### 3.3 AST 构建门槛

ANTLR 可以为了报告更多错误执行有限恢复，但 Parser API 采用严格结果：

> 只要存在 Lexer 或 Parser Error，就不构建、不返回 AST。

这样下游不会误把错误恢复产生的 Parse Tree 当成真实程序。

## 4. ANTLR4 Grammar 草案

以下 Grammar 是第二轮实现基线。生成代码的 package 等构建参数放在 Maven 插件配置，不写入 Grammar actions，保持 Grammar 与 Java 运行时解耦。

## 5. Grammar 设计说明

### 5.1 `item` 是保留变量

`find` 谓词中的 `item` 由语法保留，不允许用户将其他局部变量命名为 `item`。它只在当前 Find 谓词内有效。作用域检查属于后续阶段。

### 5.2 Create 不使用分号

Create 和 Update 以右花括号结束，不再附加分号：

```text
create Goods as goods {
  title: input.title;
}
```

区块型步骤和简单步骤采用不同结束符，不允许同时兼容 `};`，避免两种等价写法。

### 5.3 约束参数只允许常量

Constraint 参数在 Grammar 中直接限制为 Boolean、整数、小数和字符串常量，可带数字负号。零参数 Constraint 只允许 `notBlank` 形式；带参数 Constraint 必须至少有一个参数，因此 `notBlank()` 与 `min()` 均非法。`min(input.price)` 和 `min(now())` 在 Parser 阶段失败，以缩小 SLM 输出空间。

### 5.4 任意调用被语法禁止

不存在：

```text
functionCall: IDENT '(' ... ')'
```

因此 `calculatePrice(input)` 在 Parser 阶段失败。v0.1 只允许 `now()`。复杂计算必须通过未来 Operation/Implementation Slot，而不是从表达式语法逃逸。

### 5.5 Extension 不静默接受

Grammar 没有通用 `extensionBody` 或未知属性入口。未支持的 Extension 在 v0.1 是语法错误。等 Extension Registry 实现时，再通过新版本 Grammar 加入版本化扩展包络。

### 5.6 唯一表达的分层保证

Parser 负责拒绝会直接构造同一 AST 的结构同义词，例如 `notBlank()`、`save`、Create 后的 `};` 和 Enum 尾逗号。空白与注释属于词法 trivia，不进入 AST；点数字内部则禁止插入 trivia。

括号表达式会构造独立 `AstGroupedExpression`，Parser 不把它与无括号表达式静默合并。Primitive 遮蔽、`Unit` 使用位置、`fails`/`requires` 的规范顺序和冗余分组属于后续 Validation/Normalization 契约。只有依次通过 Parse、Validation 和 Normalization 的 SIR 才能进入 Lowering；“Parser 成功”本身不等于 canonical SIR。

Parser 负责拒绝会直接构造同一 AST 的结构同义词，例如 `notBlank()`、`save`、Create 后的 `};` 和 Enum 尾逗号。空白与注释属于词法 trivia，不进入 AST；点数字内部则禁止插入 trivia。

## 6. Source 模型

### 6.1 SourceId

```java
public final class SourceId {
    public static SourceId of(String logicalPath) { ... }
    public String value() { ... }
}
```

规则：

- 对文件输入使用相对 workspace 的 `/` 分隔路径；
- 对内存输入使用调用方提供的稳定逻辑名称，例如 `<memory>/test-case-01.sir`；
- 不把机器绝对路径放入 Canonical IR；
- Windows 路径在进入 SourceId 时转换为 `/`；
- 工厂拒绝绝对路径、空路径以及 `.`、`..` 路径段；
- Windows 盘符和分隔符按小写规范化，普通大小写保持不变；
- AstNodeId 中嵌入 SourceId 时，按 UTF-8 对 `%`、`#`、空格和其他 URI 保留字符执行 percent-encoding。

### 6.2 SourcePosition

```java
public record SourcePosition(
    int codePointOffset,
    int line,
    int column
) {}
```

- `codePointOffset`：从文件首字符开始、0-based、按 Unicode code point；
- `line`：1-based；
- `column`：1-based、按 Unicode code point；
- 文件结束位置允许 offset 等于总 code point 数。

Parser 实现必须使用 ANTLR CodePointCharStream，不能混用 Java UTF-16 `String` 下标作为公开 offset。

### 6.3 SourceSpan

```java
public record SourceSpan(
    SourceId source,
    SourcePosition start,
    SourcePosition end
) {}
```

Span 采用左闭右开区间 `[start, end)`。AST 节点 Span 包含完整语法结构，包括关键字和结束分隔符；Document Span 覆盖第一个非隐藏 Token 到 EOF 前最后一个非隐藏 Token。

## 7. AstNodeId

### 7.1 与 Semantic Symbol ID 分开

AstNodeId 只标识本次成功解析得到的语法节点。未来 Symbol Resolver 创建更稳定的 Semantic Symbol ID。两者不能复用同一个 Java 类型。

```java
public record AstNodeId(String value) {}
public record SymbolId(String value) {}
```

### 7.2 确定性生成

AstNodeId 不使用随机 UUID。Builder 按语法路径生成：

```text
ast://<SourceId>#document
ast://<SourceId>#software/CampusMarket
ast://<SourceId>#entity/Goods
ast://<SourceId>#entity/Goods/field/title
ast://<SourceId>#capability/PublishGoods/workflow/step/0001
```

规则：

- 命名节点使用 kind + 原始名称；
- 匿名或可重复节点使用父路径内四位序号；
- 重复命名声明尚未经过语义检查，因此第二次及之后附加 `/occurrence/0002`；
- 所有路径段使用统一 UTF-8 percent-encoding；
- Clause、Enum Member、Constraint、Binding、TypeRef 和 Expression 使用父节点内各自独立的 kind 序号域；
- 序号最少补齐四位，但超过 9999 时自然扩展，不截断；
- 删除或移动前置步骤可能改变后续 Step AstNodeId，这是允许的；
- 增量修改依赖未来 Symbol ID 和 Manifest，不依赖 Workflow Step AstNodeId 长期稳定。

## 8. Java 21 AST

### 8.1 公共接口

```java
public sealed interface AstNode permits
    AstDocument, AstSoftware, AstMetadata, AstTarget,
    AstDeclaration, AstEnumMember, AstIdentity, AstField,
    AstCapabilityClause, AstWorkflow, AstStep,
    AstTypeRef, AstConstraint, AstBinding, AstExpression {

    AstNodeId id();
    SourceSpan span();
}
```

所有 AST 公共类型放在同一个 `io.kcg.sir.ast` package，满足非 JPMS 构建下 sealed hierarchy 的 package 限制。Source 类型放在 `io.kcg.sir.source`，Parser API/Diagnostic 放在 `io.kcg.sir.api`，ANTLR 生成类和 Builder 放在 `io.kcg.sir.internal`。

所有 record 使用 compact constructor 执行 `Objects.requireNonNull`，所有集合执行 `List.copyOf`，所有 Optional 本身不得为 null。AST 构造完成后不可变，不提供 setter，也不携带 Parser Context。

名称声明与名称引用保存独立 Span：

```java
public record AstName(String text, SourceSpan span) {}
public record AstNameRef(String text, SourceSpan span) {}
```

`AstName` 用于声明位置，`AstNameRef` 用于类型、变量、字段、Error 和成员引用。它们是不可变值对象，不单独分配 AstNodeId。

## 9. Parser API

### 9.1 输入

```java
public record SirSource(
    SourceId id,
    String content
) {}
```

Parser 核心 API 不直接接收 `Path`，避免把文件读取、编码和沙箱问题混入解析逻辑。CLI 层负责读取 UTF-8 文件并构造 SirSource。

### 9.2 输出

```java
public record ParseResult(
    ParseStatus status,
    Optional<AstDocument> document,
    List<Diagnostic> diagnostics
) {
    public ParseResult { /* null、copyOf 与状态不变量检查 */ }
    public static ParseResult success(AstDocument document, List<Diagnostic> diagnostics) { ... }
    public static ParseResult failure(List<Diagnostic> diagnostics) { ... }
    public boolean isSuccess() { return status == ParseStatus.SUCCESS; }
}

public enum ParseStatus {
    SUCCESS,
    FAILED
}
```

不提供 `PARTIAL`：

- SUCCESS：document 存在且没有 Error；
- FAILED：document 为空且至少一个 Error；
- Warning 不阻止 AST，但 v0.1 Parser 阶段原则上不产生 Warning。

compact constructor 强制这些不变量；调用方优先使用 `success`/`failure` factory，不能构造 `SUCCESS + empty document` 等矛盾状态。

### 9.3 Parser 接口

```java
public interface SirParser {
    ParseResult parse(SirSource source);
}
```

Parser 不抛出用户输入导致的普通异常。可预期的 Builder 防御性失败转换为 `SIR-INTERNAL-001` 并返回 FAILED；`VirtualMachineError`、`ThreadDeath` 等 JVM 不可恢复错误允许传播，不能伪装成普通诊断。

## 10. Diagnostic 与错误恢复

### 10.1 Diagnostic

```java

```

Parser 第一批错误码：

```text
SIR-LEX-001    非法字符
SIR-LEX-002    未终止字符串
SIR-LEX-003    非法字符串转义
SIR-LEX-004    未终止块注释
SIR-PARSE-001  意外 Token
SIR-PARSE-002  缺少 Token
SIR-PARSE-003  多余 Token
SIR-PARSE-004  输入提前结束
SIR-VERSION-001 不支持的 SIR 版本
SIR-TARGET-001 不支持的 Target 组合
SIR-INTERNAL-001 内部错误
```

### 10.2 Span 策略

- 意外 Token：指向该 Token；
- 缺少 Token：使用前一个 Token 结束位置的零长度 Span；
- EOF：使用文件结束零长度 Span；
- 未终止字符串或注释：从起始分隔符到 EOF；
- Diagnostic 消息不直接使用 ANTLR 默认英文文本，而由统一映射器生成中文消息。

Lexer 使用 `INVALID_STRING`、`UNCLOSED_STRING` 和 `UNCLOSED_BLOCK_COMMENT` 专用 Token。Parser facade 先完整词法化并扫描这些 Token；存在任一词法错误时跳过 Parser。String decoder 额外拒绝解码后的孤立 Unicode surrogate。非法字符仍由 Lexer ErrorListener 收集，并与专用 Token 诊断按 SourceSpan 排序去重。

### 10.3 错误恢复

采用有限恢复以报告多个独立错误：

- `;`；
- `}`；
- 顶层声明关键字；
- Workflow Step 关键字。

Lexer 和 Parser 共用一个 Diagnostic Collector。最多返回 50 条诊断：前 49 条为详细错误，出现第 50 个候选错误时，以“错误过多，停止继续分析”作为第 50 条并终止解析。

无论恢复后的 Parse Tree 是否完整，只要出现一个 Error，AST Builder 都不执行。

### 10.4 禁止默认控制台输出

必须移除 Lexer 和 Parser 的默认 ErrorListener。所有错误进入 ParseResult，测试和 CLI 不应在未请求时向标准错误流打印 ANTLR 信息。

## 11. AST Builder

AST Builder 使用显式 Visitor：

```text
Parse Tree
→ HeaderCompatibilityCheck
→ SirAstBuilder
→ immutable AST
```

规则：

- 只在无词法/语法错误时调用；
- HeaderCompatibilityCheck 使用 `BigInteger` 读取任意长度版本数字，拒绝非 `0.1` 和非 Java 21/固定 v0.1 Target 组合，不能发生 `int` 溢出；
- 不解析符号；
- 不执行类型检查；
- 不增加默认 Capability requirement；
- 不展开任何简写；
- 解码 String；
- 使用 BigInteger/BigDecimal 解析数字和版本；
- 计算 SourceSpan；
- 生成确定性 AstNodeId；
- 保留声明、字段、Constraint 和 Step 的源顺序。

AST Builder 如果遇到理论上不可能的 Parse Tree 状态，产生内部错误而不是返回残缺 AST。

Parser 本轮只预留 `AstDocument → ParsedContext` 的单向边界，不创建可变全局 Symbol Table 或“公共黑板”；Project Knowledge Context 在后续 Symbol Resolution 阶段由 AST 构造不可变快照。

## 12. 测试矩阵

### 12.1 Lexer

- ASCII 与中文字符串；
- LF、CRLF 和 BOM；
- 所有合法转义；
- 非法转义；
- 未终止字符串；
- 未终止块注释；
- 前导零；
- `.5`、`5.` 和科学计数法；
- 非 ASCII 标识符。
- 字符串中的未转义控制字符；
- 孤立 Unicode surrogate；
- INVALID/UNCLOSED Token 诊断互斥且 Span 稳定。

### 12.2 Grammar 正例

- 最小 software；
- 每种声明；
- 每种 Workflow Step；
- Optional/List/Ref 嵌套；
- 多 Constraint；
- 一元和二元表达式；
- 注释出现在所有合法边界；
- Enum 至少有一个 Member，最后一个 Member 后禁止尾逗号，避免两种等价写法。

### 12.3 Grammar 负例

- 顶层区块错序、缺失或重复；
- Capability Clause 错序；
- `required` 和 `nullable`；
- `save`、`store`、`insert`；
- 任意函数调用；
- Java 注解和方法调用；
- Create 使用 `};`；
- 重复 `where`；
- 未闭合括号和花括号；
- 未知 Target 值；
- Extension 关键字。
- `sir 9.9` 和 `language java 99` 在兼容性检查阶段失败；
- `a < b < c` 和 `a == b == c`；
- Constraint 参数引用变量、`now()` 或成员访问。

### 12.4 AST

- 所有节点都有非空 Span；
- Span 左闭右开且父节点覆盖子节点；
- Unicode 字符后的列和 offset 正确；
- SourceId 不含机器绝对路径；
- 相同输入得到相同 AstNodeId；
- 重复声明仍得到不同 AstNodeId；
- 声明和 Step 顺序与源码一致；
- 数字使用 BigInteger/BigDecimal；
- Parse Tree 类不泄漏到 AST API。
- 所有声明名和引用名保留各自 Token Span；
- 构造 AST 后修改输入 List 不影响 AST；
- 所有公共 record 拒绝 null；
- 分组表达式保留括号 Span；
- SourceId 拒绝绝对路径和 `.`/`..` 段，并正确编码 `#`、`%` 和空格。

### 12.5 Parser API

- 成功时只有 AST、无 Error；
- 失败时无 AST、至少一个 Error；
- 用户语法错误不抛异常；
- 默认控制台无 ANTLR 输出；
- 错误数上限为 50；
- 同一输入的 Diagnostic 代码、顺序和 Span 稳定。

## 13. 第二轮完成标准

本轮设计经确认后，工程实现必须满足：

1. Grammar 可以由 ANTLR4 成功生成 Java Parser；
2. 所有正例通过，所有语法负例在 Parser 阶段失败；
3. 有任何语法 Error 时不返回 AST；
4. AST 是 Java 21 immutable sealed/record 模型；
5. SourceSpan 对中文、CRLF 和 EOF 行为有测试；
6. AstNodeId 确定且不使用随机数；
7. Parser API 不暴露 ANTLR 类型；
8. Parser/AST 不依赖 Spring Boot、MyBatis-Plus 或 Generator；
9. 默认不向控制台打印错误；
10. 第一轮完整合法示例能够构建 AST。

完成这些标准后，第三轮才能进入 Semantic Model、Symbol Table 和 Type System。
