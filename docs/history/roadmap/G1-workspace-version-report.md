# G1 报告：不依赖状态目录的版本变更（磁盘上的 SIR + Git）

> 历史文档（分层迁移 R1–R5 与“以 Git 取代自存版本历史”G1–G4 的计划、报告和更早的阶段控制）。其中提到的状态目录、基线 Bundle、CURRENT、日志与恢复、`context`/`plan` 命令、单文件 0.1 入口均已删除；现状见 [项目状态](../../PROJECT_STATUS.md)。

- 日期：2026-10-14。分支：`main`。授权：负责人 2026-10-14 确认使用 Git、同仓库、快照只含 SIR 与受管生成文件、无 `git` 时拒绝应用，并说"可以开始 G1 了"。G2 至 G4 未授权。
- 依据：[ADR-027](../../architecture/ADR-027-git-as-version-history.md)、[G 系列计划](G-git-version-history-plan.md)。
- 结论：现在可以对"磁盘上的 SIR 源码 + 生成的工程 + Git 仓库"规划并应用一次变更，**不需要状态目录**。旧的版本变更路径一行没动，仍可使用。

## 1. 怎么用

```text
磁盘上的当前 SIR ─┐
                  ├─ 规划（只读）→ 计划 ─ 应用 → 新的 SIR + 更新后的生成工程 + 两次 Git 快照
候选 SIR（指令编辑出的）┘
```

两个入口：`WorkspaceVersionApplication.plan(request)` 和 `.apply(request, 计划)`。请求里给仓库根、SIR 源码目录、生成工程目录和候选源码。Git 通过 `VersionControl` 端口接入，真实适配器是 `GitVersionControl`。

## 2. 新增了什么，以及为什么存在

| 部件 | 为什么存在 |
| --- | --- |
| `VersionControl` 端口（api） | 应用层只需要 Git 的三件事：有没有仓库、没有就建、把指定的一组文件存成一次提交。做成端口，应用层不认识 `git` 程序 |
| `GitVersionControl`（execution） | 真正调用 `git`。只提交被点名的文件，不碰用户其他文件和已暂存的内容；路径一律按字面处理（文件名像通配符或选项也不会被误解）；用用户自己的 Git 身份，没有时只为这一次提交用固定身份，不写任何 Git 配置；`git` 不能用就如实报告，不绕过 |
| `WorkspacePlanning`（internal） | 当前版本不再是一条存起来的记录，而是"磁盘上的 SIR 编译出来的结果"。规划把当前 SIR 和候选各完整编译一次、比较，并要求**整个**生成工程等于当前 SIR 的编译结果，否则报告"需要重新生成" |
| `WorkspaceWriter`（internal） | 按计划写文件。没有日志、备份和恢复，改为**可重跑**：每步先看磁盘，已经是新内容就跳过，既不是旧内容也不是新内容就停下 |
| `WorkspacePlan` 与四个结果/请求类型（api） | 不含状态目录的计划，和旧 `VersionPlan` 并存 |
| `VersionPlans.operations`、`VersionPlanning.observe/shapeChange` 改为可复用 | 新规划复用旧规划的文件比较、磁盘观察和形状检查，不复制第二份；行为未变 |

## 3. 规则

1. **整体核对。** 生成工程里任何受管文件缺失、被改、或与当前 SIR 的编译结果不符，一律拒绝，提示"重新生成或从 Git 恢复后再规划"。这同时覆盖手改和工具链升级造成的差异，系统不区分两者（ADR-027）。
2. **唯一的容忍：变更自己要写的文件。** 它已经等于新内容（或删除的文件已不在），说明上一次应用被打断，重跑就能完成，不算冲突。
3. **Git 必需。** `git` 不能用、仓库根不是 Git 顶层、保存当前版本失败，都在改动前拒绝。没有仓库时自动 `git init`。
4. **应用顺序。** 先保存当前版本（第一次快照）→ 生成文件（先新建和更新，再删除，再删空目录）→ 核对整个生成工程 → SIR 源码（先暂存全部，再依次：新增、更改、删除）→ 回读核对源码 → 保存新版本（第二次快照）。SIR 最后改，因为它定义"当前版本"。
5. **中途停下不自动修复。** 返回"需要重跑"和提示：再执行同一个应用，或用 Git 回到第一次快照。
6. **快照只含两个版本涉及的 SIR 源码和生成文件**；用户放在同目录的其他文件、已暂存的其他文件不会被带入。

## 5. 需要你知道的地方

1. **没有跨进程锁。** 旧路径用状态目录里的锁串行化；新路径没有。两个应用同时作用于一个工程由调用方避免，Git 自己的索引锁只保护快照步骤。
2. **同时改多个 SIR 源文件时，停在移动之间可能留下新旧混合的源码。** 写入前已全部暂存，移动是连续的，窗口很小；测试里的两个源文件场景在每个检查点重跑都能完成。但如果混合出来的源码彼此不兼容，重跑会在读取或编译时失败，此时用 Git 回到第一次快照。
3. **Git 钩子照常生效。** 用户仓库里的提交钩子拒绝提交时，保存当前版本失败，应用在改动前停止；保存新版本失败只给警告。
4. **SIR 目录与生成目录必须是仓库里互不包含的两个目录，且在同一文件系统。** 原子移动需要这一点；不满足就在改动前拒绝。
5. **整体核对对工具链升级是"一律拒绝"。** 升级后所有受影响文件都会被报告，处理办法是重新生成整个工程。旧工具链多生成、新工具链不再生成的文件，系统不知道它们，会残留，需要用 `git status` 发现。
6. **命令行没有切换**，仍使用旧路径；旧路径与旧测试一行未改。
