## 1. 负责人已确认的方向

1. **SIR 是建在 Java 之上的业务语言，目标是一句普通需求对应一个功能。** 如果一个普通功能要写上百行 SIR，直接让模型写 Java 更划算，本系统就没有价值。双 Token 样例共 209 行，其中登录部分占 117 行。
2. **语义分两层。**
   - 基础语义可以组合，包括实体、字段、能力和工作流步骤。
   - 功能语义是一个声明对应一个功能，比如"登录"。
   - 功能**展开成基础语义**，不直接生成 Java。
3. **作者不写机器数据类型，只写语义类型。** 例如写"序号""金额""是否"，不写 `Int64`、`Decimal`、`Boolean`。
4. **开放接口。** 用户可以自己定义语义。负责人之前提过这件事，但没有推进，仓库里也没有对应的设计。
5. **数据库迁移是变更层的工作**，数据库变更同样是增、删、改。
6. **上层的 SLM 工作尚未启动。** 软件语义没有定型之前，无法收集 SIR 格式的数据，所以本设计不受"已有训练数据"约束。

7. 负责人曾提出把"删"并入"改为空"。执行者提出反对意见（第 8 节），负责人确认保持"删"为独立操作。

## 4. 功能语义

### 4.1 一个功能由什么组成

| 部分 | 内容 | 双 Token 的例子 |
| --- | --- | --- |
| 名字 | 功能的名字 | 登录 |
| 参数 | 类型化的参数：引用作者的实体或字段、时长、开关等 | 账号实体、账号字段、口令字段、访问令牌 15 分钟、刷新令牌 7 天 |
| 契约 | 对作者已有声明的要求 | 账号字段要 `unique`，口令字段要 `secret` |
| 展开 | 一组基础语义声明，参数代入其中 | 3 个实体、3 个能力、3 种错误、2 个输入、2 个视图 |

示意（不是冻结的语法）：

```
use 登录 {
  账号: User.name;
  口令: User.passwordHash;
  访问令牌: 15 分钟;
  刷新令牌: 7 天;
}
```

这一句代替那 117 行。展开以后的东西和作者手写的完全一样，所以类型检查、Lowering、生成、变更和迁移都直接复用。

### 4.2 展开在语言里进行（设计 10 第 27.3 节的 A）

设计 10 第 27.2 节列出了 A 的五个代价。本设计逐一给出处理办法：

| 问题 | 办法 |
| --- | --- |
| 展开出的声明没有源文本 | 它们不写进 SIR。规范化声明加一个可选的"来源"槽位，标明"由某个功能声明的某个角色展开"。6 个变体共用这个槽位 |
| 稳定身份 | 由功能声明的身份加上固定的角色名确定性派生，不用时间和随机数（设计 10 第 14 节的倾向） |
| 回写 | 回写和编辑跳过带"来源"的声明。指令只能改功能声明本身，也就是它的参数，不能单独改展开出来的东西 |
| 诊断位置 | 诊断指向功能声明，并附上角色名，例如"登录 / 刷新能力：……" |
| 重名 | 展开出的名字和作者的声明冲突时，给一条专门的诊断，说明是哪个功能的哪个角色。功能允许作者设定名字前缀 |

另外，`kcg inspect` 要能列出展开结果，让作者看得到功能具体变成了什么。

### 4.3 功能只能展开成基础语义

功能里不允许写 Java，也不允许写 SQL。功能需要某种基础语义还没有的东西时，先把它作为通用能力补进基础语义，再让功能使用它。设计 10 第 15.3 节就是这样补齐双 Token 的：`unique`、时间运算、守卫更新、401、`secret`、凭据连接，每一项都是通用能力。

### 4.4 挂载点：功能之间怎样共存

功能之间不直接互相引用，只往基础语义的固定位置添加内容。

| 挂载点 | 基础语义现在有没有 | 需要它的功能（举例） |
| --- | --- | --- |
| 声明（实体、能力、输入、视图、错误） | 有 | 登录、注册、按 id 查询 |
| 请求认证 | 有（`credential`、`requires authenticated`） | 登录 |
| 每次查询都追加的条件 | 没有 | 软删除、只看本人的数据 |
| 新建或修改时的自动赋值 | 没有 | 审计（创建人、创建时间） |
| 删除记录 | 没有 | 软删除、删除接口 |

**第一轮只做"声明"和"请求认证"这两个已有的挂载点。** 双 Token 和注册、查询这类功能都够用了。其他挂载点等第二类功能确实需要时，作为基础语义的通用能力补上，每一个都按 AGENTS 的三条规则单独评审。

多个功能往同一个挂载点追加内容时，规则是合并。例如两个查询条件同时成立。两个功能要独占同一件事时（比如都想定义"删除"的行为），编译时报冲突，不悄悄选一个。

### 4.5 第一批功能从哪里来

不预先列清单。第一个功能是双 Token 的"登录"，它已经有 CI 真实库验收的证据。第二个候选是样例里反复出现的固定写法，比如注册、按 id 查询、新建并返回。具体选哪个，要先统计现有 178 个 SIR 样例里哪些写法重复得最多，再决定。

### 4.6 天花板与出口

实际需求常常偏离标准功能，比如"登录但要加验证码"。出口有两个：

1. **加参数。** 只加那些能让一类业务受益的参数，比如是否轮换刷新令牌。
2. **脱离。** 把功能的展开结果写成普通 SIR 文本，代替功能声明，作者之后自己改。这一步就是现有 `kcg scaffold` 做的事。脱离之后，这部分不再跟随功能的升级。

参数不能无限增加。一个功能如果需要很多开关才能用，说明它应该拆成更小的功能，或者退回基础语义。

## 5. 语义类型

### 5.1 三层分工

| 层 | 管什么 | "金额"的例子 |
| --- | --- | --- |
| SIR（作者写的） | 语义类型 | `金额` |
| 语义层 | 值的种类、允许的运算、约束 | 小数、两位、不能为负；只能和金额相加减 |
| Lowering | 物理表示 | `BigDecimal`、`DECIMAL(19,2)` |

语义层内部保留一小组**值的种类**（整数、小数、文本、真假、日期、时刻、标识）。它们决定哪些运算合法，与 Java 无关。作者平时不写它们，只有在定义新的语义类型时才会用到（见第 6 节）。机器类型名（`Int32`、`Boolean` 等）从语言里移除，由 Lowering 按值的种类和约束去选。

### 5.2 运算规则（倾向）

- 同一种语义类型之间才能做加减和比较。
- 不同语义类型之间的运算一律拒绝。比如金额和数量相加，作者要先说明换算方式；现在的语言里还没有乘法，这件事以后再定。
- 字面量按另一侧的语义类型理解。这和设计 10 第 23.4 节处理整数字面量宽度的方式一致。

### 5.3 内置语义类型的清单

不预先编造。确定方法是：统计 178 个现有 SIR 样例里，每个字段的名字、机器类型和约束，按"约束相同、含义相同"归类，频率高的作为内置类型，其余由作者自己定义。统计结果和清单另行提交评审。

### 5.4 改写现有样例

- 语言版本从 `sir 0.2` 升级。旧版本是否继续接受，需要负责人决定。
- 166 个 SIR 文件、约 2250 处类型写法用一次性脚本机械改写。脚本需要第 5.3 节的映射表。
- 37 个测试文件和语言参考同步修改。

## 6. 开放接口：用户自己定义语义

按"能证明的东西从多到少"分三级，能放在上一级的不放到下一级：

| 级别 | 用户能定义什么 | 能写什么 | 系统能证明什么 |
| --- | --- | --- | --- |
| 1 语义类型 | 新的语义类型 | 值的种类加纯约束，例如"序号：整数，最小为 1" | 全部 |
| 2 功能 | 新的功能 | 参数、契约，以及一段只用基础语义写成的展开模板 | 全部（展开后照常检查） |
| 3 端口 | 语义写不出来的外部能力 | 签名、失败、有无副作用；实现放在工程之外 | 只能证明接线正确，见设计 10 第 10 节 |

和设计 08 第 13 节的冲突，处理办法如下。那一节要防止的是：用户提交一套有自己执行规则的语言，绕过语义检查。第 1、2 级的用户定义没有自己的执行规则，它们只是参数化的 SIR 片段，展开后照常经过全部正式分析，所以不在那一条禁止的范围内。负责人已确认这个解释（第 10 节），设计 08 第 13 节已补一句说明。

第一轮里，用户定义写在本工程的源文件中。跨工程共享、版本管理和模块市场不在范围内。

## 7. 由变更层驱动的数据库迁移

### 7.1 分工

| 层 | 做什么 |
| --- | --- |
| 变更层 | 对旧版和新版 SIR 都编译到展开之后，用 `SemanticDelta` 得出业务层面的增删改，例如"新增实体 Label"、"Note 新增可空字段 title"、"字段 text 改名为 body" |
| Lowering | 把每条业务变化翻译成数据库操作，并判断能否安全执行。判断规则就是设计 04 第 4 节的表格 |
| 应用层 | 继承旧的迁移链，写出新的 Flyway 文件 |

比较要在**展开之后**进行。功能参数的变化（比如访问令牌从 15 分钟改成 30 分钟）先体现为展开结果的变化，再进入迁移判断。报告同时列出作者层面的变化（改了哪个功能的哪个参数）和展开后的变化。

### 7.2 身份

- Lowering 产出的表和列要带上语义身份（SymbolId）。
- 身份不写进 `schema.tsv`。更新时用当前工具链重新编译旧版 SIR，就能得到旧版每张表、每一列的身份。前提是重新编译出的结构清单和旧包里的 `schema.tsv` 逐字节相同，不同就拒绝。这样 `schema.tsv` 的格式和部署时的迁移工具都不用改（第 12 节）。
- 字段带 `@id` 时，改名不改变身份。这时迁移规划能认出"这是改名"，而不是"删一列、加一列"。改名怎样落到数据库上，第 12.5 节有一个待决定的问题。

### 7.3 保留不变的部分

- 旧版 SIR 从旧交付包的 `sir/` 目录取得。
- `schema.tsv` 继续用来核对线上数据库是否等于旧版（漂移检测），但不再用它决定迁移内容。
- 步骤③已经验收的部分全部保留：迁移链、四种迁移模式、数据摘要比对、退出码和三个 CI 实例。
- 支持范围仍然是"不变、新表、新可空列"。改名在第 1 步里只做到"能认出来，并给出明确的拒绝理由"（第 12.5 节）。

## 8. 关于"删"并入"改为空"（负责人已确认：保持独立）

先说成立的部分。现在的 `Delete` 有两种用法：从集合里移除一个元素，和清空一个可选值。第二种本来就等于"改为空"。

不建议合并，理由有三个：

1. **集合元素没有"空"这个值。** 删掉一个实体，如果说成"把它改为空"，它的身份和位置还在。这时就要再加一条规则"内容为空的元素视为不存在"，其实就是把"删"换了个名字。
2. **"空"可以是合法的值。** 对可选值来说，"改为空"可能表示"现在没有值"，也可能表示"去掉这一项"。合并后两者无法区分。
3. **数据库上的后果完全不同。** 删列（`DROP COLUMN`）会永久丢失数据，置空（`SET NULL`）只清空值，列还在。"删"是唯一需要额外确认或备份的操作。合并后，它就藏进了最日常的"改"里，迁移规划和审查都没法单独拦住它。

照同样的思路，"增"也可以说成"从空改成有值"，最后只剩下一种操作，所有区别都没了。所以建议保持增、删、改三种不变。

## 9. 实施顺序

这里只写依赖关系，不是排期。每一步都需要负责人单独授权。

1. **迁移改由变更层驱动（第 7 节）。** 它不依赖语言改动，同时修正步骤③对设计 04 的偏离。具体方案见第 12 节。
2. **功能展开机制，以"登录"为第一个功能（第 4 节）。** 验收：用功能声明重写双 Token 样例，展开后的规范化模型和现在手写的版本相同（来源槽位除外）；现有的双 Token 真实库验收和部署验收在新写法下全部通过；编辑、回写、变更都不会触碰展开出来的声明。
3. **语义类型（第 5 节）。** 先提交第 5.3 节的统计和清单，评审通过后再改语言和样例。
4. **用户自定义语义类型和功能（第 6 节第 1、2 级）。**
5. **新的挂载点（第 4.4 节）。** 按第二类功能的实际需要逐个补，每一个单独评审。

第 2 步排在第 3 步前面。理由是第 2 步直接验证这次讨论的核心判断（117 行能否变成一句），而且第 3 步改写样例时只多出一个功能模板要改。

## 12. 第 1 步的具体方案：迁移改由变更层驱动

### 12.1 现在的做法和问题

`SpringBootSchemaEvolutionPlanner` 只拿旧包的 `schema.tsv` 和新版的表结构做对比，键是物理表名和列名。这带来两个问题：

- 判断"什么变了"的不是变更层；
- 不按语义身份对应，字段改名只能被看成"删一列、加一列"。

### 12.2 新的流程

| 顺序 | 谁做 | 做什么 |
| --- | --- | --- |
| 1 | 应用层 | 校验旧交付包的完整性（不变）。从旧包的 `sir/` 和新增的 `sir-entry` 文件读出旧版 SIR |
| 2 | 应用层 | 用当前工具链编译旧版 SIR，得到旧版的规范化模型和表结构。旧版表结构渲染出的清单必须和旧包的 `schema.tsv` 逐字节相同，否则拒绝（新诊断码 `SIR-APP-PACKAGE-BASE-004`）。这一步保证"重新编译的旧版"就是"线上正在跑的旧版" |
| 3 | 变更层 | 用 `SemanticDelta` 对比旧版和新版的规范化模型，得出增、删、改清单 |
| 4 | Lowering | 把清单里涉及实体和实体字段的变化，翻译成数据库步骤或拒绝理由（规则不变：新表、新可空列；其余拒绝） |
| 5 | Lowering | 自检：按语义身份对比旧版和新版的表结构，每一处物理差异都必须能由第 3 步的某条变化解释；规划出的迁移链终点必须等于新版的结构清单（原有自检保留）。任何一项对不上，记为内部错误，不发出迁移 |
| 6 | 应用层 | 写出迁移文件（不变）。导出结果新增一项：本次更新的业务层面变化清单 |

### 12.3 要改的地方

| 位置 | 改动 | 为什么 |
| --- | --- | --- |
| `sir-change` 的 `SemanticDelta.Change` | 增加 `trail`：从外到内列出这条变化所在的、带身份的元素的身份；对带身份元素的增删，也包含这个元素自己的身份 | 现在每条变化只有一段给人看的路径文本。下游要按身份定位"哪个实体、哪个字段"，需要结构化的身份。这是通用的补充，不是为迁移加的专用操作，编辑报告同样能用 |
| `DeploymentPlan.Table` / `Column` | 各增加 `symbol`：实体、主键或字段的语义身份 | 表结构和语义身份对得上，才能把变化落到具体的表和列上 |
| `SpringBootSchemaEvolutionPlanner` | 输入改为"旧版表结构、新版表结构、变更层的变化清单"，按第 12.2 节第 4、5 步规划 | 第 7.1 节的分工 |
| `sir-lowering-spring-boot` 的依赖 | 新增对 `sir-change` 的依赖 | Lowering 要读取变更层的输出。`sir-change` 只依赖 parser 和 semantic，不会形成循环 |
| `DeploymentPackageApplication` | 按第 12.2 节第 1、2、6 步改写；导出时写出 `sir-entry` | 更新时必须知道旧版 SIR 的入口文件，旧包里原来没有记录 |
| 导出结果与 CLI JSON | `Continuation` 增加 `changes`（业务层面的变化，每条一行） | 第 7.1 节：报告同时列出业务层面的变化 |

`schema.tsv`、各版本的结构清单、部署时的迁移工具（Migrate）和 `deploy.sh` 都不改。

### 12.4 拒绝理由的变化

| 情况 | 原来 | 现在 |
| --- | --- | --- |
| 字段不带 `@id` 改名 | `COLUMN_REMOVED` 加上新增列的拒绝 | 不变（名字派生的身份本来就不同，确实是一删一增） |
| 字段带 `@id` 改名 | 同上 | 列跟着改名（第 12.5 节）；主键改名以 `PRIMARY_COLUMN_RENAMED` 拒绝 |
| 实体改名 | `TABLE_REMOVED` | 不变（实体没有 `@id`，改名就是一删一增） |
| 旧包的 SIR 重新编译后和 `schema.tsv` 对不上 | 无 | `SIR-APP-PACKAGE-BASE-004` |
| 旧包里没有 `sir-entry` | 无 | `SIR-APP-PACKAGE-BASE-003`（旧格式的包不能作为基础，符合第 10 节第 3 点） |

### 12.5 改名怎样落到数据库（负责人 2026-10-17 确认：列跟着改名）

字段带 `@id` 改名时，数据库里的列也跟着改名。迁移执行 `ALTER TABLE 表 RENAME COLUMN 旧列 TO 新列`，MySQL 8 只改元数据，数据原样保留。列名始终等于字段名的下划线形式，同一份 SIR 生成的代码也始终相同。

曾考虑过另外两种办法：沿用旧列名，或者由 `@id` 决定列名。这两种都让列名和字段名分家，只有在外部程序也直接读这个数据库时才有必要。按设计 04，本系统的数据库只给生成的应用自己用，所以不采用。

| 规则 | 内容 |
| --- | --- |
| 什么算改名 | 同一个语义身份（字段带 `@id`）、表不变、除列名外所有物理属性都相同 |
| 顺序 | 改名排在建表和加列之前，后面的版本都按新列名书写 |
| 拒绝 | 主键改名（`PRIMARY_COLUMN_RENAMED`，其他表按列名引用它）；新列名和表里另一列只差大小写或相同（`NAME_CASE_CONFLICT`）；改名的同时还改了类型等属性（`COLUMN_CHANGED`） |
| 不带 `@id` 的改名 | 身份随名字变化，仍然看作删一列、加一列，照旧拒绝 |
| 迁移工具 | 交付包新增 `deploy/renames.tsv`，每行是"版本、表、旧列名、新列名"，后续版本会继承。迁移工具更新时按它把旧版的列对应到新列名，再做前后数据摘要比对；被改名的列不当作"新加的列"去检查是否为空。全新部署不用这份记录 |

### 12.6 验收

- 单元测试：变更层的 `trail`；规划器的不变、加表加列（含依赖顺序）、各类拒绝、带 `@id` 改名被认出、物理差异无法解释时的自检。
- 应用层测试：现有的继承旧链、拒绝回退、篡改旧包三项照旧通过；新增"旧包缺 `sir-entry`"的拒绝。
- CI：v2 样例把 `Note.text` 改名为 `body`（v1 样例给这个字段加了 `@id("note-text")`），所以 v2 的迁移链是 V2 改列名、V3 建 `label` 表、V4 加 `title` 列，`schemaVersion == 4`。更新后旧数据在新列名 `body` 下逐行不变，旧列名 `text` 已不存在；update、dataUpdate、freshChain 都应为 PASSED。

**第 1 步：迁移由变更层驱动。** 按第 12 节实施（b5fddb4）。之后补上了带 `@id` 字段改名时列跟着改名并保留数据（4b40439，CI 的 v2 样例把 `Note.text` 改名为 `body`）。

**第 2 步：功能展开。** `use 功能 { 参数: 值; }` 在合并各文件声明之前展开（4ffbf13）。展开出来的声明身份派生自 `use`，位置借用 `use`；编辑、回写和变更只碰 `use` 本身。双 Token 部署样例的登录部分由 117 行变为 7 行，两种写法的模型一致，生成的工程逐字节相同。

**第 3 步：语义类型。** 字段只写语义类型（18 个，见语言参考第 2 节），语言升到 `sir 0.3`，不再接受旧写法（6bb8e0c）。全部样例用脚本改写；68 份可生成的样例经新旧工具链对比，生成的工程逐字节相同。

**第 4 步：用户自定义。** `type` 以已有语义类型为底定义新类型，`feature` 用带 `${参数}` 的 SIR 模板定义功能（5a778f6）。参数只有 `name` 与 `duration` 两种；模板里没有条件和循环。

**第 5 步：新的挂载点。** 按需逐个补齐：

- `delete` 步骤，独立的变更操作（d06c844）；
- 字段 `default`：常量、枚举成员与 `now()`（8a3ff4d、6462939）。常量和枚举成员也成为数据库列默认值，已上线的表因此可以加带默认值的必填列（8aea5b3、52e746b）；
- 实体 `scope`：在 `implementable()` 中补进该实体的每个 `find`、`any()` 与 `load`（d9b5cdd）；
- `extend`：给已有实体加字段，功能借它带上自己需要的字段（3c12308）。

**收尾。** 双 Token 功能改用这些能力：经 `extend` 给账号加登录名与口令字段，`used` 用 `default false`（1d010d2）；脚手架仍面向已有账号字段的软件。另外修正了两处诊断码重用：`delete` 改用 `SIR-VALID-012`（1bcf42d），`type` 声明改用 `SIR-TYPE-005`（5e3a0ad）。
