## 1. 负责人已确认的方向

1. **SIR 是建在 Java 之上的业务语言，目标是一句普通需求对应一个功能。** 如果一个普通功能要写上百行 SIR，直接让模型写 Java 更划算，本系统就没有价值。双 Token 样例共 209 行，其中登录部分占 117 行。
2. **语义分两层。**
   - 基础语义可以组合，包括实体、字段、能力和工作流步骤。
   - 功能语义是一个声明对应一个功能，比如"登录"。
   - 功能**展开成基础语义**，不直接生成 Java。
3. **作者不写机器数据类型，只写语义类型。** 例如写"序号""金额""是否"，不写 `Int64`、`Decimal`、`Boolean`。
4. **开放接口。** 用户可以自己定义语义。负责人之前提过这件事，但没有推进，仓库里也没有对应的设计。
5. **数据库迁移是变更层的工作**，数据库变更同样是增、删、改。
6. **上层的 SLM 工作尚未启动。** 软件语义没有定型之前，无法收集 SIR 格式的数据，所以本设计不受"已有训练数据"约束。

7. 负责人曾提出把"删"并入"改为空"。执行者提出反对意见（第 8 节），负责人确认保持"删"为独立操作。

## 4. 功能语义

### 4.1 一个功能由什么组成

| 部分 | 内容 | 双 Token 的例子 |
| --- | --- | --- |
| 名字 | 功能的名字 | 登录 |
| 参数 | 类型化的参数：引用作者的实体或字段、时长、开关等 | 账号实体、账号字段、口令字段、访问令牌 15 分钟、刷新令牌 7 天 |
| 契约 | 对作者已有声明的要求 | 账号字段要 `unique`，口令字段要 `secret` |
| 展开 | 一组基础语义声明，参数代入其中 | 3 个实体、3 个能力、3 种错误、2 个输入、2 个视图 |

示意（不是冻结的语法）：

```
use 登录 {
  账号: User.name;
  口令: User.passwordHash;
  访问令牌: 15 分钟;
  刷新令牌: 7 天;
}
```

这一句代替那 117 行。展开以后的东西和作者手写的完全一样，所以类型检查、Lowering、生成、变更和迁移都直接复用。

### 4.2 展开在语言里进行（设计 10 第 27.3 节的 A）

设计 10 第 27.2 节列出了 A 的五个代价。本设计逐一给出处理办法：

| 问题 | 办法 |
| --- | --- |
| 展开出的声明没有源文本 | 它们不写进 SIR。规范化声明加一个可选的"来源"槽位，标明"由某个功能声明的某个角色展开"。6 个变体共用这个槽位 |
| 稳定身份 | 由功能声明的身份加上固定的角色名确定性派生，不用时间和随机数（设计 10 第 14 节的倾向） |
| 回写 | 回写和编辑跳过带"来源"的声明。指令只能改功能声明本身，也就是它的参数，不能单独改展开出来的东西 |
| 诊断位置 | 诊断指向功能声明，并附上角色名，例如"登录 / 刷新能力：……" |
| 重名 | 展开出的名字和作者的声明冲突时，给一条专门的诊断，说明是哪个功能的哪个角色。功能允许作者设定名字前缀 |

另外，`kcg inspect` 要能列出展开结果，让作者看得到功能具体变成了什么。

### 4.3 功能只能展开成基础语义

功能里不允许写 Java，也不允许写 SQL。功能需要某种基础语义还没有的东西时，先把它作为通用能力补进基础语义，再让功能使用它。设计 10 第 15.3 节就是这样补齐双 Token 的：`unique`、时间运算、守卫更新、401、`secret`、凭据连接，每一项都是通用能力。

### 4.4 挂载点：功能之间怎样共存

功能之间不直接互相引用，只往基础语义的固定位置添加内容。

| 挂载点 | 基础语义现在有没有 | 需要它的功能（举例） |
| --- | --- | --- |
| 声明（实体、能力、输入、视图、错误） | 有 | 登录、注册、按 id 查询 |
| 请求认证 | 有（`credential`、`requires authenticated`） | 登录 |
| 每次查询都追加的条件 | 没有 | 软删除、只看本人的数据 |
| 新建或修改时的自动赋值 | 没有 | 审计（创建人、创建时间） |
| 删除记录 | 没有 | 软删除、删除接口 |

**第一轮只做"声明"和"请求认证"这两个已有的挂载点。** 双 Token 和注册、查询这类功能都够用了。其他挂载点等第二类功能确实需要时，作为基础语义的通用能力补上，每一个都按 AGENTS 的三条规则单独评审。

多个功能往同一个挂载点追加内容时，规则是合并。例如两个查询条件同时成立。两个功能要独占同一件事时（比如都想定义"删除"的行为），编译时报冲突，不悄悄选一个。

### 4.5 第一批功能从哪里来

不预先列清单。第一个功能是双 Token 的"登录"，它已经有 CI 真实库验收的证据。第二个候选是样例里反复出现的固定写法，比如注册、按 id 查询、新建并返回。具体选哪个，要先统计现有 178 个 SIR 样例里哪些写法重复得最多，再决定。

### 4.6 天花板与出口

实际需求常常偏离标准功能，比如"登录但要加验证码"。出口有两个：

1. **加参数。** 只加那些能让一类业务受益的参数，比如是否轮换刷新令牌。
2. **脱离。** 把功能的展开结果写成普通 SIR 文本，代替功能声明，作者之后自己改。脱离之后，这部分不再跟随功能的升级。原先只有双 Token 能脱离（`kcg scaffold dual-token`，模板与功能各一份）；负责人 2026-10-20 决定删除该命令，脱离暂时由作者手写完成。

参数不能无限增加。一个功能如果需要很多开关才能用，说明它应该拆成更小的功能，或者退回基础语义。

## 5. 语义类型

### 5.1 三层分工

| 层 | 管什么 | "金额"的例子 |
| --- | --- | --- |
| SIR（作者写的） | 语义类型 | `金额` |
| 语义层 | 值的种类、允许的运算、约束 | 小数、两位、不能为负；只能和金额相加减 |
| Lowering | 物理表示 | `BigDecimal`、`DECIMAL(19,2)` |

语义层内部保留一小组**值的种类**（整数、小数、文本、真假、日期、时刻、标识）。它们决定哪些运算合法，与 Java 无关。作者平时不写它们，只有在定义新的语义类型时才会用到（见第 6 节）。机器类型名（`Int32`、`Boolean` 等）从语言里移除，由 Lowering 按值的种类和约束去选。

### 5.2 运算规则（倾向）

- 同一种语义类型之间才能做加减和比较。
- 不同语义类型之间的运算一律拒绝。比如金额和数量相加，作者要先说明换算方式；现在的语言里还没有乘法，这件事以后再定。
- 字面量按另一侧的语义类型理解。这和设计 10 第 23.4 节处理整数字面量宽度的方式一致。

### 5.3 内置语义类型的清单

不预先编造。确定方法是：统计 178 个现有 SIR 样例里，每个字段的名字、机器类型和约束，按"约束相同、含义相同"归类，频率高的作为内置类型，其余由作者自己定义。统计结果和清单另行提交评审。

### 5.4 改写现有样例

- 语言版本从 `sir 0.2` 升级。旧版本是否继续接受，需要负责人决定。
- 166 个 SIR 文件、约 2250 处类型写法用一次性脚本机械改写。脚本需要第 5.3 节的映射表。
- 37 个测试文件和语言参考同步修改。

## 6. 开放接口：用户自己定义语义

按"能证明的东西从多到少"分三级，能放在上一级的不放到下一级：

| 级别 | 用户能定义什么 | 能写什么 | 系统能证明什么 |
| --- | --- | --- | --- |
| 1 语义类型 | 新的语义类型 | 值的种类加纯约束，例如"序号：整数，最小为 1" | 全部 |
| 2 功能 | 新的功能 | 参数、契约，以及一段只用基础语义写成的展开模板 | 全部（展开后照常检查） |
| 3 端口 | 语义写不出来的外部能力 | 签名、失败、有无副作用；实现放在工程之外 | 只能证明接线正确，见设计 10 第 10 节 |

和设计 08 第 13 节的冲突，处理办法如下。那一节要防止的是：用户提交一套有自己执行规则的语言，绕过语义检查。第 1、2 级的用户定义没有自己的执行规则，它们只是参数化的 SIR 片段，展开后照常经过全部正式分析，所以不在那一条禁止的范围内。负责人已确认这个解释（第 10 节），设计 08 第 13 节已补一句说明。

第一轮里，用户定义写在本工程的源文件中。跨工程共享、版本管理和模块市场不在范围内。

## 7. 由变更层驱动的数据库迁移

### 7.1 分工

| 层 | 做什么 |
| --- | --- |
| 变更层 | 对旧版和新版 SIR 都编译到展开之后，用 `SemanticDelta` 得出业务层面的增删改，例如"新增实体 Label"、"Note 新增可空字段 title"、"字段 text 改名为 body" |
| Lowering | 把每条业务变化翻译成数据库操作，并判断能否安全执行。判断规则就是设计 04 第 4 节的表格 |
| 应用层 | 继承旧的迁移链，写出新的 Flyway 文件 |

比较要在**展开之后**进行。功能参数的变化（比如访问令牌从 15 分钟改成 30 分钟）先体现为展开结果的变化，再进入迁移判断。报告同时列出作者层面的变化（改了哪个功能的哪个参数）和展开后的变化。

### 7.2 身份

- Lowering 产出的表和列要带上语义身份（SymbolId）。
- 身份不写进 `schema.tsv`。更新时用当前工具链重新编译旧版 SIR，就能得到旧版每张表、每一列的身份。前提是重新编译出的结构清单和旧包里的 `schema.tsv` 逐字节相同，不同就拒绝。这样 `schema.tsv` 的格式和部署时的迁移工具都不用改（第 12 节）。
- 字段带 `@id` 时，改名不改变身份。这时迁移规划能认出"这是改名"，而不是"删一列、加一列"。改名怎样落到数据库上，第 12.5 节有一个待决定的问题。

### 7.3 保留不变的部分

- 旧版 SIR 从旧交付包的 `sir/` 目录取得。
- `schema.tsv` 继续用来核对线上数据库是否等于旧版（漂移检测），但不再用它决定迁移内容。
- 步骤③已经验收的部分全部保留：迁移链、四种迁移模式、数据摘要比对、退出码和三个 CI 实例。
- 支持范围仍然是"不变、新表、新可空列"。改名在第 1 步里只做到"能认出来，并给出明确的拒绝理由"（第 12.5 节）。

## 8. 关于"删"并入"改为空"（负责人已确认：保持独立）

先说成立的部分。现在的 `Delete` 有两种用法：从集合里移除一个元素，和清空一个可选值。第二种本来就等于"改为空"。

不建议合并，理由有三个：

1. **集合元素没有"空"这个值。** 删掉一个实体，如果说成"把它改为空"，它的身份和位置还在。这时就要再加一条规则"内容为空的元素视为不存在"，其实就是把"删"换了个名字。
2. **"空"可以是合法的值。** 对可选值来说，"改为空"可能表示"现在没有值"，也可能表示"去掉这一项"。合并后两者无法区分。
3. **数据库上的后果完全不同。** 删列（`DROP COLUMN`）会永久丢失数据，置空（`SET NULL`）只清空值，列还在。"删"是唯一需要额外确认或备份的操作。合并后，它就藏进了最日常的"改"里，迁移规划和审查都没法单独拦住它。

照同样的思路，"增"也可以说成"从空改成有值"，最后只剩下一种操作，所有区别都没了。所以建议保持增、删、改三种不变。

## 9. 实施顺序

这里只写依赖关系，不是排期。每一步都需要负责人单独授权。

1. **迁移改由变更层驱动（第 7 节）。** 它不依赖语言改动，同时修正步骤③对设计 04 的偏离。具体方案见第 12 节。
2. **功能展开机制，以"登录"为第一个功能（第 4 节）。** 验收：用功能声明重写双 Token 样例，展开后的规范化模型和现在手写的版本相同（来源槽位除外）；现有的双 Token 真实库验收和部署验收在新写法下全部通过；编辑、回写、变更都不会触碰展开出来的声明。
3. **语义类型（第 5 节）。** 先提交第 5.3 节的统计和清单，评审通过后再改语言和样例。

5. **新的挂载点（第 4.4 节）。** 按第二类功能的实际需要逐个补，每一个单独评审。

## 12. 第 1 步的具体方案：迁移改由变更层驱动

### 12.1 现在的做法和问题

`SpringBootSchemaEvolutionPlanner` 只拿旧包的 `schema.tsv` 和新版的表结构做对比，键是物理表名和列名。这带来两个问题：

- 判断"什么变了"的不是变更层；
- 不按语义身份对应，字段改名只能被看成"删一列、加一列"。

### 12.2 新的流程

| 顺序 | 谁做 | 做什么 |
| --- | --- | --- |
| 1 | 应用层 | 校验旧交付包的完整性（不变）。从旧包的 `sir/` 和新增的 `sir-entry` 文件读出旧版 SIR |
| 2 | 应用层 | 用当前工具链编译旧版 SIR，得到旧版的规范化模型和表结构。旧版表结构渲染出的清单必须和旧包的 `schema.tsv` 逐字节相同，否则拒绝（新诊断码 `SIR-APP-PACKAGE-BASE-004`）。这一步保证"重新编译的旧版"就是"线上正在跑的旧版" |
| 3 | 变更层 | 用 `SemanticDelta` 对比旧版和新版的规范化模型，得出增、删、改清单 |
| 4 | Lowering | 把清单里涉及实体和实体字段的变化，翻译成数据库步骤或拒绝理由（规则不变：新表、新可空列；其余拒绝） |
| 5 | Lowering | 自检：按语义身份对比旧版和新版的表结构，每一处物理差异都必须能由第 3 步的某条变化解释；规划出的迁移链终点必须等于新版的结构清单（原有自检保留）。任何一项对不上，记为内部错误，不发出迁移 |
| 6 | 应用层 | 写出迁移文件（不变）。导出结果新增一项：本次更新的业务层面变化清单 |

### 12.3 要改的地方

| 位置 | 改动 | 为什么 |
| --- | --- | --- |
| `sir-change` 的 `SemanticDelta.Change` | 增加 `trail`：从外到内列出这条变化所在的、带身份的元素的身份；对带身份元素的增删，也包含这个元素自己的身份 | 现在每条变化只有一段给人看的路径文本。下游要按身份定位"哪个实体、哪个字段"，需要结构化的身份。这是通用的补充，不是为迁移加的专用操作，编辑报告同样能用 |
| `DeploymentPlan.Table` / `Column` | 各增加 `symbol`：实体、主键或字段的语义身份 | 表结构和语义身份对得上，才能把变化落到具体的表和列上 |
| `SpringBootSchemaEvolutionPlanner` | 输入改为"旧版表结构、新版表结构、变更层的变化清单"，按第 12.2 节第 4、5 步规划 | 第 7.1 节的分工 |
| `sir-lowering-spring-boot` 的依赖 | 新增对 `sir-change` 的依赖 | Lowering 要读取变更层的输出。`sir-change` 只依赖 parser 和 semantic，不会形成循环 |
| `DeploymentPackageApplication` | 按第 12.2 节第 1、2、6 步改写；导出时写出 `sir-entry` | 更新时必须知道旧版 SIR 的入口文件，旧包里原来没有记录 |
| 导出结果与 CLI JSON | `Continuation` 增加 `changes`（业务层面的变化，每条一行） | 第 7.1 节：报告同时列出业务层面的变化 |

`schema.tsv`、各版本的结构清单、部署时的迁移工具（Migrate）和 `deploy.sh` 都不改。

### 12.4 拒绝理由的变化

| 情况 | 原来 | 现在 |
| --- | --- | --- |
| 字段不带 `@id` 改名 | `COLUMN_REMOVED` 加上新增列的拒绝 | 不变（名字派生的身份本来就不同，确实是一删一增） |
| 字段带 `@id` 改名 | 同上 | 列跟着改名（第 12.5 节）；主键改名以 `PRIMARY_COLUMN_RENAMED` 拒绝 |
| 实体改名 | `TABLE_REMOVED` | 不变（实体没有 `@id`，改名就是一删一增） |
| 旧包的 SIR 重新编译后和 `schema.tsv` 对不上 | 无 | `SIR-APP-PACKAGE-BASE-004` |
| 旧包里没有 `sir-entry` | 无 | `SIR-APP-PACKAGE-BASE-003`（旧格式的包不能作为基础，符合第 10 节第 3 点） |

### 12.5 改名怎样落到数据库（负责人 2026-10-17 确认：列跟着改名）

字段带 `@id` 改名时，数据库里的列也跟着改名。迁移执行 `ALTER TABLE 表 RENAME COLUMN 旧列 TO 新列`，MySQL 8 只改元数据，数据原样保留。列名始终等于字段名的下划线形式，同一份 SIR 生成的代码也始终相同。

曾考虑过另外两种办法：沿用旧列名，或者由 `@id` 决定列名。这两种都让列名和字段名分家，只有在外部程序也直接读这个数据库时才有必要。按设计 04，本系统的数据库只给生成的应用自己用，所以不采用。

| 规则 | 内容 |
| --- | --- |
| 什么算改名 | 同一个语义身份（字段带 `@id`）、表不变、除列名外所有物理属性都相同 |
| 顺序 | 改名排在建表和加列之前，后面的版本都按新列名书写 |
| 拒绝 | 主键改名（`PRIMARY_COLUMN_RENAMED`，其他表按列名引用它）；新列名和表里另一列只差大小写或相同（`NAME_CASE_CONFLICT`）；改名的同时还改了类型等属性（`COLUMN_CHANGED`） |
| 不带 `@id` 的改名 | 身份随名字变化，仍然看作删一列、加一列，照旧拒绝 |
| 迁移工具 | 交付包新增 `deploy/renames.tsv`，每行是"版本、表、旧列名、新列名"，后续版本会继承。迁移工具更新时按它把旧版的列对应到新列名，再做前后数据摘要比对；被改名的列不当作"新加的列"去检查是否为空。全新部署不用这份记录 |

- 应用层测试：现有的继承旧链、拒绝回退、篡改旧包三项照旧通过；新增"旧包缺 `sir-entry`"的拒绝。

## 14. 迁移补充：放宽与删除（2026-10-20）

负责人确认：已上线系统的结构变更再支持两类，其余照旧拒绝。

**放宽（不丢数据，不要确认）。** 一个列能装下原来装的所有值、还能装更多：32 位整数改 64 位（`Count` 改 `Serial`）、有长度的文本改更长或去掉长度、必填改可空。迁移是一条 `MODIFY COLUMN`，只重述类型、可空和默认值，唯一键和外键留在原处。一个列可以同时有几项变化，规划器让它依次经过：改名、放宽、改默认值，每步各占一个版本，合同链里的每一行都是上一步留下的样子。反方向（缩短、改必填、改成别的类型）可能丢值或被旧数据卡住，继续拒绝。MySQL 把 `INT` 改成 `BIGINT` 要复制整张表，大表会锁一段时间；这就是放宽不加 `ALGORITHM` 子句的原因。

**删除（会丢数据，要确认备份）。** 源码里不再有的实体或字段，打包时带 `--confirm-backup yes` 才生成 `DROP COLUMN`、`DROP TABLE`，否则以 `SIR-DEPLOY-UPDATE-BACKUP-001` 拒绝并说明怎么做。选这个形式而不是别的，理由：
- 删除不可回滚：数据库已经执行了 `DROP`，把文件退回旧版本也找不回那一列。所以要在谁也看得见的地方单独确认，不放进平常的修改里；
- 确认放在导出时：此时还什么都没动，随时可以取消；`update` 本身不备份，也不再问第二遍；
- 确认只是声明，工具无法检查备份是否存在，结果的 `dataLoss` 把丢什么写出来，留作记录。

迁移工具对被删的列和表不比对数据，其余的表与列仍逐行摘要比对，输出 `KCG_DATA_DROPPED`。它从合同链本身得出哪些列被删（旧合同有、终点合同没有、又没被改名），不另带一个记录文件。

**仍然拒绝。** 主键列、引用别的表的列，即使确认了也不删：删引用列要先按名字删外键约束，而合同里没有这个名字（V1 的名字按声明顺序编号，之后新建表的按版本编号），猜名字不可靠；整张表可以删。可选引用 `Optional<Ref<X>>` 的列名不带 `_id`，所以必填引用改可选引用，物理上是先改名再放宽。

**实现与验证。** `SchemaEvolution` 新增 `WidenColumn`、`DropColumn`、`DropTable`；规划器 `plan(..., allowDataLoss)`。本机：规划器 15 项、部署包 13 项、CLI 包命令测试，包括部署样例 v1→v2→v3 链（`dual-token-v3`：`Note.state` 16 改 64、删 `Note.title`、删 `label` 表）。真实 MySQL 上的验证由 CI 部署冒烟承担，待提交后的同 SHA CI。

## 15. 唯一约束的补充：冲突报错与联合唯一（2026-10-20）

试写八个典型后端（[试写报告](../qualification/TOPIC_TRIALS.md)）发现：选课、点赞、预约都需要"几个字段合起来不重复"，并且重复时要报业务错误；而单字段 `unique` 冲突时也没有地方说报什么，数据库的异常原样成了 500。负责人确认下面的做法。

**冲突报什么：**`persist 变量 else 错误名;` 现在也能写在 `create` 出来的行上（实体有唯一约束时）：生成的代码捕获 `DuplicateKeyException`，换成声明的错误。任何一个唯一约束被撞到都是这个错误；不写 `else` 的行为不变。

**联合唯一：**实体最后写 `unique (a, b);`，可写多条。规则 `SIR-VALID-014`：字段是这个实体自己的、至少两个、不可选（空值之间不算重复）、不是 `secret`、版本号或主键、不限长的文本要先限长、文本长度加起来不超过 768。数据库里是 `UNIQUE KEY kcg_uq_<序号>`；结构合同在表的列行之后加 `UNIQUE` 行，迁移工具核对复合唯一索引。

**保留数据的更新：**联合唯一只能随新建表一起建；给已有表加、删、改仍拒绝（`UNIQUE_KEY_CHANGED`），理由和给已有表加单字段唯一列一样：旧数据可能已经重复。

**没有做：**允许可选字段（它会让约束悄悄失效）；联合唯一与 Crud 的组合；给已上线的表加联合唯一前先检查旧数据（设计 04 的目标做法，另行设计）。

## 16. 原子计数（2026-10-20）

试写发现选课、下单、点赞都要“在原来的数上加减一，并且并发下不丢、不超卖”。原来的写法有两种，都不满足：普通的“读、改、写”能写但会丢更新；守卫更新能保证原子，却不允许绑定的值读自己的字段，库存减一写不出来。负责人确认下面的做法。

**不加新语法。** `update` 的绑定写成 `字段: 变量.同一个字段 + 值` 或 `- 值`，就是计数。生成的是一条 `UPDATE ... SET col = col + ? WHERE id = ? [AND 守卫]`，由数据库在存着的值上做加减。守卫的比较右边除了值，还可以恰好是目标的另一个字段（`course.enrolled < course.capacity`），写成两列比较，名额检查和加一在同一条语句里，不会超卖。

**为什么是这个形状，而不是别的：**
- 问题的根是“拿读到的值算新值再整个写回”，所以让数据库做加减；不是给每个实体加锁，也不用 `versioned`；
- 加减之外的算术没有同样的写法（`col = col * ?` 不会让并发的请求各自算对），所以本阶段不做乘法；Money 加减后来由第 20 节 G10 在严格连接与明确精度的边界内补齐；
- 其它读自己字段的绑定仍可写（不带守卫时），只在文档里提醒并发下会丢更新；一律禁掉会让原来能写的东西写不出来。

**行为：**影响行数不是 1 时，带守卫的报守卫的错误；不带守卫的以服务器错误结束（行在读到之后被别人删了）。写入后把计数列读回，返回的是存着的值。这一行只能有这一个 `update`，因为它整个写成一条语句，只写绑定的列（以前带守卫的更新也如此）。

**写入顺序。**新建一行并给它引用的行计数时，要先 `persist` 被计数的行。真实 MySQL 的外键检查会给被引用的行加读锁；先插入再改被引用的行，两个并发请求会各拿读锁、再互相等对方放开，死锁。这条没有做成编译器规则（顺序是作者写的，哪一行被另一行引用不总看得出来），写进语言参考，题目样例与部署样例按此书写，部署冒烟让同一个账号同时收藏六篇笔记来验证。

**没有做：**对 `versioned` 实体的计数（版本已经保护了这一行）；一次请求对多行计数（需要循环，G5）；`Money` 的加减。

**实现与验证。** 语义：`ValidatePass`（`SelfRelativeBinding` 认出这个形状；守卫右边可以是同一行的另一列）；降级：`Binding.relative`；生成：`LambdaUpdateWrapper` 的 `setIncrBy`／`setDecrBy`，两列比较用 `apply`。本机：语义 9 项、降级 3 项、生成 3 项；八个题目的生成工程离线编译通过，选课、商城、博客已改用。真实 MySQL 上的并发验证由 CI 部署冒烟承担：第三版部署样例给 `User` 加了 `favorites Count default 0`（链变成 V1 到 V11，多一步 `ADD_DEFAULTED_COLUMN user.favorites`），收藏时 `reader.favorites + 1`，冒烟里同一账号并发收藏六篇笔记，计数必须是 7（含先前的一次，重复收藏被回滚不计）。

## 17. 可选值：空值判断、比较与显式筛选（G7，2026-10-20）

负责人确认：`x is none`／`x is present` 判断可选值是否为空，查询、工作流校验和更新守卫采用相同含义。原来的 `.present` 不变，仍表示 PATCH 请求是否传过字段，显式 null 也算传过。`is`、`none` 是上下文词，不夺走已有标识符。

**比较规则。** 去掉可选包装后的类型须兼容。`== != < <= > >=` 任意一侧为空均为 false，两个空值也不相等；`not` 按普通布尔值取反，因此 `not (x == y)` 在有空值时为 true，不与 `x != y` 互换。判断空值必须明确写 `is none`，没有独立的空值字面量。这不是直接暴露 SQL 的三值逻辑，也不是把空值视为一个可比较的业务值。

**可选筛选没有隐式规则。** 请求没传就跳过条件，写 `(input.minimum is none or item.price >= input.minimum)`，多个条件继续用 `and` 组合。没有新增专门的筛选子句，也不让同一个比较在查询和工作流里含义不同。相比“没传就自动省略比较”，多写的空值判断换来了可见的业务意图，尤其避免授权检查被意外放宽。

**为什么这些代码存在。** 语法复用一元表达式节点，增加 `IS_NONE`／`IS_PRESENT`，引用仍按原有 Resolve binding 解析一次，源码写回保持运算优先级。Type 只对比较解开可选包装，不放开可选算术。Lowering 给可选比较写入 `PresentComparison`（底层类型、左右两侧各需不需要非空保护），IR Validator 拒绝丢失或与操作数不符的计划。Java 渲染短路的非空保护；SQL 渲染参数化的 `COALESCE(比较, FALSE)`，在外层 `NOT` 前消除 UNKNOWN。空值判断生成 `IS NULL`／`IS NOT NULL`，请求值的空值判断生成明确的真／假条件，不能用空 Wrapper 偷换语义。已有 `any` 子查询内部也遵守这个规则，不扩展它原先不支持的请求参数或工作流位置（G2/G4 留待后续）。

**样例与验收。** tasks 的指派人与到期时间改为可选，创建时可未指派；可按状态和优先级选择性筛选，并增加只允许项目所有者读取的未指派查询。可选指派人在视图里投影为可空引用编号，不引入新的可选嵌套视图能力。market 增加可选价格区间和成色筛选。部署样例 v3 在本来就新建的 Favorite 表里加可选 score，不改变 V1..V11 的迁移版本数；CI 冒烟覆盖空值筛选、`!=` 与 `not (==)`、工作流校验与更新守卫的真库行为。

**没有做。** 可选值加减、时间平移、空引用继续访问成员、默认值运算、隐式类型收窄、可选文本作为 containsLiteral 的右操作数均未放开。可选筛选不是自动过滤或自动授权。G7 之外的缺口没有借此展开。

**证据。** 本机采用 Windows 11、Temurin 21.0.11、Maven 3.9.14，串行定向测试，Maven 堆 768 MiB、测试 fork 堆 512 MiB。RED 是新语法被解析器拒绝及降级计划尚不存在；语义、降级、生成契约与 Java 真值表随后转绿。详细命令、数量及环境缺口见[验证说明](../qualification/README.md)。没有运行全量闸门、八题生成工程离线构建或真实 MySQL／HTTP；同源码 CI 为 NOT_RUN。Windows 的部署导出测试在现有安全读源边界失败（`SecureDirectoryStream` 不可用），没有为验收而放宽它。

## 18. 多行查询：关联参数与 exists／count 步骤（G4/G2，已确认并实现）

**状态。** 负责人已授权推进下一阶段。G7 已提交并推送为 `33f960b`，按要求不等待或核验 CI；这不是 CI 通过的声明。负责人随后确认本节方案，G4/G2 已贯通生产链与定向验证；负责人随后已授权将本批提交并推送、不等待 CI；实现随本提交保存，没有已核验的同源码 CI 证据。

### 18.1 当前为什么写不出

不是缺少一个现成的 `rows.count` 属性：`find` 当前面向读取／分页投影，取回列表后数行既可能只数当前页，也可能读全表，不能代替数据库计数。现有 `any` 也不是通用查询函数：

- `TypePass.typeAnyExpression` 要求条件里有 `<Ref 字段> == item`，明确把它限定为关联当前根行的子查询；`NormalizePass` 记录该连接字段，不能简单去掉 Type 的限制而沿用后续模型。
- `ValidatePass.validateExistenceUsage` 拒绝在工作流校验、赋值等位置放 `any`（`SIR-FLOW-005`），同时拒绝嵌套 `any`（`SIR-FLOW-006`）。
- `SpringBootInputValidator.validateExistsCondition` 与 `SpringBootModelLowerer.memberReference` 只接受相关列、根行列、字面量和枚举成员，不接受 `input.tag` 等外部值，因此 G4 在 Lowering 被拒绝。

提案把“关联子查询可绑定外部值”和“工作流读出一个布尔／数量”分开实现，共用既有的类型检查、引用绑定、过滤语义及 G7 空值规则。

### 18.2 先补 G4：关联条件的外部值按参数绑定

保留 `any(PostTag, post == item and tag == input.tag)` 的现有形状；其中 `tag` 与 `input.tag` 必须有兼容的引用类型（例如 `Ref<Tag>`），不为了查询把任意主键或整数自动当成引用。

在目前允许的比较位置增加外部的请求字段、actor、已加载行的标量／引用值。Resolve 仍只绑定一次；Lowering 根据 binding 区分数据库列与请求时的值，将后者写入有类型的参数计划，按固定遍历顺序编号。Generator 只渲染参数表达式和绑定，不能把请求值拼进 SQL，也不能自己重新猜变量或列。

可选参数沿用 G7：缺失时普通比较为 false；“没传就不筛选”必须在外层显式写 `input.tag is none or any(...)`。保留关联根行的要求，不把缺少连接的 `any` 静默解释为查整张表。仍不支持嵌套 any、任意 SQL 或空引用成员访问。

### 18.3 再补 G2：明确的 exists／count 工作流步骤

已实现的写法（声明与完整示例见语言参考第 5.9 节）：

```text
exists Loan where item.reader == actor and item.returned == false as hasOpenLoans;
count Loan where item.reader == actor and item.returned == false as openLoanCount;
validate not hasOpenLoans else HasOpenLoans;
```

`exists`／`count` 按上下文识别，不新增全局保留字。`item` 和已有 `find` 一样表示本次查询的行，查询结果按 `as` 声明普通的强类型工作流变量。`exists` 返回 Boolean，至少一行符合即为 true，零行为 false；`count` 返回非负的核心 Int64（Java long），没有匹配时为 0，不返回 null，不改变现有 `Count` 字段的 32 位类型。

每个步骤执行一条数据库查询。Lowering 明确存在查询／计数查询计划、源实体、谓词、结果变量及语句数量；exists 选择主键投影、固定 `LIMIT 1` 和 `selectObjs` 后转 Boolean，count 选择 `selectCount`／`COUNT(*)`，不取回全部行计数，不以“查总数再判断非零”实现存在查询。这样复用既有 Mapper，不因某个能力是否存在而改变实体 Mapper；实体产物不变性测试同时覆盖新增查询能力的删除。两者统计的是满足条件的源实体行，不是关联 join 的重复行，不带分页、排序或视图加载。

新步骤接入当前实体 `scope` 的同一注入链，不能让计数或存在查询绕过软删除范围。过滤继续复用 find 的 Boolean 组合、比较与 G7 空值行为；相关 `any` 复用 G4 的参数计划。源身份、字段和查询变量必须经过正式 ReferenceRole／binding，SourceEditor 与 SIR 写回同步覆盖新节点，不新增业务专用 Change 指令。

### 18.4 为什么采用步骤，而不直接放开表达式

- `rows.count`／`rows.empty` 容易混淆“当前页有多少”和“整个筛选有多少”，也诱导先加载数据；不采用。
- 直接让 `any`／`count` 出现在任意表达式，会把数据库读取藏进短路布尔、更新绑定或单语句更新守卫中，还需要决定重复求值与执行顺序；这不是本次普通多行查询所必需，不采用。
- 显式步骤多一行，但读取发生在哪里、读几次、之后复用什么值都可见；可以组合现有 validate、更新与返回，不为借书、预约、选课各加一个关键词。代价是本阶段 `validate any(...)` 仍拒绝，应先用 exists 步骤绑定结果。

### 18.5 读取不等于并发约束

`count < 5` 后插入不是并发限额：两个请求可能都读到 4，再各插一行。`requires atomic` 也不自动把任意范围查询变成跨行互斥。需要硬上限的借阅数、名额等，继续使用已有的行内原子计数与守卫，并与业务写入在同一事务内完成；仅新增 count 不能把试写报告的“并发安全借阅上限”记为完成。

同样，“不存在重叠预约”后插入也不能由 exists 自动保证并发互斥。固定时段继续由已有联合唯一约束兜底；任意时间段的并发排他不在本提案中隐式承诺。只读数量／存在性是本次能力，通用锁、隔离级别控制、查询后自动锁定不是。

| `writeRole: LIBRARIAN` | 写能力要求当前账号的角色等于这一枚举成员；必须同时给 writer。默认不加角色门。首轮只支持一个枚举值，不新增角色集合或任意权限表达式。 |
| `roleField: role` | writer 实体的非可选枚举字段，默认 role；仅在 writeRole 给出时消费。不是假定所有账号都有 role。 |
| `writeExclude: [status, createdAt]` | 创建和更新的输入及赋值都排除这些实体字段，视图不因此隐藏字段；默认空列表。它不是 secret，也不自动赋值。 |
| `read: public` | Get／List 不因 owner 要求认证或追加本人条件；默认不填，保持原规则。只改变模板自己的归属门，不绕过实体 scope。 |
| 既有 `path` | 增加字符串形式 `path: "my/posts"`，并继续接受单段名字；只接受静态小写段，不接受空段、前后斜杠、`..`、查询串或占位参数。各能力仍共用一个基础路径。 |

图书目录写为（library 样例已采用）：

```text
use Crud {
  entity: Book;
  path: books;
  writer: User;
  writeRole: LIBRARIAN;
}
```

Book 原来没有 owner，Get／List 继续公开；创建／修改／删除必须已登录且角色为 LIBRARIAN。当前账号不存在仍按现有 ActorBinding 返回 401，角色错误为生成的 BookForbidden（403）。角色检查先于业务行加载，不能由未获写权限的用户探测目标行是否存在。角色比较的枚举类型取自 roleField 的正式类型，作者不用重复写一个可能不一致的 roleType。

公开读、本人写且保护系统字段的组合：

```text
use Crud {
  entity: Item;
  owner: seller;
  path: "market/items";
  read: public;
  writeExclude: [status, createdAt];
}
```

这表示公开 Get／List 的所有符合实体 scope 的行，**不等于只公开 ON_SALE 的商品**。market 已有带状态条件的 BrowseItems／详情能力不应直接删掉或替换；公开读组合用独立验收夹具覆盖。market 本轮实际只需要加 writeExclude，保留已有接口和浏览业务。

writer 和 owner 同时给出时必须指向同一账号类型；写角色与归属按 AND 组合，不提供“管理员绕过 owner”。角色正确但不是所有者仍沿用原 Crud 的 404，原 owner 使用者未配置 read: public 时，读权限不变。

### 19.3 字段排除不是悄悄丢数据

字段名必须属于 entity 的合并字段集合（含 extend），重复或未知项要定位到具体元素并拒绝。若排除了创建必填、无默认值的字段，创建仍必须被正式分析拒绝，不能补零、空串或放宽实体约束；有默认值的字段沿用默认值，可选字段沿用原创建规则。owner 自动赋值、版本乐观锁、secret 的读隐藏与 PATCH 三态保持原协议。系统字段只由显式业务工作流改变。

writeExclude 生效后，客户端无论在普通更新还是 PATCH 中夹带 status，都不得改变持久化状态；未知请求字段是忽略还是拒绝沿用现有 DTO 协议，本轮不顺带全局改变 Jackson 行为。没有可写字段时不制造空 update，返回定位到 use 的结构化拒绝，要求作者手写其实际需要的能力。

### 19.4 两个通用补点，而不是一个更大的特例

1. **功能参数有明确的文本／名字列表载体。** 在现有 name、duration 外增加通用 text、names；字符串、列表和值元素有独立的 AST 表示与 span，绑定后的值保持类型与不可变顺序，不通过字符串首字符猜种类或按逗号手拆。path 兼容旧名字写法；自定义 feature 也能使用文本参数和字段列表选择器。模板只增加 names 参数作为 only／except 字段集合的能力，不增加业务循环、任意表达式求值或递归 feature。
2. **功能参数引用也按正式 binding 改名。** entity、writer、owner、roleField、writeRole、writeExclude 的真实引用点需要稳定 ID、相应 ReferenceRole 和唯一 Resolve binding；列表元素带所属实体，角色值带枚举身份，模式词 public 和路径文本不是符号引用。绑定从参数契约和模板消费位置取得，不能在 Rename 或 Normalize 里重新搜名字。SourceEditor 仍只改 use 本身并重新正式分析，不写展开声明。此修正服务内置与作者自定义 feature，不给 Change 添加 Crud 专用命令。

保持现有参数事实的编辑协议兼容；新值的 canonical 源码形式必须能经 inspect／add／update／rename／回读恢复相同的类型和值。新增引用角色时同步补跨文件正例、逐个删除 import 的同位置反例，不能再次用 allOf(ReferenceRole) 排除新角色来“修测试”。

### 19.5 为什么不采用其他办法

| 方案 | 好处 | 不选择的原因 |
| --- | --- | --- |
| 每题手写五个能力或复制一个专用 Crud 模板 | 不改编译器 | library、market 等重复授权和字段规则；同一漏洞要逐题修，普通需求重新变成长样板。复杂规则仍允许走这个出口，但不作为标准写保护的唯一办法。 |
| 只改 Crud 模板，字段名列表塞进普通字符串 | 改动小 | 解析、类型、准确诊断、改名和编辑协议都会漂移；不会真正解决一类业务的共同问题。 |
| 新增权限框架或在 Generator 识别 Crud | 看似少写 SIR | 已有 actor／validate／scope 能表达；另造权限语义及目标端分支违反展开与分层规则。 |
| 显式参数 + 通用值载体／绑定（本方案） | 常见需求短；默认兼容；全部权限落到已有 SIR；字段与引用机制可复用 | 需同时贯通 Parser、Semantic 与 Change，不能假装是模板微调。复杂多角色、逐操作例外仍退回普通 SIR。 |

### 19.6 实施与验收边界

先做通用参数载体、模板集合选择和绑定／回写的 RED→GREEN；再让 Crud 组合现有 actor、角色 validate、归属检查及字段选择，最后改 library／market。核心原则是：旧 use 的展开语义与生成文件必须不变；不在 Lowering／Generator 内引入 Crud 分支，不新增依赖，不修改迁移历史。

## 20. G10：Money 的精度、交付与金额加减（#147 已验收）

### 20.1 已核对的实现边界

| 现有事实 | 对 G10 的影响 |
| --- | --- |

已核验目标版本 MySQL `mysql-8.4.5` 的第一方源码：[my_decimal.h](https://github.com/mysql/mysql-server/blob/mysql-8.4.5/sql-common/my_decimal.h) 定义最大 precision 为 `9 * 9 - 8 * 2 = 65`；[dtoa.h](https://github.com/mysql/mysql-server/blob/mysql-8.4.5/include/mysql/strings/dtoa.h) 定义最大 scale 为 30。对应 blob 为 `12557dc4563100947eb3ee21ebc54dec718be66b`、`cb34d9755758f9bbf8d004ffb3048a272083f6ce`。不以最新文档版本冒称该目标版本依据。

### 20.2 作者看到的规则

负责人确认 Money 默认携带 `precision(19, 2)`：总共最多 19 位，其中最多 17 位整数、2 位小数，最大绝对值 `99999999999999999.99`。这是本次新增的语言规则；旧 Money 先前没有该限制。Money 不隐含非负、不带币种、不做汇率转换；需要非负的价格／金额仍显式声明 min。作者可以复用现有 where 写法：

```text
type Price = Money where min(0);
type UnitPrice = Money where precision(19, 4), min(0);
```

`precision(p, s)` 的两个参数必须是整数常量，满足 `p >= 1`、`0 <= s <= p`，且能由规则载体的整数参数表示；同层重复、错误参数个数、负数、小数及非十进制字段都正式拒绝并定位。类型派生／字段 where 的同名覆盖沿用现有协议，因此 UnitPrice 的显式四位小数替换 Money 的默认两位，其他规则保留。不会为了允许四位单价另造乘法、货币对象或一套类型转换。

MySQL 交付还须满足 `p <= 65`、`s <= 30`；目标限制在交付计划阶段明确拒绝，不把它冒充所有未来目标都必须遵守的 Core 上限。未携带精度规则的底层 Decimal 仍不能被交付层悄悄套成 Money(19, 2)。金额字段的新默认会收紧旧 Money 的合法值范围，须明确记录为语言规则变更；旧非金额源码和交付基线不应因此变化。

### 20.3 数值语义：精确可表示，不隐式舍入

判断的是数值是否可精确表示，不是请求文本写了几个字符。对于默认 Money，`1.23`、`1.2300`、`1.2300e0` 表示同一合法数值；`1.234` 拒绝；`0`、`0.00`、负数及合法指数写法按相同数值规则处理。`precision(2, 2)` 的零和 `0.99` 合法，`1` 非法。比较仍使用现有数值比较语义，不因 BigDecimal 的 scale 不同把等值金额判成不等。

输入、候选值与默认值共用同一个精确可表示判定。DTO 的 Optional 元素约束、PATCH 的 absent／null／present、普通 create／update 与版本更新均要覆盖；计算后写入值按**目标字段**规则检验，不能因为输入用了较宽的 UnitPrice 就允许数据库替两位金额舍入。缺省与显式 null 仍遵守已有必填／可选协议，precision 不负责发明新的 null 语义。

不直接把 Jakarta `@Digits` 当成全部实现：其按 BigDecimal 表示检查小数位，不能未经处理就把 `1.2300` 当四位金额拒绝。建议生成一个针对 precision 的约束与校验器，DTO 容器元素约束和候选支持代码共用判定；复用现有 Bean Validation 与生成支持文件机制，不新增外部金额库。规范化只用于判定和确定性存储／默认值表示，不通过 double 中转，也不修改调用者对象。

加、减、取负的中间结果保持 BigDecimal 精确计算，不在每个表达式内部截位。当前视图读取实体字段的金额；G10 不顺带增加计算视图、金额格式化、乘除、税费或用户可配置的舍入模式。输入和可计算候选值的范围／精度违反沿用结构化字段错误；原子写入在数据库当前值上才发生的溢出按下一节的执行失败协议处理。

### 20.4 Lowering 与交付合同

Lowering 把已解析的精度降成明确的不可变 precision／scale 计划，生成注解、候选检查与交付层消费同一事实。DeploymentPlan 增加 DECIMAL 及相应形状，不把 precision 藏进字符串 length 或 SQL 文本，不由 Generator 重读原始约束推断业务。

DDL 必须生成 `DECIMAL(p,s)`，合法数字默认值先验证，再用目标 scale 的精确形式写入，例如 `0.0` 与 MySQL 返回的 `0.00` 在合同中统一。默认值无法精确表示时，计划就拒绝，不能交给建表执行后才发现截断。添加非空金额列仍遵守现有“有明确默认值才可给已有行补列”的迁移规则。

建议仅 DECIMAL 列行在原 11 列后追加 precision／scale 两列；新读取器接受旧非金额 11 列行，拒绝缺少精度的 Decimal 行及不合法额外列。旧非金额合同逐字节不变，旧迁移历史不可重写；不声称旧二进制能读取新 Decimal 合同。现场核验读取 `information_schema.COLUMNS` 的 NUMERIC_PRECISION／NUMERIC_SCALE，默认值与类型检查不能只看 DATA_TYPE=decimal。

现有基线里的同一列若改变 precision／scale，按改变物理定义拒绝自动更新；本轮不自动放大、缩小或改写已有金额。新增／回滚金额列沿用已有迁移和清理机制。交付成功不等于获得任意精度数据迁移能力。

### 20.5 金额原子加减与并发边界

非 version 的加载行继续用既有 `field: row.field + amount`／减法及 guard／else 机制，在一条 SQL 中根据数据库当前值计算。只扩展数值形状，不引入先查余额再覆盖的伪原子更新，不取消必需的 guard，不自动生成“余额不足”业务规则，也不改变 version 路径原有禁止自相对写的规则。

金额 delta 在执行前必须可精确落入目标 scale；整数部分不因输入类型更宽就由数据库静默夹断。最终整数位是否溢出不能只验证 load 出来的旧值：并发下该值可能已经过时。本方案要求实际执行原子写入的同一事务连接具有 STRICT_TRANS_TABLES 或 STRICT_ALL_TABLES；缺少严格模式时拒绝该写入，不尝试在运行时悄悄更改服务器全局设置。实现时将检查落在真实事务连接的支持层，不以导出时／启动时另一连接的检查代替；不把 Connector/J 的默认配置当证据。

严格模式下，最终 DECIMAL 溢出必须失败并回滚，沿用数据库执行异常协议，不冒充作者 guard 指定的余额不足错误。合法 guard 不通过仍走原声明的 else；精度不合法的请求提前给字段错误。真库验收须同时验证普通越界、并发最后一步越界和显式非严格模式，证明没有截断／夹断／只改一半。输入非负、余额下界等业务约束仍由类型 min 和 SQL guard 组合表达。

### 20.6 取舍与验收

| 不选择的方案 | 原因 |
| --- | --- |
| 直接让所有 BigDecimal 映射 DECIMAL 或 DOUBLE | 没有作者契约；前者可能用数据库默认精度，后者丢失十进制精确性 |
| Money 全部用整数分 | 会改变已存在的十进制含义及 HTTP 协议，也无法自然表示四位单价 |
| 全局设置 HALF_UP 或超出 scale 自动截断 | 把业务舍入政策藏进存储层；作者无法知道金额何时改变 |
| 仅 DTO 使用 @Digits | 表示尺度和数值尺度不一致，且漏过计算后与普通 update 的目标值 |
| 只验证 load 后在 Java 算出的余额 | 并发下不是数据库实际待写值，不能证明最终结果不溢出 |

## 21. G6：精确乘法与金额乘数量（#147 已验收）

本节最初以 `303a139` 勘察；负责人随后要求继续下一阶段，已按下述范围实现。G10 金额真库在 #143 的 57 项检查通过，但部署仍未闭环；#144 在初次合同测试缺少 provider 下载失败，已单独由 `b8f2cf0` 修复，见[验证第 16 节](../qualification/README.md#ci-144-dependency-fix)。本节的 G6 完成情况见 21.6，不将旧 CI 成功外推到新源码。

### 21.1 实施前核对的缺口，不只是补一个符号

- `Sir.g4` 没有 `*` token，additiveExpression 直接接 unaryExpression；AstBinaryOperator、目标 BinaryOperator 与 ExpressionRenderer 只有 ADD／SUB。需要增加独立的乘法优先级，而不是把 `*` 塞进加减层。
- `TypePass.typeBinaryExpression` 的加减要求两侧同类数值；Int64 与整数常量已有上下文定宽，但 Int32 字段不自动变 Int64。Money／自定义金额别名的底层是 Decimal，Quantity 是带 min(1) 的 Int32。只支持同型乘法仍表达不了 `product.price * input.quantity`。
- 目标算术 IR 的校验要求两操作数与结果类型一致。Generator 根据结果类型选择 BigDecimal 方法或 Math 精确整数方法；必须由 Lowering 明确插入整数到 Decimal 的无损转换，不能让 Generator 根据字段名字或 Money 文本猜测。
- `ValidatePass.rejectArithmeticTheQueryCannotCarry` 目前只识别 ADD／SUB；find／exists／count 的列运算与 any 内运算有既有拒绝边界。新增运算必须纳入检查，不能出现解析通过却生成不了 SQL 的 D 类缺陷。
- `SirDeclarationWriter` 单独维护优先级、结合方向与操作符表；SourceEditor 使用该链写回。仅改 Parser／Generator 会破坏 inspect／edit／rename 后的表达式结构。
- `lowerProperty` 目前只为带 precision 的非 Optional 字段补 NOT_NULL；Quantity 的 min 不表达必填。与此同时，`WorkflowRenderer.renderFind` 明确把未传 page／size 默认成 1／defaultSize。因此不能为了新数量字段，直接给所有数值 DTO 字段铺 `@NotNull`，破坏已有分页缺省协议。

### 21.2 作者侧语法与类型规则

使用普通表达式 `a * b`。优先级为成员访问、一元操作、乘法、加减／时间平移、比较与布尔组合，乘法同级向左结合；括号保留作者指定的求值树。`a + b * c` 与 `(a + b) * c` 不等价，`a * (b * c)` 也不能因“数学上可结合”被改写：精确整数的中间溢出点可能不同。时长仍是现有常量时间平移，不新增“日期 × 数量”或动态时长。

| 两侧实际类型 | 结果与规则 |
| --- | --- |
| Int32 × Int32 | Int32；精确整数乘法，溢出失败，不能回绕 |
| Int64 × Int64 | Int64；沿用同类精确运算的溢出协议 |
| Decimal × Decimal | Decimal；精确乘积，无隐式舍入 |
| Decimal × Int32／Int64，以及左右互换 | Decimal；整数先无损转 Decimal，再乘 |
| Int32 字段 × Int64 字段 | 拒绝；不借本轮放开所有整数自动提升 |
| Optional、文本、布尔、日期／时间、枚举、Ref、列表等 | 拒绝；不补零、不展开列表、不因判空条件自动解包 |

整数常量沿用现有定宽和越界检查，Int64 另一侧可使整数常量定宽为 Int64；Decimal 的出现不使任意大整数常量自动成为无限宽整数。原加减、比较、赋值的混合类型规则不变，不顺带增加显式 cast、除法或取模。Money 并不是带币种的量纲类型，乘法结果只具有底层数值类型，不自动继承左右两边规则的并集。

金额中间值使用无 MathContext 的 BigDecimal.multiply，整数转换用 BigDecimal.valueOf(long)，不经 double；写入时继续按目标字段的 precision／min／max 检查。比如四位单价乘整数，结果能精确写入两位 Money 才成功；`0.1250 * 3` 写默认 Money 要拒绝，`0.1250 * 8` 可精确写为 1.00，不能各子表达式提前四舍五入。整数乘法沿用既有加减的 ArithmeticException／执行失败回滚协议，不冒充作者声明的业务错误；BigDecimal 自身指数或 scale 超界也必须失败，不宣称无限资源。

已从 OpenJDK 21 GA 第一方源码核对 [BigDecimal](https://github.com/openjdk/jdk/blob/jdk-21%2B35/src/java.base/share/classes/java/math/BigDecimal.java) 的 valueOf(long) 与无 MathContext 的 multiply，以及 [Math](https://github.com/openjdk/jdk/blob/jdk-21%2B35/src/java.base/share/classes/java/lang/Math.java) 的 multiplyExact(int,int)／(long,long)。源 blob 分别为 `094c48bc02fbed4d5b7e371aaade9cd9b3ea0fd7`、`fd5c8bb0491e6bfd894e3517e73c96f4661b5c06`；无 MathContext 的乘法保留精确值，目标字段校验负责是否能存储。不新增数学或金额依赖。

### 21.3 必须有值的算术参数，不改变分页缺省

复用现有结构化字段错误，在 Lowering 为能力中的数值算术（加、减、乘、数值取负）收集其实际引用的非 Optional 数值 input 字段，按正式 INPUT binding 产出不可变的必需值检查计划。执行工作流前统一检查；缺省／显式 null 返回 400 INVALID_REQUEST 并带字段路径，不把 null 当成零，也不让自动拆箱／valueOf 首次发现问题。只检查本能力实际算术所依赖的字段，不给整个共享 DTO 全局改变约束；字段 ID、属性名、来源与顺序由计划提供，不在 Generator 扫源码或重建引用。

纯分页的 page／size 不因此变必填，保留现有局部默认值。若作者另把同一请求字段直接用于算术，其取值必须显式传入；分页步骤的局部默认不是修改整个 input 对象的隐式赋值。不在本轮统一所有非数值字段的必填政策，不改变 PATCH 的 absent／null 协议。检查计划与现有 ValidationSupport 的 notNull／字段错误机制共用；readonly 能力若需要此检查也必须拥有对应支持产物，不能依赖软件恰好有金额列或写能力。

这会使过去可能在算术自动拆箱时报错的缺失数值提前成为字段错误，属于明确的输入边界收敛；实现前必须用实际生成 DTO／服务复现并验证。它不放开 Optional 算术。短路表达式中的非 Optional 算术输入也按此必需值契约处理；不能依赖未执行分支，把已声明为必需的数值当作可选值。

### 21.4 显式降级与原子写边界

Core 在 BinaryExpression 上记录 MUL 和正式结果类型；不改绑定字段的类型来伪装转换。Spring Boot Lowering 对 Decimal 与整数的乘法插入明确的 `IntegralToDecimal` 表达式，携带新节点 ID、origin、整数操作数与 Decimal 结果；目标 Validator 拒绝非整数／Optional 操作数、错误结果类型和缺失来源，遍历、来源图与审查入口同步覆盖。Generator 只渲染该节点和 MUL，不自行决定提升。Schema 完整性门、IR 硬化用例与通用 DTO 契约必须纳入受影响定向，不能再次只选新金额测试。

复用普通 validate、create、update 的表达式和 G10 候选校验。请求／actor／其他已加载行算出的独立数值可以作为查询参数、守卫右侧或原子增减的 amount；仍不得把 `item.price * item.quantity` 翻成 SQL。any 内算术继续沿用已有拒绝，不顺带扩展 SQL 表达式系统。

`balance: wallet.balance - (product.price * input.quantity)` 可沿用已有的 `SET balance = balance - ?`，但 amount 不能读取 wallet 自身；guard、加载行、非 version、同事务严格连接与回滚规则不变。不增加 `SET balance = balance * ?` 的原子乘法。无 guard 的普通更新仍沿用已有非版本持久化语义，不能把新增 `row.field * factor` 的普通赋值宣称为并发安全。

## 22. G11：来源行上的计算视图字段（已实现，待同源码 CI）

### 22.1 实施前核对的共同问题

以下是基线原有的落点与缺口，不把它当成“DTO 上多加一个 getter”：

- `Sir.g4.viewDecl` 与 input 共用 `fieldDecl`，目前不能写字段表达式；`AstViewField.name` 是 AstNameRef，承担引用实体同名字段的职责。计算字段的名字是自己的定义，不应继续被强制绑定到实体同名列。
- ResolvePass.resolveViewMembers 注册视图自己的 FieldSymbol 后，无条件调用 bindProjectedField／bindProjectedRelation；TypePass.typeViewFields 只核对被绑定字段的类型，没有视图来源行的表达式作用域。
- NormalizedViewField 必须携带 sourceField，再用可选 relation 区分普通列与关系；SpringBootDeclaration.ViewField 同样要求 sourceFieldSymbol、sourcePropertyName。计算值可能依赖零个或多个字段，不能伪造一个实体字段作来源，也不能偷偷把剩余名额存回实体。
- WorkflowRenderer.renderProjectedValue 处理普通返回，renderProjectionRow 处理分页／批量关联后的逐行组装，两处都直接拼 getter。必须在共同的字段取值处支持计算，否则只补一种返回路径会重现过去的 D2／D4。
- SirDeclarationWriter.writeView 当前只输出字段名和类型；不接通结构草稿、表达式遍历与正式引用，inspect／edit／rename 会丢表达式或改错名字。ViewDtoRenderer 则已是只读 final 字段加全参构造器，应保留，不另起一套 DTO 计算规则。

### 22.2 作者写法与命名规则

只为 view 新增 `= expression`，继续使用已有表达式语法与优先级，不借机放开 input／entity 的字段初始化写法：

```sir
view CourseView from Course {
  field id: Id;
  field name: Name;
  field capacity: Quantity;
  field enrolled: Count;
  field remaining: Count = item.capacity - item.enrolled;
  field full: Flag = item.enrolled >= item.capacity;
}
```

对应的完整可执行示例已加入语言参考并通过示例检查。没有等号的字段继续是原有同名列／关系投影，旧约束与引用行为不变；有等号时左侧是独立的视图字段定义，右侧的 `item` 是**该视图 from 实体的当前行**，按稳定的正式符号绑定，不是 caller 工作流中的同名变量，也不是 SQL 查询列上下文。

所有字段共享原有唯一命名空间，重复名字仍拒绝。允许显式表达式的输出名与实体字段同名，但 `item.x` 永远读实体的 x，不读另一个视图字段。因此声明顺序不影响求值，不做计算字段间依赖或拓扑排序；不能以裸字段名、`view.x` 或 `item.remaining` 访问另一个计算值（除非实体自己确有 remaining 列，此时读的是那一列）。

### 22.3 允许的值与明确不做的事情

首版是**来源行上的纯值表达式**，不是新的查询语言：

| 范围 | 规则 |
| --- | --- |
| 值 | 已有标量字面量、枚举常量、当前行标量字段与括号；不新增字符串拼接或通用函数调用 |
| 运算 | 复用现有数值加减乘、取负、比较、not／and／or、值级 is none／is present；日期／时刻只沿用已有的常量时间平移，不增加日期差或动态时长 |
| 数值 | G6 的宽度、精确溢出和 Decimal 混合乘法规则不变；整数不回绕、不随意提升、不经 double；不自动把负的剩余名额钳成0 |
| Optional | 可直接投影可空标量或做已有判空／比较；比较遇空仍按G7为false，算术不因前面判空而自动解包，不补0、不增加coalesce或条件表达式 |
| 关系 | 保留原有单行／列表嵌套投影；计算表达式不能顺着外键读取另一行的业务字段。仅沿用现有合法的引用主键取值，如非空引用的 `item.teacher.id`，不隐式加载 teacher |
| 上下文 | 不允许 input、actor、调用方局部变量、其他计算字段或 now()；显示值不因调用者或逐字段取时不同而暗中改变 |
| 查询与安全 | 不允许 any、exists／count、聚合、containsLiteral、matches、PATCH .present、secret字段的任何读取（含比较／判空）；不允许写入与外部调用 |

计算字段的声明类型必须与表达式的正式结果类型相符，沿用现有数值字面量定宽与语义类型底层类型协议，不增加新的混合加减或可空提升。计算结果只允许标量及可空标量，不用表达式构造 Ref、view、Page、List 或 Unit；关联值继续由原有关系投影声明。

与现有 view 一致，声明的语义类型不会在响应端新增 Bean Validation 或持久化约束检查，字段也不能写 where／versioned 等实体或输入约束。特别是 Money 的存储精度不等于“把展示乘积四舍五入到两位”；计算保持精确值，不能隐式舍入。如果以后要给响应规定精度／格式／值域，应另定输出契约，不能把它塞进本轮取值计划。写入时的G10目标字段校验完全不变。

数值溢出等运行失败继续采用现有表达式执行失败协议，不凭空新增声明业务错误；不能把响应投影失败当作输入400。计算基于**传入该次投影的行对象**，与同一响应里直接字段保持一致，不额外刷新行，不承诺提交时的全局最新值，也不拿剩余名额展示代替选课时的原子守卫。

### 22.4 一次绑定、显式计划、所有投影路径共用

Core 为每个视图保留明确的来源行绑定，Resolve／Type／Validate 在该作用域中处理表达式，并复用现有成员与枚举的正式引用角色。secret禁读和来源行限制在Core验证，不用字段名字符串作安全判断。跨文件实体与枚举继续执行现有可见性规则，语义类型保持全项目可见，不新增另一套import协议。

规范化模型与目标模型的字段取值已改为**互斥的封闭分支**：普通字段读取、关系投影、表达式取值。普通分支携带真实来源字段；关系分支保留原有方向、关联键和目标view；表达式分支携带有类型、有来源的表达式和所属视图的正式行绑定。不能给计算字段填自己的ID充当sourceField，不能用两个未校验的Optional让“同时有列和表达式／都没有”进入模型。能保持旧语义的构造入口保留为普通／关系分支的兼容构造器，所有模型消费者一起更新。

Lowering 复用 G6 的 IntegralToDecimal 与 G7 的空值比较计划；明确记录来源实体、行符号、成员符号、目标Java属性、字段类型和origin。独立IR校验核对分支完整性、来源行与字段归属、正式类型、节点来源和转换合法性，拒绝把另一个视图／工作流的同类型变量混入。Generator 只替换计划中正式行符号的目标变量名、渲染计划，不再从输出字段名回找实体列，不读取原始SIR、不重做类型提升。计算中没有请求输入，因此不生成G6的算术input必填检查，也不改变分页／PATCH规则。

普通返回与分页／嵌套投影共用一个字段取值实现；嵌套处的item绑定到**相关行**而不是根行。原有批量关系读取与深度限制保留，计算本身增加0条SQL；query预算与read-plan校验同步覆盖，防止每行追加查询。计算依赖的来源字段不必同时出现在响应中，取值也不依赖DTO getter的调用顺序。DTO仍接收构造时已经计算好的值、只读序列化；Optional沿用现有实体nullable值到响应Optional的边界，只包一次。

计算字段不进入实体、Mapper列映射、数据库schema或迁移计划。find的where／order仍针对实体字段；不能把剩余名额这个view输出名自动展开成SQL排序／筛选，原有列算术拒绝不放宽。新增普通显示计算无需DDL，也不变更已有版本链。

### 22.5 源编辑和结构合同属于同一项能力

新取值分支、来源行与表达式必须从规范化根模型可达，纳入Schema完整性、StructureView、canonical表示、来源图和节点遍历；不添加架构门白名单。可编辑草稿暴露作者写下的表达式，不要求调用者手工填写绑定或target属性；写回再走正式分析产生这些派生事实。

精确改名必须分别证明：改实体capacity只改右侧正式引用和原有直接投影，不误改无关文本；改计算字段remaining只改它自己的输出定义，不改实体的同名字段；改类型／枚举及跨文件成员沿正式绑定同步；表达式里的括号和求值树不丢失。add／update／delete计算字段或把普通字段改为显式表达式都通过既有编辑命令，不新增“计算字段专用”的旁路命令。

### 22.6 取舍与验收顺序

| 替代做法 | 不选择的原因 |
| --- | --- |
| 在实体里持久化remaining | 增加无必要迁移与一致性维护，普通显示需求变复杂 |
| DTO getter自己按名字找列并计算 | 类型／来源决定落到Generator，路径与序列化时机不一致，难以用IR校验 |
| 允许计算字段互相引用 | 必须引入排序、环检测与更多名字歧义，本次需求不需要 |
| 允许来源表达式随意访问关系或查询 | 隐式I/O与N+1风险破坏原有批量读取／SQL预算；这属于G2／G8的业务或聚合范围 |
| 同时做SQL计算排序、查询聚合和日期差 | 把独立能力绑在一起，无法明确这一轮闭环了哪项需求 |

先写语义／源往返的RED，再贯通互斥取值模型、Lowering与独立IR校验，最后改共用渲染和course样例。定向包括：来源字段不存在／类型不符、宽度与乘法转换、secret与外部上下文拒绝、Optional判空比较及算术拒绝、同名输出、精确改名与多源可见性、Schema／结构覆盖、缺失或跨视图来源等畸形IR。

真实生成Java必须编译并执行普通load／create／update返回、分页、嵌套一对一／一对多以及同一view的多处使用；用不同来源行值验证没有串行符号／重复Optional包装，并证明计算不增加SQL。旧视图、DTO、G6/G7/G10、关系读取和源编辑需回归，未使用计算字段的旧源码生成工程应保持逐字节不变。本机仅跑受影响定向，不全量构建、不启动应用或MySQL；八题生成工程、真实HTTP／MySQL投影和原子选课后的显示由同SHA CI承担。

course增加remaining与full，仍用原子守卫控制名额。只有实际实现与验收后才能重判“显示剩余名额”这一条；library可借数量需要跨行计数，不因本轮本行计算就算完成。G5／G8、日期差、界面和小模型评估都不在本轮范围。本机实现证据见下节；同源码 CI 仍待运行，不把新增写法直接当作真库验收结果。

## 23. G2 业务组合：显式行锁与区间预约（第一批已实现，待同源码 CI）

负责人确认继续后进入实施，基线 `359a45a` 的 #152 success。本节修正实施前草案中未闭合的取值与并发假设，不把草案当实现。第一批交付显式行锁及预约防重叠；借阅限额、课程冲突与先修课仍须后续完成。

### 23.1 复核后修正的边界

- `count Loan` 后比较不是并发借阅限额；需要读者行上的原子计数，并把借／还／重复还书的计数与 Loan 一致性共同验证。本批未改 library。
- 课程冲突即使用时段快照，也必须先锁学生行，才不会让同一学生并发选入重叠课程。旧草案只说“atomic 内先查再写”不足以保证这点。
- 旧草案的先修课片段引用了尚未取得的 `required`。`Prerequisite` 是集合，现有单行 load／exists 不能自动遍历它；必须先设计“是否存在尚未完成的必修先修记录”的受支持反关联检查。不用单门限制、客户端传入先修课或一份时段快照冒充任意集合检查。
- 排队提升仍缺稳定的首行取得及其并发归属；跨引用谓词、循环、聚合与日期差不随本批增加。

### 23.2 作者显式锁定共同父行

```text
load Room by input.roomId as room for update else RoomNotFound;
```

仅允许在 `requires atomic` 的 command 中按主键加载；readonly／query、非原子能力、`by uniqueField:` 均由 Semantic 以 `SIR-FLOW-004` 拒绝。取不到或 scope 不满足时仍用原错误。锁持有到整个事务结束，无需 persist 父行。

Core 的 LoadStep 增加显式的 `forUpdate` 事实；Scope 改写、SoftwareSchema、声明写出与 SourceEditor 都保留这一事实。Lowering 对实际执行给出两项独立事实：`forUpdate` 与 `explicitLock`；前者仍包含旧版本自动锁，后者选择通用 Mapper 的 identity locking query，不在 Generator 根据实体或业务名称猜测。

**选择与草案不同之处：**显式锁通过已有 BaseMapper 的 `selectOne(identity 条件 … FOR UPDATE)` 执行，不按能力新增／删除实体 Mapper 方法，保留实体产物不依赖能力集合的不变性。原版本条件更新的 `selectByIdForUpdate` 路径不变；显式锁也可作用于版本实体。

### 23.3 旧快照与事务内缓存必须共同处理

仅串行拿到锁还不够：MySQL 默认 REPEATABLE READ 可能在先前查询就建立旧快照；MyBatis 的 SESSION 本地缓存也可能复用前一次相同查询。两者都能使等待锁后的冲突检查继续误判“没有预约”。

Spring Boot Lowering 为包含显式锁的能力给出 `TransactionMode.READ_COMMITTED`，Generator 按计划渲染 `@Transactional(isolation = Isolation.READ_COMMITTED)`；同时在生成工程的 ApplicationConfig 中计划 `statementScopedQueryCache=true`，渲染 `mybatis-plus.configuration.local-cache-scope: STATEMENT`。该缓存设置是工程级的；未使用显式锁的软件不改变配置，其它能力的事务模式不变。独立 IR 校验拒绝丢锁、按非主键锁、GET 锁、降为默认隔离或丢弃 STATEMENT 缓存的构造模型。

这不是自动的“任意业务并发安全”：所有可能制造冲突的写路径仍须约定同一父行、先锁后检查、并在同一事务写入。多父行保持固定锁顺序；锁等待超时／死锁沿用执行失败协议，无自动重试。外部手工写库或覆盖上述运行配置不属于保证。

### 23.4 预约题目与区间语义

Booking 改为 `startsAt/endsAt: Moment`，不再将一条预约限制为一小时。合法区间满足 `startsAt < endsAt`，采用半开区间 `[startsAt, endsAt)`，所以端点相邻可共存。Book 锁 Room 后执行：

```text
exists Booking where item.room == room and item.startsAt < input.endsAt and item.endsAt > input.startsAt as taken;
validate not taken else HourTaken;
```

随后写 Booking，事务提交才释放 Room；名称保留 `HourTaken` 的声明错误，不改变为隐式数据库错误映射。唯一 `(room, startsAt)` 只是附加约束，不替代重叠检查。列表与房间日程同步按区间查询。新表模型仅用于样例新实例，不把旧 day/hour 数据自动转换。取消只删除自己的预约，不会制造新区间；本批未增加“过去的预约不得取消”等独立规则。
