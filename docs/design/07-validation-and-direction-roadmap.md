# 第七步：验证主线、分阶段推进与方向决策

日期：2026-09-08。状态：推荐设计草案。汇总 [01](01-product-and-delivery.md)、[02](02-sir-language-and-modules.md)、[03](03-compiler-and-generated-backend.md)、[04](04-database-evolution.md)、[05](05-source-package-and-docker-deployment.md)、[06](06-web-platform-and-build-cache.md)。

本文定义主设计目标如何验证；当前实现与当次测试单独见[证据对照](implementation-baseline.md)。实施编号统一为 G0–G7；00–07 仅为文档顺序，不替换仓库 Q 系列活动工作单。当前具备承接 G0 的源码基础，不据此宣布 G0 已完成。

## 1. 验证的基本单位

每个能力必须记录目标、输入、执行路径、预期结果、实际证据和用户可见效果。一个测试通过只能证明对应层级，不能把 Parser 测试、构建成功、容器健康和完整业务验收合并为“全部可用”。

设计场景使用稳定 scenarioId。验收报告同时标识工具链、SIR、Profile、生成包、测试定义和环境版本；平台测试与本地部署分别记录。未执行、跳过、阻断、失败和通过保持独立状态。

## 2. 贯穿数据模型与版本

主线为学生选课，采用 02 的目标能力。为验证持续修改，版本切分如下：

| 发布 | 主要变化 | 数据库要求 |
| --- | --- | --- |
| r0001 / s0001 | Account、Student、Course、Enrollment；初始 Student 尚无 email/yearGroup | 空库初始化，固定主键与关系 |
| r0002 / s0002 | Student 新增可空 email；Course description 从 500 扩大到 1024 | 保留全部旧字段，旧学生 email 为 null |
| r0003 / s0003 | Student 新增必填 yearGroup，明确旧记录回填 UNSPECIFIED | 先新增可空列、回填、验证、再非空约束 |
| r0004 / s0003 | 仅调整接口说明或一个不收紧旧数据规则的 query 投影 | 无新迁移；仍核验实例、父发布与 schema |

r0001..r0004 是该固定实验的标签，不意味着产品发布必须无空缺连续编号。每版只接受其直接 parentReleaseId 更新；测试中跳过父版本应按契约阻断。

## 3. 固定数据集

固定时间戳、角色和实体 ID；密码只用隔离测试凭据。每个测试从明确快照开始，不依赖上一个测试留下的变化。

| 对象 | 基础数据 |
| --- | --- |
| 账号 | 一个 ADMIN，三个各自关联 Student 的 STUDENT，以及一个 disabled 账号 |
| Student | 1001、1002、1003；不同学号；姓名包含中文、非 BMP 字符或组合文本 |
| Course 2001 | capacity=2，enrolledCount=1；有一个 ACTIVE 报名 |
| Course 2002 | capacity=1，enrolledCount=0；用于并发名额场景 |
| Enrollment 3001 | Student 1001 -> Course 2001，ACTIVE |
| Enrollment 3002 | Student 1002 -> Course 2001，CANCELLED；重新激活必须复用记录 |

增加独立边界 fixture：description 的 null、空串、最大合法码点长度；精确小数值对象；日期/时间点；不同大小写编号；新增唯一约束所需的重复数据；外部 ALTER 漂移。重复数据不能插入已有唯一约束列来伪造测试，应针对原本未唯一、准备新增约束的专用字段构造。

迁移验收在停写条件下对每个旧主键与受保护字段逐一比较，并校验关系。只比较表行数或成功退出码不合格。

## 4. 语言与生成验证

| scenarioId | 输入/动作 | 预期证据与可见效果 |
| --- | --- | --- |
| LANG-01 | 对同一声明跨文件移动/重命名并保留 ID | binding 指向同一 SymbolId；相关输出正确更新 |
| LANG-02 | 重复声明 ID 或不存在的引用 | 所属阶段、code、数量和 SourceSpan 正确；无候选包 |
| LANG-03 | Date 与 Long 比较、错误关系基数 | Type/Validate 各自诊断，后续不重新按名称修复 |
| LANG-04 | 插入查询条件、保留已有 nodeKey | 引用点身份合理稳定；位置对应当前源 |
| LANG-05 | 未支持扩展、任意源码片段 | 明确拒绝；不会生成空方法或执行任意脚本 |
| GEN-01 | 相同完整输入重复生成，切换 Locale/工作路径 | 文件路径、顺序和字节一致 |
| GEN-02 | 故意提供冲突的 Lowered DTO/SQL/路由 | Generator 前模型校验失败 |
| GEN-03 | 构建完整源码包 | app 与部署执行器均可构建，不依赖平台私有二进制 |
| GEN-04 | 删除某个模板必需输入 | 明确内部错误，无半成品可下载 |

LANG-04 需要源位置独立于身份的实现证据；不能因为一个缓存返回旧 AST 而“看上去 ID 没变”。GEN-01 比较实际字节，不只比较文件数量。

## 5. 业务验收

| scenarioId | 输入/动作 | 预期结果 |
| --- | --- | --- |
| BIZ-01 | 管理员创建/查询/修改课程 | 正确状态码、返回投影和数据库值 |
| BIZ-02 | 非法长度、缺必填、未知请求字段 | 400 与字段错误；无写入 |
| BIZ-03 | r0002 中 PATCH 缺席 email / 显式 null / 新值 | 分别保留、清空、替换；version 按成功操作递增 |
| BIZ-04 | 两次使用同一个 expectedVersion 修改 | 一次成功，另一次 409；没有丢失更新 |
| BIZ-05 | 含中文与字面量 %/_ 的查询、不同分页参数 | 查询字面量、total、排序正确；非法页参数 400 |
| BIZ-06 | 关联过滤导致多个关联匹配同一根记录 | 根记录不重复，关联读取 SQL 次数满足预算 |
| BIZ-07 | 未登录、错误角色、查询他人报名 | 分别 401、403、按归属过滤后的 404；无越权数据 |
| BIZ-08 | 两个学生同时争抢 Course 2002 一个名额 | 恰好一个有效报名；另一请求 409；enrolledCount=1 |
| BIZ-09 | 同一学生并发重复报名 | 仅一个 ACTIVE 记录，计数只增加一次 |
| BIZ-10 | 连续取消同一报名 | 首次成功，第二次 409；计数不重复减少 |
| BIZ-11 | 重新激活 Enrollment 3002 | 复用原 id，重新检查名额，行数不增加 |
| BIZ-12 | 写计数后注入报名写入失败 | 事务回滚，计数与报名都保持前状态 |
| BIZ-13 | 会话登录、取得 CSRF、退出再写入 | 示例可对接；失效会话被拒绝，不能靠关闭安全配置通过 |

并发场景通过同步屏障制造真实竞争，不只是顺序调用两次。事务从实际 HTTP/Service 代理入口执行；数据库使用真实目标 MySQL。

## 6. 数据库与部署验证

| scenarioId | 输入/动作 | 预期结果 |
| --- | --- | --- |
| DB-01 | 空库 INITIALIZE 至 r0001 | READY，history 与声明一致 |
| DB-02 | 重复同一初始化请求 | 验证后返回既有结果，无重复建表/账号重置 |
| DB-03 | r0001 -> r0002 | 旧行、旧值、关系不变；新增 email=null |
| DB-04 | r0002 -> r0003 | yearGroup 全部按声明回填，约束建立，旧字段不变 |
| DB-05 | r0003 -> r0004 | 没有新迁移，部署版本改变，schemaVersion 保持 |
| DB-06 | 删除 description 并修正所有 SIR 引用 | Core 可合法但迁移规划拒绝删除；无 DROP 输出 |
| DB-07 | 缩短字段、缩小数值精度、新约束冲突 | 对应阶段阻断，不截断或清理数据 |
| DB-08 | 脚本改写、history 改写、额外表/触发器 | 包校验或漂移检查失败；不自动 repair |
| DB-09 | DDL 后、history 记录前注入中断 | DB_RECOVERY_REQUIRED，保留已提交结构及证据 |
| DB-10 | history 完整、最终数据库元数据发布前中断 | 显式 recover 核验后完成发布，不重跑 SQL |
| DB-11 | 已 READY 后 app 启动失败 | 数据库不回退，本地 FAILED，提供应用诊断 |
| DEP-01 | 干净 Docker 机器下载 ZIP 冷构建 | 无 JDK/Maven/MySQL/KCG 安装即可部署 |
| DEP-02 | 新版解压到中文/空格路径，旧目录不在 cwd | 找到原 environmentId 和持久卷，数据保留 |
| DEP-03 | 删除任一必要卷后运行 update/start | TARGET_MISSING，无新空卷，无假成功 |
| DEP-04 | 两个入口并发部署同一实例 | 仅一个获得协调权，另一明确忙或阻断 |
| DEP-05 | 平台不可达，公共依赖可达 | 已下载包仍可构建与部署，不要求平台登录 |
| DEP-06 | 构建失败、网络失败、端口冲突 | 明确分类；更新构建失败时旧服务继续运行 |
| DEP-07 | 错项目、多实例、跳版本、同 releaseId 不同摘要 | 不接管错误目标，不覆盖旧数据 |
| DEP-08 | stop、重建镜像、修改显示名、丢失脚本执行位 | 数据与配置保留；系统 shell 路径仍可使用 |

数据库中断点按实际驱动/Flyway执行边界注入，并明确区分可自动继续与需要人工裁定的情况；无法自动恢复不等于允许清库。测试报告必须暴露恢复边界。

## 7. 平台与缓存验证

| scenarioId | 输入/动作 | 预期结果 |
| --- | --- | --- |
| WEB-01 | 两个保存请求基于同一 draftRevision | 一个成功，另一个冲突；不丢修改 |
| WEB-02 | Agent 提案晚于用户新编辑返回 | 旧提案不覆盖新草稿 |
| JOB-01 | 相同幂等键重发/不同输入复用键 | 同输入同 job；异输入 409 |
| JOB-02 | 租约过期后旧 Worker 继续提交 | 候选不能改变当前任务或发布 |
| PUB-01 | 两个候选以同一 parent 发布 | 只一个成为 head；另一个 HEAD_MOVED |
| PUB-02 | 每个 PublicationIntent 阶段中断 | 按 CURRENT 方向恢复，无双重发布或旧状态回写 |
| PUB-03 | 不完整包、未提交 Release 被下载 | 不可见，不返回半成品 |
| CACHE-01 | 关闭/开启缓存生成相同输入 | 确定性输出一致 |
| CACHE-02 | 只改标题、Java 包名、API 字段名 | 受影响输出重新生成，无旧名称泄漏 |
| CACHE-03 | 修改模板、Profile、fixture 或测试版本 | 相应缓存失效，证据不冒称当次执行 |
| CACHE-04 | 另一个项目请求相同摘要 | 先鉴权，私有源码/产物不泄漏 |

缓存命中率只是成本指标，不能替代正确性指标。数据库现场检查不因平台缓存命中被跳过。

## 8. 推荐推进顺序

| 门 | 主要交付与依赖 | 完成门与验收方向 |
| --- | --- | --- |
| G0：现有链路资格收口 | 当前起点：单文件编译、Lowered、Generator、PSG、受支持 Change 与本地文件事务；冻结真实支持矩阵 | 标准 clean 构建、生成样例编译、诊断/确定性与文件故障恢复证据；B0/B1/未知 CURRENT 均验证，排除测试明确记录 |
| G1：单文件课程业务切片 | 在 G0 上先一个实体及查询，再扩展 CRUD、分页、校验、关联；继续生成 SIR/修改 SIR | BIZ-01..06 的基础业务与反例，GEN-01/02；真实 MySQL 中验证 HTTP 和数据结果，测试建库设施不冒称产品 INITIALIZE |
| G2：持久身份与受控模块 | 在 G1 上明确身份格式兼容、多文件源清单、import/binding 与稳定物理映射；不做模块市场 | LANG-01..05；显式旧身份映射、重复 ID、同名重建、改名/移动、引用闭包与旧 Bundle 不被误读 |
| G3：数据库生命周期 | 依赖 G2 的身份及旧/新 schema；实现 INITIALIZE、UPDATE、历史、漂移与恢复 | DB-01..11，连续两次保留数据更新、逐主键逐字段比较及真实 DDL 中断；文件事务测试不抵扣 |
| G4：完整源码与 Docker 交付 | 在 G3 上封装清单、完整构建源码、bootstrap、部署执行器、脚本、持久卷与依赖配方 | GEN-03/04、DEP-01..08；仅有 Docker 的机器能运行已取得的包，平台不可达仍可部署，目录/名称变化不丢数据 |
| G5：完整课程业务 | 在前述基础上完善登录、会话、角色/归属、选课/取消、名额和事务 | BIZ-01..13 全部必要场景，真实并发不超额、失败回滚、无人工源码补丁；重新验证生成交付包 |
| G6：网页平台与可靠发布 | 接入已验证的编译/包链，实现需求提案与 SIR 编辑、任务隔离、下载、发布协调 | WEB/JOB/PUB 必要场景，实际网页到本地部署闭环；所启用的缓存通过 CACHE；不将文件 B1 当作 Release 可下载 |
| G7：独立试用与换题 | 活动报名、学生试用、大创对比证据；主线功能门均通过 | 第二题与持续修改、完整数据保留、人工介入记录；依据证据决定模块拼装与共享缓存等后续方向 |

各阶段都保留最终网页交付目标。G1 起固定输入与隔离目录，G2 冻结身份，G3 保护数据库，G4 保护持久卷，G6 验证平台发布协议。G1–G4 未完成权限时只用于隔离开发验证；G5 证明完整业务，G6 才证明完整产品入口。某项实现可提前准备，但依赖完成门不能被跳过。

上述 G 阶段取代本组草案旧的双重阶段编号；基础框架只引用此表。r0001..r0004 是数据库实验发布标签，不是 G 阶段，也不是仓库 Bundle 编号。阶段通过需要当次证据，当前源码基础不等于相应完成门已关闭。

不按“Parser 全做完，再所有 Semantic，再所有模板”的横向方式一次性铺满语言；每个切片包含所需的端到端路径和对应反例。先用一条 query 证明契约，再扩展其他业务能力。

## 9. 每张后续工作单应包含什么

工作单需要目标场景、依赖文档与版本、允许修改范围、不可破坏契约、要新增的 SIR 能力、生成及部署可见效果、失败用例、执行命令和报告位置。以本轮源码对照为起点，实施时复核实际依赖模块和当次测试；本设计不自动授权修改生产代码。

完成门不允许“基本可用”“大部分通过”作为替代。若受环境限制未跑真实 MySQL、Docker 或平台故障用例，记录具体阻断和未验证范围，不用单元测试数量补足。

## 10. 大创验证与使用价值

推荐建立至少两道固定题目，每道包含首次交付与两轮变更需求。比较 Agent 直接开发与 Agent + KCG-Code，固定模型、工具条件、题目、时间预算和判分场景；实验前约定次数与失败计分，不能只挑成功样例。

记录到首次可运行的耗时、业务场景通过率、人工介入次数、两轮修改成功率、数据保留、危险变更阻断和冷/热构建时间。人工修补生成 Java 应记为该工具路径未完成，修复 SIR/工具链后单独记录重试结果。

模块复用的证据是第二题减少了哪些定义和修订，并且业务测试仍正确；Docker 缓存的证据是哪些阶段少花了时间。两者不能混成一个“复用率”。

试用报告同时收集用户能否理解诊断、找到接口文档、取得本地凭据、完成更新和识别失败。商业化需要这些真实使用证据，不能从架构完整或一次答辩演示直接推出。

## 11. 下一方向的选择规则

| 观察到的主要问题 | 优先行动 | 暂缓 |
| --- | --- | --- |
| 需求表达经常失败 | 改善 SIR 能力、诊断和 Agent 提案协议 | 拖拽界面、云端共享缓存 |
| 源码可用但安装耗时长 | 改善依赖镜像、构建缓存与部署反馈 | 新业务模块市场 |
| 更新经常需要人工处理 | 缩小支持范围、补迁移/恢复协议与故障测试 | 在线迁移、复杂拆表 |
| 第二题能稳定复用模块 | 引入明确模块包与表单式组合 | 通用任意模块拼接 |
| 生成快但构建慢 | 优化依赖和构建环境，评估预构建镜像 | 先做复杂 SIR 增量编译 |
| 多人试用遇到发布竞争 | 完善队列、发布协调与资源预算 | 立即拆成大量微服务 |

模块包、共享缓存与“搭积木”沿同一套 SIR 接口演进。只有主线已经证明能首次运行、持续修改并保留数据后，再依据观察选择下一条投入方向。

## 12. 推荐报告格式

每阶段报告使用“目标 -> 当次证据 -> 用户可见效果”，附未通过/未执行项目和下一张工作单建议。证据来自当次命令、测试报告、HTTP 响应和数据库比较；引用历史结果时明确日期与范围。

一份报告分别列出平台验证、生成工程验证和本地 Docker 验证。缓存复用证据标明来源；文档评审通过不记录为功能测试通过。本文件中的所有场景目前都是计划，不填写虚构的通过数量。
