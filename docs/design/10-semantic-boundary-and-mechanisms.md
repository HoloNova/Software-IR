# 机制与语义的边界：以双 Token 认证为起点

- 日期：2026-10-15。
- 状态：**DRAFT**。记录负责人与执行者在 2026-10-15 讨论中确认的方向，以及 S2（设计评审）要回答的问题。**目标设计，不授权实现，不代表任何能力已存在。**
- 依据：[MAIN](../../MAIN.md) 第 1.1 节与规则 9、10，[ADR-026](../architecture/ADR-026-layered-semantic-command-architecture.md)，[ADR-027](../architecture/ADR-027-git-as-version-history.md)，[设计 02](02-sir-language-and-modules.md) 第 9–10 节，[设计 03](03-compiler-and-generated-backend.md) 第 10 节。
- 起因：公开 CLI 阶段验收后，规划下一阶段时提出“双 Token 认证能否在软件语义层表示”，它关系到 SIR 的基础概念：软件语义是否被基础组件绑死。

## 1. 已确认的方向

1. **SIR 描述软件语义，不增加基础组件的词汇。** 例如 HTTP 方法不是 SIR 作者写的，由降级阶段按能力种类和输入形状选择（`SpringBootModelLowerer.lowerHttpMethod`：查询为 GET，局部更新输入为 PATCH，其余为 POST）。“没有 DELETE”是当前 Profile 的映射，不是语言缺口；真正的问题是语言有没有“移除一条记录”的语义。
2. **分层判断。** 一个细节放语义还是放 Profile，问一句：换掉这个选择，符合契约的客户端或验收测试会不会察觉？不会，是机制，留给 Profile（JWT 还是不透明串、签名算法、Header 还是 Cookie、MySQL 还是 Redis）。会，比如“令牌必须是 JWT，因为别的服务要验”，它是目标约束，写在 `target` 里，降级时检查 Profile 是否支持，不支持就诊断，不悄悄满足。
3. **双 Token 的方向是更高层的修饰。** 登录是语义（用凭据确立身份），双 Token 是对“身份如何跨请求延续”的修饰（访问令牌有效期、刷新令牌有效期、是否轮换）。这与语言现有的写法一致：`requires atomic / readonly / authenticated` 本来就是挂在能力上的修饰，由降级决定实现。这是方向，不是冻结的语法。
4. **要建语义系统，不靠源码补洞。** 目前搭不出来的东西，多数是“还没实现”，不是原理上做不到。语义不完整的部分，补充路径是**登记的、类型化的端口**：SIR 声明端口的签名和契约，生成器产出接口，实现放在工程之外。这不是“嵌入任意源码”，所以不违反 MAIN 规则 10；MAIN 第 1.1 节本来就写了“扩展按登记的契约和负责人的明确授权执行”。负责人已确认把它作为 S2 的设计内容，实现另行授权。

## 2. 现状（已逐项核对代码）

- `requires atomic`：生成的服务类加 `@Transactional`（`ServiceRenderer`），整条工作流在一个数据库事务内。不加锁，不防两个事务同时读到同一行。
- 条件写入 `persist … else`：只用于带 `version` 字段的实体。校验 SIR-VALID-004 规定，带版本实体的 `update` 必须由该实体的 patch 输入驱动，`else` 只报告“行的版本与读到时不一致”。因此**服务端自己决定的状态流转今天写不出来**：带版本的要客户端 PATCH 驱动，不带版本的没有并发保护。
- 工作流步骤只有 `validate / load / find / create / update / persist / return`，没有移除记录的步骤。
- 认证：`requires authenticated` 加 `actor Ref<实体>`，生成工程里是 `ActorIdentityAdapter` 接口（`external` 模式要求部署方提供约定名字的 bean），另有 `local-fixed` 本地固定身份模式。没有登录、会话、令牌、角色。设计 02/03 描述的“标准身份能力”（登录、退出、当前身份、CSRF，首轮内存会话）尚未实现。
- 表达式里有 `now()`；没有散列、随机串、签名。`uuid` 只是实体主键的生成策略。
- 没有源码块（语法里没有 java、sql、native 一类构造）；生成工程不允许手改（ADR-027）；代码里没有“扩展登记”机制，它只出现在设计 02。
- 数据库初始化与迁移还不是产品能力，生成工程的表结构在测试里由夹具建立。
- 手写的 `ActorIdentityAdapter` bean 怎样交付：已核实，见第 10.2 节。

## 4. S2 要回答的问题（只设计，不实现）

1. **刷新凭据存在哪里。** 作者显式声明一个实体并由修饰引用它，还是无状态令牌（做不了作废和轮换，语义更弱）。数据库初始化不是产品能力，所以修饰不能暗含一张隐藏的表。答案草稿见第 8.1 节。
2. **“基本语义”采用哪种形态。**（答案草稿见第 8.2–8.3 节。） 用同一份双 Token 拆解，对照两种做法各写出作者要写的内容和各自新增的东西：修饰形式（登录加延续策略），与纯 SIR 组合（作者自己声明凭据实体与流程）。**切换条件**：如果“账号密码登录，访问令牌 15 分钟，刷新令牌 7 天并轮换”这样一句普通需求，用组合写出来仍然绕口，就把稳定下来的组合升级为内建修饰。
3. **“带条件的状态流转”的最小语义。** 条件的形式、冲突如何报告、与 `version`、`atomic` 的关系。答案草稿见第 9 节。
4. **登记端口的契约。** 声明什么（签名、契约、失败语义），生成什么，验证怎样兜底（端口后面的逻辑 SIR 看不见，只能靠业务判题器），报告里怎样标出“含外部实现”，以及上面“未核实”的交付问题。
5. **小规模模型实验的接入。** 需要第一道实验题、实验手册、外部“题目测试包”的格式，以及判题器与隔离数据库的生产版实现；业务判题器和数据库沙箱目前只存在于测试代码中，CLI 没有对应命令。
6. **移除记录的语义**与状态流转的取舍。

负责人 2026-10-15 的定位：双 Token 是对系统扩展性的测试，不是一次能力提升。本节只记录读数，不冻结语法，不授权实现。

### 7.1 被测样本（负责人已确认）

需求句子：账号密码登录，访问令牌 15 分钟，刷新令牌 7 天并轮换，登出后作废。

客户端可观察的七条行为：①登录成功得到一对令牌；②有效访问令牌可调用受保护接口；③过期访问令牌被拒；④有效刷新令牌换得新的一对，旧刷新令牌随即失效；⑤重放旧刷新令牌被拒；⑥登出后刷新令牌失效；⑦错误密码被拒，且不泄露账号是否存在。

判据来自第 1 节第 2 点：换掉这个选择，符合契约的客户端会不会察觉。下表的“结果”是编译器的真实回应；诊断码取自 `check` 输出。

| 行为 | 样本与结果 | 缺口 | 归类 |
| --- | --- | --- | --- |

### 7.3 读数：补一个修饰要碰多少处

用已有的三个 `requires` 词作参照（只数引用位置，来自代码检索）：

- `Sir.g4` 把 `authenticated | atomic | readonly` 写死在 `requirement` 规则里，词法里每个词各占一个记号。新增任何修饰都要改语法。
- `AstRequirementKind` 枚举；`SirAstBuilder.requirement()` 里只有 authenticated 的判断，其余用 `ATOMIC() != null ? ATOMIC : READONLY` 兜底，第四种词必须改这段写法。
- `ValidatePass` 有 `SIR-VALID-001`“requires 必须按 authenticated, atomic, readonly 顺序”，顺序列表在 `SirDeclarationWriter.REQUIREMENT_ORDER` 里再写一遍。
- 降级在 `SpringBootModelLowerer` 约第 507 行把词映射为 `authenticated` 与 `TransactionMode`；生成器消费降级后的标志。
- `NormalizedCapability.requires` 是通用的 `@Fact @Keyed` 列表；`sir-change` 的指令层没有任何引用。

读数：新增一个修饰词，改动落在 parser、semantic、lowering、generator 四个模块、至少七处，指令层（Change／Command）不需要改。这支持 ADR-026 的一半：新增语义不必重复修改指令；但也说明，**语法层没有“登记新修饰”的缝，每个修饰都是一次语法改动**。另外 `target { … }` 的六个字段同样写死在语法里，没有位置声明“令牌必须是某种格式”这类目标约束，第 1 节第 2 点说的约束要先有这个位置。错误状态码白名单（400/404/409）是同一类刚性：它写在校验里，不是可登记的表。

| 缺口 | 靠组合？ | 普通需求是否绕口 | 一类业务受益 | 判断 |
| --- | --- | --- | --- | --- |

### 7.5 暂定结论与待办

- 双 Token 本身不是一个孤立的大功能：七条行为里有两条（凭据值、登出作废）现有 SIR 已能组合写出；其余缺口分属几类通用能力（时间运算、带条件的状态流转、按键取唯一一条、延续策略、状态码），每一类都不只服务于双 Token。
- 实测多出的两个缺口（按键取唯一一条、401／403）比读代码时预想的更基础：它们不属于“认证”，是任何业务都会碰到的。这说明探针量到的是语言的通用能力边界，不是双 Token 的特殊要求。
- 这支持“推荐搭语义系统”的方向；读数也暴露了语法层的刚性（7.3），后续任何语义补充都要先回答“新词往哪里登记”。
- 第 4 节第 1、2 问（刷新凭据存哪里，修饰形式与组合形式的对照）可以据此写：组合形式下刷新凭据只能是作者声明的实体（无状态分支已排除）；对照时要把上表的缺口逐项列入两种形式各自“新增什么”。
- 局限：样本只到 GENERATION，没有构建或运行；`now()` 渲染只看了一个样本的生成代码；没有测并发。这些结论是语言能力边界的读数，不是行为验证。

## 8. 第 4 节第 1、2 问的答案

状态：负责人 2026-10-15 确认按本节推荐的方向（8.1 的实体存放、8.3 的“先组合、后升格、修饰定义为展开”）；8.4 的开放问题仍待回答。本节不冻结语法，不授权实现。下面出现的写法都是示意，用来比较“作者要写什么”，不是语法提案。依据是第 7 节的实测读数。

### 8.1 第 1 问：刷新凭据存在哪里

| 选项 | 结论 | 理由 |
| --- | --- | --- |
| 无状态令牌（不落库） | 排除 | 表达式没有签名；即使 Profile 能签，也做不了作废和轮换（7.2） |
| 修饰暗含一张隐藏的表 | 排除 | 数据库初始化与迁移不是产品能力（第 2 节）；作者在 SIR 里看不到这张表，它的结构变化无处追溯，也违背“SIR 是唯一的源” |
| **作者声明一个普通实体，修饰引用它** | **建议** | 它和其他实体走同一条路径（表结构、版本变更、生成），不新增一类隐藏产物；7.2 已证明这样的实体现在就能声明和读写 |

建议的含义：

- 凭据实体是普通实体。修饰（或后述的展开）只规定它必须**扮演哪些角色**：属主（引用账号）、失效时刻、已作废标志，轮换时还要“已使用”标志。哪些字段扮演哪个角色由作者显式指定，Validate 检查类型，不靠字段名约定，与现有“类型化引用位置绑定”的风格一致。
- 访问令牌的形态是 Profile 的机制选择：落库的不透明串，或签名串。客户端察觉不到差别，按第 1 节判据留给 Profile；若 Profile 不支持作者要求的形态，降级阶段给诊断，不悄悄替换。刷新凭据则必须落库，因为作废和轮换需要状态。
- 这条结论不依赖尚未解决的数据库初始化问题：该问题对所有实体一视同仁，本方案没有让它变糟。

### 8.2 第 2 问：两种形态逐项对照

被测需求同第 7.1 节。下面“作者要写”的数量是示意，用来比较体量，不是精确行数。

**形态 C：纯 SIR 组合。** 作者声明账号实体和凭据实体，自己写三个能力：登录（按账号名取账号、校验口令、创建带失效时刻的凭据）、刷新（取旧凭据、条件流转为已使用、创建新凭据）、登出（作废）。再加一处声明，告诉 `requires authenticated` 访问凭据如何识别出 `actor`。作者要写的：两个实体、三个能力（各约六到十步）、一处连接声明。

**形态 M：修饰。** 登录是语义，双 Token 是挂在登录上的“延续策略”，示意：

```
login Account by name, password        // 语义：用凭据确立身份
  continuity { access 15 minutes; refresh 7 days, rotating; store Credential }
```

作者要写的：两个实体、一处登录声明、一处延续策略，受保护能力照旧写 `requires authenticated`。刷新与登出由谁提供是个问题：隐式生成的能力不在作者的 SIR 里（见 8.4）。

| 项 | 形态 C：纯组合 | 形态 M：修饰（按私有实现） |
| --- | --- | --- |
| 作者要写的体量 | 大，普通需求仍绕口 | 小，接近需求原话 |
| 需要新增的通用语义 | 按键取唯一一条、时间运算、带条件的状态流转、401／403，各自都被别的业务复用 | 同样的东西被修饰的降级私下实现，**通用缺口留在原地**，别的业务得不到 |
| 认证专属的新增 | 凭据与认证的连接声明 | 登录声明、延续策略、隐式能力 |
| 三条规则：靠组合已有能力 | 是（缺口补上之后） | 否，是一个新的整体 |
| 三条规则：普通需求是否绕口 | 是 | 否 |
| 三条规则：修一次让一类业务受益 | 是 | 否，只有登录类业务 |

### 8.3 建议：先组合，再升格；修饰定义为组合的展开

两种形态不是二选一：

1. **先补通用语义，用组合把双 Token 写出来。** 这一步同时是探针的验收：写出来了，才说明语言真的够用。
2. **再把稳定下来的组合升格为内建修饰，修饰的含义定义为“编译期展开成上面那段组合”**，而不是一段私有的降级代码。这就是第 4 节第 2 问约定的切换条件：普通需求句子用组合写仍然绕口，就升格。展开保证三件事：通用缺口必须被真正补上；展开后的节点能在规范化模型里看见和解释；修饰只是糖，不是新的基础组件。

这与负责人最初的两个方向一致：“做成软件基本语义”和“通过现有 SIR 做固定搭配”是同一件事的先后两步。

依赖顺序（只列依赖，不排期）：按键取唯一一条 → 时间运算（失效时刻）→ 带条件的状态流转（轮换）→ 401／403 → 口令只存摘要 → 凭据与认证的连接 → 修饰糖。

### 8.4 本节仍然开放的问题

- 展开出来的节点（刷新、登出能力）没有源文本，它们的稳定身份与来源怎样登记，指令层怎样引用，需要先回答。设计 02 的稳定身份规则是否够用，未核对。
- 连接声明（凭据如何识别 `actor`）放在哪里：能力上、实体上，还是延续策略里。
- 角色绑定的写法：逐字段显式指定，还是整体声明“这个实体是凭据”。
- “按键取唯一一条”的最小语义：不存在时的错误怎样声明，键是否要求唯一约束；数据库初始化不是产品能力，唯一约束由谁保证，尚无答案。
- 本节没有评估口令摘要算法与令牌格式对 `target` 的要求，留给后续。

## 9. 第 3 问：带条件的状态流转的最小语义

状态：负责人 2026-10-15 授权按推荐方案推进：守卫挂在 `update` 上；最小范围只允许不带 `version` 的实体；算术作为独立一问评估（第 12 节）。不冻结语法，不授权实现；下面的写法是示意。依据是现有实现的逐段阅读（`WorkflowRenderer.renderLoad／renderPersist`、`MapperRenderer`、`SpringBootModelLowerer.locksRow／lowerConditionalUpdate`、`ValidatePass` 的 `SIR-VALID-004`），没有运行代码。

### 9.1 现有机制恰好是它的一个特例

带 `version` 的实体今天的流程：`load` 时 `SELECT … FOR UPDATE`；与请求带来的期望版本比对；`UPDATE … SET <实体的全部变更列>, version = version + 1 WHERE id = ? AND version = ?`；影响行数不是 1 就抛 `persist … else` 声明的错误。

换个角度看，这就是“**仅当存储中的当前状态满足条件才写入，否则报声明的错误**”，条件固定成了“版本等于客户端给的值”。`SIR-VALID-004` 要求版本实体的更新由 patch 驱动，正是因为期望版本只能来自客户端。要让服务端自己决定流转，不是新增一类机制，而是把这个条件**从“版本相等”放宽为“对存储状态的一个布尔条件”**。

### 9.2 建议的最小语义

示意（守卫挂在 `update` 步骤上，因为 `update` 决定“改什么”，守卫决定“从什么状态改”，并且守卫里的字段读的是更新前的值，不会和更新后的候选值混淆）：

```
load Credential by input.token as c else Invalid;
update c when c.used == false else AlreadyUsed { used: true; }
persist c;
```

1. **形态。** `update` 步骤可带一个守卫：一个布尔表达式加一个声明的错误。守卫失败报这个错误，不写入。
2. **守卫能引用什么。** 目标实体自身的字段（读存储中的当前值，更新前）、`input`、常量、`now()`。不引用其他实体，不用 `any`。这和现有 `find … where` 谓词能翻译成 SQL 的范围一致，可以复用那套翻译（谓词渲染在 `WorkflowRenderer.renderPredicateNode`）。
3. **写入语义。** 一条 `UPDATE … SET <只含被绑定的列> WHERE id = ? AND <守卫>`；影响行数不是 1 就抛声明的错误。注意与版本路径的区别：`MapperRenderer` 里版本路径的 `SET` 列表是实体的全部变更列，注释明说这样做之所以安全，是因为版本把整行钉住了；守卫路径没有版本钉住整行，**`SET` 只能写被绑定的列**，否则会用过期副本盖掉别人刚改的其他列。
4. **绑定表达式不得读目标自身的字段。** 绑定值在 Java 里按加载时的副本算出，守卫只钉住它判断的那些字段；绑定若读了别的字段，就会读到过期值再写回（丢失更新）。可以读 `input`、常量、`now()`。这条限制会挡住计数器类写法，见 9.4。
5. **与 `version`。** 版本路径不变。最小范围：守卫只用于不带 `version` 的实体，同一个 `update` 不同时使用版本令牌与守卫。带版本的实体能否也用守卫（并在同一条语句里递增版本），列为开放问题。
6. **与 `atomic`。** 两者正交：守卫保证一行的“检查并写入”不可分；`atomic` 保证多步全有或全无。轮换需要两者同时用：守卫失败抛错，同一事务里的“创建新凭据”随之回滚，不会出现旧凭据没作废而新凭据已签发。
7. **失败怎样报告。** 必须声明 `else` 错误，状态码沿用现有的 400／404／409（401／403 是另一个缺口，见 7.2）。与 `persist … else` 的现有规则一致。

### 9.3 能覆盖什么

| 业务 | 是否覆盖 | 说明 |
| --- | --- | --- |
| 一次性凭据、刷新令牌轮换与重放检测 | 是 | 守卫 `used == false`，标记已使用；并发的第二个请求影响行数为 0，被拒 |
| 状态机流转（取消、重新激活、审批） | 是 | 守卫 `status == ACTIVE`，把状态改为 `CANCELLED` |
| 邮件验证、邀请码核销 | 是 | 同上 |
| 名额、库存、计数器 | 否 | 需要 `remaining - 1` 这样的算术，且要在语句里读存储值；与第 7 节的“没有算术”是同一个缺口，应作为一族（时间运算与数值运算）统一评估，不在本问里解决 |
| 幂等键 | 否 | 靠“唯一约束 + 重复键报告”，是另一种机制，与守卫无关 |
| 跨实体条件 | 否 | 最小语义不引用其他实体 |

### 9.4 按三条规则打分

- **靠组合已有能力：** 是。复用谓词到 SQL 的翻译、`ConditionalUpdate` 的降级结构、`fails` 与声明错误；没有新的基础组件。
- **普通需求是否绕口：** 否。“这个凭据只能用一次”是一个子句。
- **修一次让一类业务受益：** 是，见 9.3。

### 9.5 改动面（估计，实现评审时再核实）

沿用 7.3 的方法粗估，守卫要触及：`Sir.g4`（`updateStep` 增加可选子句）、AST 与 `SirAstBuilder`、规范化模型与 `SoftwareSchema` 里该步骤的槽位、`TypePass`（守卫须为 Boolean，且读更新前的值）、`ValidatePass`（第 5、4 条限制）、`SirDeclarationWriter`、降级里的 `ConditionalUpdate` 变体、`SpringBootIrValidation`、`WorkflowRenderer`、`MapperRenderer`（按能力生成只含绑定列的 `UPDATE`，而不是现在按实体生成一条）。大致是五个模块、十来处；指令层是否需要改，取决于槽位是否由 schema 通用描述，未核实。

### 9.6 验收要求（将来实现时）

不接受“生成并构建通过”作为证据。需要真实 MySQL 上的并发测试：两个请求同时使用同一个一次性凭据，恰有一个成功、另一个得到声明的错误；轮换场景里失败一方不留下新凭据。这与现有写入切片 IT 的做法一致，由 CI 承担。

### 9.7 与设计 02 的关系，以及开放问题

设计 02 第 9 节已经把“流程是有限状态机：每个动作声明来源状态、目标状态和授权”写成目标设计，并且点名“不能从普通 PATCH 修改流程状态”。守卫是它的下层原语：将来的状态机声明（来源状态、目标状态）可以定义为守卫的展开，与第 8.3 节“先组合、后升格”同构。该层不在本阶段范围内。

开放问题：

- 带 `version` 的实体能否使用守卫，并在同一条语句里递增版本（建议后续再评估，最小范围不含）。
- 守卫失败与“记录不存在”不需要区分：`load … else` 已经单独覆盖了不存在。
- 算术见第 12 节；第 9.2 第 4 条的限制在算术可译成 SQL 之后可以放宽（见 12.4）。

## 10. 第 4 问：登记的类型化端口

状态：按负责人 2026-10-15 对第 1 节第 4 点的确认展开。不冻结语法，不授权实现；引入任何新构件仍需 MAIN 第 1.1 节所说的负责人明确授权，那是实现阶段的事。

### 10.1 先例已经在产品里

端口不是新概念。生成工程里的 `ActorIdentityAdapter` 就是一个：生成器产出接口和调用点，实现由部署方以约定名字的 bean 提供，启动时检查“恰好一个这样的 bean”（`KCG-ACTOR-STARTUP-003`），缺失就拒绝启动。端口设计是把这个模式从“认证专用”推广成“SIR 能声明任意一个”，而不是引入嵌入源码。

### 10.2 实现放哪里：核实结果

负责人关心的矛盾是“生成工程不允许手改”与“手写实现要进工程”。核实：

- 版本规划 `WorkspacePlanning.plan` 只对编译结果里出现的路径逐个比对磁盘（`FileDelta.compare` 产生的条目），磁盘上多出的、编译结果里没有的文件不会被观察，因此不会触发 `SIR-APP-WORKSPACE-DRIFT-001`。这是读 `plan` 方法得出的现有行为，没有用样例工程实测，也不是合同：把手写文件放进生成目录只是碰巧没被拒绝，一旦工具链将来生成同一路径，就会被判为漂移。
- 版本应用的 Git 快照只含涉及的 SIR 与生成文件，手写文件不在其中，历史保存要靠使用者自己的 Git。

结论：**实现放在生成工程之外**，作为部署方提供的 bean（独立模块或独立 jar），和现在外置的 `ActorIdentityAdapter` 完全一致。生成器只负责接口、调用点和启动检查。这与 ADR-027“生成物不手改”及 MAIN 规则 10“不嵌入源码”都不冲突，因为 SIR 里没有任何实现文本。

### 10.3 契约：声明什么、生成什么

| 项 | 内容 |
| --- | --- |
| SIR 里声明 | 端口名、输入类型、输出类型、可能的失败（沿用 `fails` 的已声明错误）、是否有副作用（只读还是会改外部状态） |
| 工作流里怎么用 | 一个调用步骤：带输入、绑定输出；失败按声明的错误报告。步骤集合因此增加一种，仍是封闭集合，没有任意调用 |
| 生成 | 接口与输入输出类型、调用点、启动检查（缺失或不止一个就拒绝启动，沿用 `KCG-ACTOR-STARTUP-003` 的写法）、失败映射 |
| 事务 | 端口抛出声明的失败，按声明的错误返回，`atomic` 内的数据库写入随之回滚；端口自己对外部世界的副作用不在回滚之内，有副作用的端口放进 `atomic` 要在声明里标出 |

### 10.4 验证与报告：端口后面的东西 SIR 看不见

- 编译结果和报告必须列出“含外部实现的端口”，每个端口一行。验证报告的每一级（静态、构建、启动、业务）都标注是否依赖端口，依赖时记录所用实现的身份（版本或摘要）。
- 启动检查意味着没有实现就无法启动，所以**验证必须自带端口的测试实现**（题目测试包的一部分），它只证明 SIR 一侧的接线正确，不证明真实实现正确。报告里写“业务门在测试实现下通过”，不写成端口本身已验证。
- 端口真实实现的正确性由提供它的人负责，不在本工具链的验收范围内。

### 10.5 使用顺序：端口是最后手段

判断顺序：能用语义表达的（第 9 节的守卫、第 12 节的算术）写进语言；纯机制选择（令牌格式、散列算法）归 Profile；两者都放不下，才声明端口。理由：端口越多，SIR 能证明的东西越少。因此每个端口声明应附一句话说明“为什么语义和 Profile 都放不下”，供评审时核对，不满足的退回去补语义。

### 10.6 范围外与开放问题

- 范围外：端口实现的分发与版本管理、端口的权限与沙箱、跨项目共享端口。
- 开放：有副作用的端口在 `readonly` 能力里是否一律禁止（倾向禁止）；端口输入输出可用的类型范围（倾向只用 SIR 已有类型，不引用实体行本身）。

## 11. 第 6 问：移除记录

建议：**最小范围不新增“移除记录”步骤。**

- 设计 02 第 6 节已经写明：删除必须显式声明，默认外键 RESTRICT，不隐式级联；取消保留记录，再次报名用重新激活；归档是可观察的状态变化。这些用例用第 9 节的守卫加状态字段就能表达，不需要物理删除。
- 物理删除牵连数据保留、外键、已有数据不丢（设计 04 的数据库演进与“潜在丢数据”风险），而数据库初始化与迁移还不是产品能力，在它之前加删除语义，等于先开了最危险的口子。
- 当出现“不能用状态表达”的真实业务时再加。届时的最小形态：显式声明、默认 RESTRICT、被引用时返回 409（沿用现有 409 白名单）；HTTP 方法仍由降级阶段选择，不由 SIR 作者写（第 1 节第 1 点）。
- 与第 3 问的关系：软删除（置已作废、已取消）正是守卫更新，两者合起来覆盖设计 02 的状态流转用例。

## 12. 算术一族（第 7 问，探针中新增）

起因：第 7 节实测，`now() + 900` 在词法层被拒，表达式没有任何算术；设计 02 第 9 节早就写了“有限表达式用于比较、逻辑组合和边界算术”，现状只实现了前两项。它同时卡住 15 分钟有效期、7 天有效期、名额与库存，所以按“一族”评估，而不是按用例补丁。

### 12.1 最小范围

1. **时长字面量与时间运算。** 时长字面量（单位：秒、分钟、小时、天）；`DateTime ± 时长 → DateTime`，`Date ± 天数 → Date`。这就够写“签发时间加 15 分钟”。时长是表达式里的类型，不能作为实体字段存储。
2. **数值加减。** `Int32`、`Int64`、`Decimal` 内部的加减，两边类型相同；溢出视为错误，不静默回绕（“边界算术”的含义）。不含除法与取余。
3. **使用范围。** 工作流表达式（绑定值、`validate`）。`find … where` 里的算术要翻译成 SQL，放到后续。

### 12.2 按三条规则打分

靠组合已有能力：否，是新的表达式类别；普通需求是否绕口：是（“15 分钟”写不出来）；一类业务受益：是（会话、优惠券、邀请码、预约锁定、任何带有效期的凭据）。

### 12.3 改动面（估计，实现评审时再核实）

表达式是封闭的集合，新增运算符大致触及：`Sir.g4`（词法的时长记号、表达式优先级层）、AST 二元表达式的运算符、`TypePass`（类型规则）、规范化表达式、降级表达式、`ExpressionRenderer`（`renderBinary` 对运算符做穷尽的 `switch`，新增运算符必须补分支）、`SirDeclarationWriter`。四个模块、七处左右。对照参考：把错误状态码集合扩展一项（401）是 `TypePass` 的集合、降级的 `HttpStatus` 枚举、降级里的 `switch` 三处、两个模块；封闭枚举扩展便宜，新增语法层级贵。

### 12.4 与第 9 节的衔接

名额类业务（设计 02 的报名用例：有剩余名额才能报名，一次原子操作占用一个名额）需要“守卫 `remaining > 0` 加语句内 `remaining = remaining - 1`”。这要求绑定表达式能读目标自身的字段并翻译进同一条 `UPDATE`。也就是说，第 9.2 第 4 条的限制只在“表达式不能译成 SQL”时成立；等 12.1 的算术具备 SQL 翻译能力后，可以放宽为“读自身字段的绑定整体下推到 `UPDATE` 语句里”。这是后续的一问，不在最小范围内。

## 14. 第 8.4 节开放问题：倾向

| 问题 | 倾向与理由 |
| --- | --- |
| 展开出来的节点（刷新、登出）怎样登记身份 | 展开节点不写进 SIR 文本，不是作者的声明。它的身份由修饰声明的 `declarationId` 加固定的角色名确定性派生（不用时间或随机数，设计 02 第 2 节的要求）；规范化模型中标注“来源：某修饰的展开”。指令只能作用于修饰声明，不能单独编辑展开节点，否则会出现“改了展开结果却没改源”。设计 02 第 2 节的稳定身份规则是否够用，仍需实现评审时对照 |
| 连接声明（凭据如何识别 `actor`）放哪里 | 放在凭据实体的角色绑定里，一处声明；每个 `requires authenticated` 的能力保持原样。理由：连接是整个软件一份，不是每个能力一份 |
| 角色绑定写法 | 逐字段显式指定，不用字段名约定。与现有“类型化引用位置绑定”的风格一致，改字段名不会悄悄改变语义 |
| “按键取唯一一条”的最小语义 | 扩展 `load`，允许按声明为唯一的字段加载，保持 `load … else 错误` 的形态（找不到就是已声明的错误），因此不需要“判断是否为空”。这要求先有字段上的 `unique` 声明（语言里目前没有任何唯一约束）。数据库初始化还不是产品能力，所以最小实现是生成时按 `LIMIT 2` 查询，多于一条按内部错误处理；将来有初始化能力时再把 `unique` 落成唯一索引 |
| 401 与 403 | 401：把声明错误的状态码集合扩展到 401（改动小，见 12.3 的参照），登录失败返回 401 是通行做法，并且生成的认证拦截器本来就返回 401，只是无法在 SIR 里声明。403：等授权语义（角色与数据范围，设计 02 第 10 节）出现再加，现在没有地方产生它 |
| 口令只存摘要 | 字段上的修饰（暂称 `secret`）：声明该字段存摘要，比较用专门的运算而不是 `==`，摘要算法归 Profile。排在“按键取唯一一条”之后 |

### 15.2 探针的总读数

双 Token 的七条行为里，现有语言能组合出的只有凭据值与登出作废。其余缺口都是通用能力，且多数很小：把错误状态码集合扩展一项是两个模块三处；新增一个修饰词是四个模块七处以上；新增表达式运算符与守卫都是四到五个模块、七到十来处。指令层在这些改动里都不是改动对象。这支持 ADR-026 的一半，另一半是语法层没有登记新构件的缝，每个新词都是语法改动。

### 15.3 建议的实现顺序（只是依赖关系，不是排期，每一步需要负责人授权）
