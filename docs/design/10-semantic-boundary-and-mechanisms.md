# 机制与语义的边界：以双 Token 认证为起点

- 日期：2026-10-15。
- 状态：**DRAFT**。记录负责人与执行者在 2026-10-15 讨论中确认的方向，以及 S2（设计评审）要回答的问题。**目标设计，不授权实现，不代表任何能力已存在。**
- 依据：[MAIN](../../MAIN.md) 第 1.1 节与规则 9、10，[ADR-026](../architecture/ADR-026-layered-semantic-command-architecture.md)，[ADR-027](../architecture/ADR-027-git-as-version-history.md)，[设计 02](02-sir-language-and-modules.md) 第 9–10 节，[设计 03](03-compiler-and-generated-backend.md) 第 10 节。
- 起因：公开 CLI 阶段验收后，规划下一阶段时提出“双 Token 认证能否在软件语义层表示”，它关系到 SIR 的基础概念：软件语义是否被基础组件绑死。

## 1. 已确认的方向

1. **SIR 描述软件语义，不增加基础组件的词汇。** 例如 HTTP 方法不是 SIR 作者写的，由降级阶段按能力种类和输入形状选择（`SpringBootModelLowerer.lowerHttpMethod`：查询为 GET，局部更新输入为 PATCH，其余为 POST）。“没有 DELETE”是当前 Profile 的映射，不是语言缺口；真正的问题是语言有没有“移除一条记录”的语义。
2. **分层判断。** 一个细节放语义还是放 Profile，问一句：换掉这个选择，符合契约的客户端或验收测试会不会察觉？不会，是机制，留给 Profile（JWT 还是不透明串、签名算法、Header 还是 Cookie、MySQL 还是 Redis）。会，比如“令牌必须是 JWT，因为别的服务要验”，它是目标约束，写在 `target` 里，降级时检查 Profile 是否支持，不支持就诊断，不悄悄满足。
3. **双 Token 的方向是更高层的修饰。** 登录是语义（用凭据确立身份），双 Token 是对“身份如何跨请求延续”的修饰（访问令牌有效期、刷新令牌有效期、是否轮换）。这与语言现有的写法一致：`requires atomic / readonly / authenticated` 本来就是挂在能力上的修饰，由降级决定实现。这是方向，不是冻结的语法。
4. **要建语义系统，不靠源码补洞。** 目前搭不出来的东西，多数是“还没实现”，不是原理上做不到。语义不完整的部分，补充路径是**登记的、类型化的端口**：SIR 声明端口的签名和契约，生成器产出接口，实现放在工程之外。这不是“嵌入任意源码”，所以不违反 MAIN 规则 10；MAIN 第 1.1 节本来就写了“扩展按登记的契约和负责人的明确授权执行”。负责人已确认把它作为 S2 的设计内容，实现另行授权。

## 2. 现状（已逐项核对代码）

- `requires atomic`：生成的服务类加 `@Transactional`（`ServiceRenderer`），整条工作流在一个数据库事务内。不加锁，不防两个事务同时读到同一行。
- 条件写入 `persist … else`：只用于带 `version` 字段的实体。校验 SIR-VALID-004 规定，带版本实体的 `update` 必须由该实体的 patch 输入驱动，`else` 只报告“行的版本与读到时不一致”。因此**服务端自己决定的状态流转今天写不出来**：带版本的要客户端 PATCH 驱动，不带版本的没有并发保护。
- 工作流步骤只有 `validate / load / find / create / update / persist / return`，没有移除记录的步骤。
- 认证：`requires authenticated` 加 `actor Ref<实体>`，生成工程里是 `ActorIdentityAdapter` 接口（`external` 模式要求部署方提供约定名字的 bean），另有 `local-fixed` 本地固定身份模式。没有登录、会话、令牌、角色。设计 02/03 描述的“标准身份能力”（登录、退出、当前身份、CSRF，首轮内存会话）尚未实现。
- 表达式里有 `now()`；没有散列、随机串、签名。`uuid` 只是实体主键的生成策略。
- 没有源码块（语法里没有 java、sql、native 一类构造）；生成工程不允许手改（ADR-027）；代码里没有“扩展登记”机制，它只出现在设计 02。
- 数据库初始化与迁移还不是产品能力，生成工程的表结构在测试里由夹具建立。
- 手写的 `ActorIdentityAdapter` bean 怎样交付：已核实，见第 10.2 节。

## 4. S2 要回答的问题（只设计，不实现）

1. **刷新凭据存在哪里。** 作者显式声明一个实体并由修饰引用它，还是无状态令牌（做不了作废和轮换，语义更弱）。数据库初始化不是产品能力，所以修饰不能暗含一张隐藏的表。答案草稿见第 8.1 节。
2. **“基本语义”采用哪种形态。**（答案草稿见第 8.2–8.3 节。） 用同一份双 Token 拆解，对照两种做法各写出作者要写的内容和各自新增的东西：修饰形式（登录加延续策略），与纯 SIR 组合（作者自己声明凭据实体与流程）。**切换条件**：如果“账号密码登录，访问令牌 15 分钟，刷新令牌 7 天并轮换”这样一句普通需求，用组合写出来仍然绕口，就把稳定下来的组合升级为内建修饰。
3. **“带条件的状态流转”的最小语义。** 条件的形式、冲突如何报告、与 `version`、`atomic` 的关系。答案草稿见第 9 节。
4. **登记端口的契约。** 声明什么（签名、契约、失败语义），生成什么，验证怎样兜底（端口后面的逻辑 SIR 看不见，只能靠业务判题器），报告里怎样标出“含外部实现”，以及上面“未核实”的交付问题。
5. **小规模模型实验的接入。** 需要第一道实验题、实验手册、外部“题目测试包”的格式，以及判题器与隔离数据库的生产版实现；业务判题器和数据库沙箱目前只存在于测试代码中，CLI 没有对应命令。
6. **移除记录的语义**与状态流转的取舍。

负责人 2026-10-15 的定位：双 Token 是对系统扩展性的测试，不是一次能力提升。本节只记录读数，不冻结语法，不授权实现。

### 7.1 被测样本（负责人已确认）

需求句子：账号密码登录，访问令牌 15 分钟，刷新令牌 7 天并轮换，登出后作废。

客户端可观察的七条行为：①登录成功得到一对令牌；②有效访问令牌可调用受保护接口；③过期访问令牌被拒；④有效刷新令牌换得新的一对，旧刷新令牌随即失效；⑤重放旧刷新令牌被拒；⑥登出后刷新令牌失效；⑦错误密码被拒，且不泄露账号是否存在。

判据来自第 1 节第 2 点：换掉这个选择，符合契约的客户端会不会察觉。下表的“结果”是编译器的真实回应；诊断码取自 `check` 输出。

| 行为 | 样本与结果 | 缺口 | 归类 |
| --- | --- | --- | --- |

### 7.3 读数：补一个修饰要碰多少处

用已有的三个 `requires` 词作参照（只数引用位置，来自代码检索）：

- `Sir.g4` 把 `authenticated | atomic | readonly` 写死在 `requirement` 规则里，词法里每个词各占一个记号。新增任何修饰都要改语法。
- `AstRequirementKind` 枚举；`SirAstBuilder.requirement()` 里只有 authenticated 的判断，其余用 `ATOMIC() != null ? ATOMIC : READONLY` 兜底，第四种词必须改这段写法。
- `ValidatePass` 有 `SIR-VALID-001`“requires 必须按 authenticated, atomic, readonly 顺序”，顺序列表在 `SirDeclarationWriter.REQUIREMENT_ORDER` 里再写一遍。
- 降级在 `SpringBootModelLowerer` 约第 507 行把词映射为 `authenticated` 与 `TransactionMode`；生成器消费降级后的标志。
- `NormalizedCapability.requires` 是通用的 `@Fact @Keyed` 列表；`sir-change` 的指令层没有任何引用。

读数：新增一个修饰词，改动落在 parser、semantic、lowering、generator 四个模块、至少七处，指令层（Change／Command）不需要改。这支持 ADR-026 的一半：新增语义不必重复修改指令；但也说明，**语法层没有“登记新修饰”的缝，每个修饰都是一次语法改动**。另外 `target { … }` 的六个字段同样写死在语法里，没有位置声明“令牌必须是某种格式”这类目标约束，第 1 节第 2 点说的约束要先有这个位置。错误状态码白名单（400/404/409）是同一类刚性：它写在校验里，不是可登记的表。

### 7.5 暂定结论与待办

- 双 Token 本身不是一个孤立的大功能：七条行为里有两条（凭据值、登出作废）现有 SIR 已能组合写出；其余缺口分属几类通用能力（时间运算、带条件的状态流转、按键取唯一一条、延续策略、状态码），每一类都不只服务于双 Token。
- 实测多出的两个缺口（按键取唯一一条、401／403）比读代码时预想的更基础：它们不属于“认证”，是任何业务都会碰到的。这说明探针量到的是语言的通用能力边界，不是双 Token 的特殊要求。
- 这支持“推荐搭语义系统”的方向；读数也暴露了语法层的刚性（7.3），后续任何语义补充都要先回答“新词往哪里登记”。
- 第 4 节第 1、2 问（刷新凭据存哪里，修饰形式与组合形式的对照）可以据此写：组合形式下刷新凭据只能是作者声明的实体（无状态分支已排除）；对照时要把上表的缺口逐项列入两种形式各自“新增什么”。
- 局限：样本只到 GENERATION，没有构建或运行；`now()` 渲染只看了一个样本的生成代码；没有测并发。这些结论是语言能力边界的读数，不是行为验证。

## 8. 第 4 节第 1、2 问的答案

状态：负责人 2026-10-15 确认按本节推荐的方向（8.1 的实体存放、8.3 的“先组合、后升格、修饰定义为展开”）；8.4 的开放问题仍待回答。本节不冻结语法，不授权实现。下面出现的写法都是示意，用来比较“作者要写什么”，不是语法提案。依据是第 7 节的实测读数。

### 8.1 第 1 问：刷新凭据存在哪里

| 选项 | 结论 | 理由 |
| --- | --- | --- |
| 无状态令牌（不落库） | 排除 | 表达式没有签名；即使 Profile 能签，也做不了作废和轮换（7.2） |
| 修饰暗含一张隐藏的表 | 排除 | 数据库初始化与迁移不是产品能力（第 2 节）；作者在 SIR 里看不到这张表，它的结构变化无处追溯，也违背“SIR 是唯一的源” |
| **作者声明一个普通实体，修饰引用它** | **建议** | 它和其他实体走同一条路径（表结构、版本变更、生成），不新增一类隐藏产物；7.2 已证明这样的实体现在就能声明和读写 |

建议的含义：

- 凭据实体是普通实体。修饰（或后述的展开）只规定它必须**扮演哪些角色**：属主（引用账号）、失效时刻、已作废标志，轮换时还要“已使用”标志。哪些字段扮演哪个角色由作者显式指定，Validate 检查类型，不靠字段名约定，与现有“类型化引用位置绑定”的风格一致。
- 访问令牌的形态是 Profile 的机制选择：落库的不透明串，或签名串。客户端察觉不到差别，按第 1 节判据留给 Profile；若 Profile 不支持作者要求的形态，降级阶段给诊断，不悄悄替换。刷新凭据则必须落库，因为作废和轮换需要状态。
- 这条结论不依赖尚未解决的数据库初始化问题：该问题对所有实体一视同仁，本方案没有让它变糟。

### 8.2 第 2 问：两种形态逐项对照

被测需求同第 7.1 节。下面“作者要写”的数量是示意，用来比较体量，不是精确行数。

**形态 C：纯 SIR 组合。** 作者声明账号实体和凭据实体，自己写三个能力：登录（按账号名取账号、校验口令、创建带失效时刻的凭据）、刷新（取旧凭据、条件流转为已使用、创建新凭据）、登出（作废）。再加一处声明，告诉 `requires authenticated` 访问凭据如何识别出 `actor`。作者要写的：两个实体、三个能力（各约六到十步）、一处连接声明。

**形态 M：修饰。** 登录是语义，双 Token 是挂在登录上的“延续策略”，示意：

```
login Account by name, password        // 语义：用凭据确立身份
  continuity { access 15 minutes; refresh 7 days, rotating; store Credential }
```

作者要写的：两个实体、一处登录声明、一处延续策略，受保护能力照旧写 `requires authenticated`。刷新与登出由谁提供是个问题：隐式生成的能力不在作者的 SIR 里（见 8.4）。

| 项 | 形态 C：纯组合 | 形态 M：修饰（按私有实现） |
| --- | --- | --- |
| 作者要写的体量 | 大，普通需求仍绕口 | 小，接近需求原话 |
| 需要新增的通用语义 | 按键取唯一一条、时间运算、带条件的状态流转、401／403，各自都被别的业务复用 | 同样的东西被修饰的降级私下实现，**通用缺口留在原地**，别的业务得不到 |
| 认证专属的新增 | 凭据与认证的连接声明 | 登录声明、延续策略、隐式能力 |
| 三条规则：靠组合已有能力 | 是（缺口补上之后） | 否，是一个新的整体 |
| 三条规则：普通需求是否绕口 | 是 | 否 |
| 三条规则：修一次让一类业务受益 | 是 | 否，只有登录类业务 |

### 8.3 建议：先组合，再升格；修饰定义为组合的展开

两种形态不是二选一：

1. **先补通用语义，用组合把双 Token 写出来。** 这一步同时是探针的验收：写出来了，才说明语言真的够用。
2. **再把稳定下来的组合升格为内建修饰，修饰的含义定义为“编译期展开成上面那段组合”**，而不是一段私有的降级代码。这就是第 4 节第 2 问约定的切换条件：普通需求句子用组合写仍然绕口，就升格。展开保证三件事：通用缺口必须被真正补上；展开后的节点能在规范化模型里看见和解释；修饰只是糖，不是新的基础组件。

这与负责人最初的两个方向一致：“做成软件基本语义”和“通过现有 SIR 做固定搭配”是同一件事的先后两步。

依赖顺序（只列依赖，不排期）：按键取唯一一条 → 时间运算（失效时刻）→ 带条件的状态流转（轮换）→ 401／403 → 口令只存摘要 → 凭据与认证的连接 → 修饰糖。

### 8.4 本节仍然开放的问题

- 展开出来的节点（刷新、登出能力）没有源文本，它们的稳定身份与来源怎样登记，指令层怎样引用，需要先回答。设计 02 的稳定身份规则是否够用，未核对。
- 连接声明（凭据如何识别 `actor`）放在哪里：能力上、实体上，还是延续策略里。
- 角色绑定的写法：逐字段显式指定，还是整体声明“这个实体是凭据”。
- “按键取唯一一条”的最小语义：不存在时的错误怎样声明，键是否要求唯一约束；数据库初始化不是产品能力，唯一约束由谁保证，尚无答案。
- 本节没有评估口令摘要算法与令牌格式对 `target` 的要求，留给后续。

## 9. 第 3 问：带条件的状态流转的最小语义

状态：负责人 2026-10-15 授权按推荐方案推进：守卫挂在 `update` 上；最小范围只允许不带 `version` 的实体；算术作为独立一问评估（第 12 节）。不冻结语法，不授权实现；下面的写法是示意。依据是现有实现的逐段阅读（`WorkflowRenderer.renderLoad／renderPersist`、`MapperRenderer`、`SpringBootModelLowerer.locksRow／lowerConditionalUpdate`、`ValidatePass` 的 `SIR-VALID-004`），没有运行代码。

### 9.1 现有机制恰好是它的一个特例

带 `version` 的实体今天的流程：`load` 时 `SELECT … FOR UPDATE`；与请求带来的期望版本比对；`UPDATE … SET <实体的全部变更列>, version = version + 1 WHERE id = ? AND version = ?`；影响行数不是 1 就抛 `persist … else` 声明的错误。

换个角度看，这就是“**仅当存储中的当前状态满足条件才写入，否则报声明的错误**”，条件固定成了“版本等于客户端给的值”。`SIR-VALID-004` 要求版本实体的更新由 patch 驱动，正是因为期望版本只能来自客户端。要让服务端自己决定流转，不是新增一类机制，而是把这个条件**从“版本相等”放宽为“对存储状态的一个布尔条件”**。

### 9.2 建议的最小语义

示意（守卫挂在 `update` 步骤上，因为 `update` 决定“改什么”，守卫决定“从什么状态改”，并且守卫里的字段读的是更新前的值，不会和更新后的候选值混淆）：

```
load Credential by input.token as c else Invalid;
update c when c.used == false else AlreadyUsed { used: true; }
persist c;
```

1. **形态。** `update` 步骤可带一个守卫：一个布尔表达式加一个声明的错误。守卫失败报这个错误，不写入。
2. **守卫能引用什么。** 目标实体自身的字段（读存储中的当前值，更新前）、`input`、常量、`now()`。不引用其他实体，不用 `any`。这和现有 `find … where` 谓词能翻译成 SQL 的范围一致，可以复用那套翻译（谓词渲染在 `WorkflowRenderer.renderPredicateNode`）。
3. **写入语义。** 一条 `UPDATE … SET <只含被绑定的列> WHERE id = ? AND <守卫>`；影响行数不是 1 就抛声明的错误。注意与版本路径的区别：`MapperRenderer` 里版本路径的 `SET` 列表是实体的全部变更列，注释明说这样做之所以安全，是因为版本把整行钉住了；守卫路径没有版本钉住整行，**`SET` 只能写被绑定的列**，否则会用过期副本盖掉别人刚改的其他列。
4. **绑定表达式不得读目标自身的字段。** 绑定值在 Java 里按加载时的副本算出，守卫只钉住它判断的那些字段；绑定若读了别的字段，就会读到过期值再写回（丢失更新）。可以读 `input`、常量、`now()`。这条限制会挡住计数器类写法，见 9.4。
5. **与 `version`。** 版本路径不变。最小范围：守卫只用于不带 `version` 的实体，同一个 `update` 不同时使用版本令牌与守卫。带版本的实体能否也用守卫（并在同一条语句里递增版本），列为开放问题。
6. **与 `atomic`。** 两者正交：守卫保证一行的“检查并写入”不可分；`atomic` 保证多步全有或全无。轮换需要两者同时用：守卫失败抛错，同一事务里的“创建新凭据”随之回滚，不会出现旧凭据没作废而新凭据已签发。
7. **失败怎样报告。** 必须声明 `else` 错误，状态码沿用现有的 400／404／409（401／403 是另一个缺口，见 7.2）。与 `persist … else` 的现有规则一致。

### 9.3 能覆盖什么

| 业务 | 是否覆盖 | 说明 |
| --- | --- | --- |
| 一次性凭据、刷新令牌轮换与重放检测 | 是 | 守卫 `used == false`，标记已使用；并发的第二个请求影响行数为 0，被拒 |
| 状态机流转（取消、重新激活、审批） | 是 | 守卫 `status == ACTIVE`，把状态改为 `CANCELLED` |
| 邮件验证、邀请码核销 | 是 | 同上 |
| 名额、库存、计数器 | 否 | 需要 `remaining - 1` 这样的算术，且要在语句里读存储值；与第 7 节的“没有算术”是同一个缺口，应作为一族（时间运算与数值运算）统一评估，不在本问里解决 |
| 幂等键 | 否 | 靠“唯一约束 + 重复键报告”，是另一种机制，与守卫无关 |
| 跨实体条件 | 否 | 最小语义不引用其他实体 |

### 9.4 按三条规则打分

- **靠组合已有能力：** 是。复用谓词到 SQL 的翻译、`ConditionalUpdate` 的降级结构、`fails` 与声明错误；没有新的基础组件。
- **普通需求是否绕口：** 否。“这个凭据只能用一次”是一个子句。
- **修一次让一类业务受益：** 是，见 9.3。

### 9.5 改动面（估计，实现评审时再核实）

沿用 7.3 的方法粗估，守卫要触及：`Sir.g4`（`updateStep` 增加可选子句）、AST 与 `SirAstBuilder`、规范化模型与 `SoftwareSchema` 里该步骤的槽位、`TypePass`（守卫须为 Boolean，且读更新前的值）、`ValidatePass`（第 5、4 条限制）、`SirDeclarationWriter`、降级里的 `ConditionalUpdate` 变体、`SpringBootIrValidation`、`WorkflowRenderer`、`MapperRenderer`（按能力生成只含绑定列的 `UPDATE`，而不是现在按实体生成一条）。大致是五个模块、十来处；指令层是否需要改，取决于槽位是否由 schema 通用描述，未核实。

### 9.6 验收要求（将来实现时）

不接受“生成并构建通过”作为证据。需要真实 MySQL 上的并发测试：两个请求同时使用同一个一次性凭据，恰有一个成功、另一个得到声明的错误；轮换场景里失败一方不留下新凭据。这与现有写入切片 IT 的做法一致，由 CI 承担。

### 9.7 与设计 02 的关系，以及开放问题

设计 02 第 9 节已经把“流程是有限状态机：每个动作声明来源状态、目标状态和授权”写成目标设计，并且点名“不能从普通 PATCH 修改流程状态”。守卫是它的下层原语：将来的状态机声明（来源状态、目标状态）可以定义为守卫的展开，与第 8.3 节“先组合、后升格”同构。该层不在本阶段范围内。

开放问题：

- 带 `version` 的实体能否使用守卫，并在同一条语句里递增版本（建议后续再评估，最小范围不含）。
- 守卫失败与“记录不存在”不需要区分：`load … else` 已经单独覆盖了不存在。
- 算术见第 12 节；第 9.2 第 4 条的限制在算术可译成 SQL 之后可以放宽（见 12.4）。

## 10. 第 4 问：登记的类型化端口

状态：按负责人 2026-10-15 对第 1 节第 4 点的确认展开。不冻结语法，不授权实现；引入任何新构件仍需 MAIN 第 1.1 节所说的负责人明确授权，那是实现阶段的事。

### 10.1 先例已经在产品里

端口不是新概念。生成工程里的 `ActorIdentityAdapter` 就是一个：生成器产出接口和调用点，实现由部署方以约定名字的 bean 提供，启动时检查“恰好一个这样的 bean”（`KCG-ACTOR-STARTUP-003`），缺失就拒绝启动。端口设计是把这个模式从“认证专用”推广成“SIR 能声明任意一个”，而不是引入嵌入源码。

### 10.2 实现放哪里：核实结果

负责人关心的矛盾是“生成工程不允许手改”与“手写实现要进工程”。核实：

- 版本规划 `WorkspacePlanning.plan` 只对编译结果里出现的路径逐个比对磁盘（`FileDelta.compare` 产生的条目），磁盘上多出的、编译结果里没有的文件不会被观察，因此不会触发 `SIR-APP-WORKSPACE-DRIFT-001`。这是读 `plan` 方法得出的现有行为，没有用样例工程实测，也不是合同：把手写文件放进生成目录只是碰巧没被拒绝，一旦工具链将来生成同一路径，就会被判为漂移。
- 版本应用的 Git 快照只含涉及的 SIR 与生成文件，手写文件不在其中，历史保存要靠使用者自己的 Git。

结论：**实现放在生成工程之外**，作为部署方提供的 bean（独立模块或独立 jar），和现在外置的 `ActorIdentityAdapter` 完全一致。生成器只负责接口、调用点和启动检查。这与 ADR-027“生成物不手改”及 MAIN 规则 10“不嵌入源码”都不冲突，因为 SIR 里没有任何实现文本。

### 10.3 契约：声明什么、生成什么

| 项 | 内容 |
| --- | --- |
| SIR 里声明 | 端口名、输入类型、输出类型、可能的失败（沿用 `fails` 的已声明错误）、是否有副作用（只读还是会改外部状态） |
| 工作流里怎么用 | 一个调用步骤：带输入、绑定输出；失败按声明的错误报告。步骤集合因此增加一种，仍是封闭集合，没有任意调用 |
| 生成 | 接口与输入输出类型、调用点、启动检查（缺失或不止一个就拒绝启动，沿用 `KCG-ACTOR-STARTUP-003` 的写法）、失败映射 |
| 事务 | 端口抛出声明的失败，按声明的错误返回，`atomic` 内的数据库写入随之回滚；端口自己对外部世界的副作用不在回滚之内，有副作用的端口放进 `atomic` 要在声明里标出 |

### 10.4 验证与报告：端口后面的东西 SIR 看不见

- 编译结果和报告必须列出“含外部实现的端口”，每个端口一行。验证报告的每一级（静态、构建、启动、业务）都标注是否依赖端口，依赖时记录所用实现的身份（版本或摘要）。
- 启动检查意味着没有实现就无法启动，所以**验证必须自带端口的测试实现**（题目测试包的一部分），它只证明 SIR 一侧的接线正确，不证明真实实现正确。报告里写“业务门在测试实现下通过”，不写成端口本身已验证。
- 端口真实实现的正确性由提供它的人负责，不在本工具链的验收范围内。

### 10.5 使用顺序：端口是最后手段

判断顺序：能用语义表达的（第 9 节的守卫、第 12 节的算术）写进语言；纯机制选择（令牌格式、散列算法）归 Profile；两者都放不下，才声明端口。理由：端口越多，SIR 能证明的东西越少。因此每个端口声明应附一句话说明“为什么语义和 Profile 都放不下”，供评审时核对，不满足的退回去补语义。

### 10.6 范围外与开放问题

- 范围外：端口实现的分发与版本管理、端口的权限与沙箱、跨项目共享端口。
- 开放：有副作用的端口在 `readonly` 能力里是否一律禁止（倾向禁止）；端口输入输出可用的类型范围（倾向只用 SIR 已有类型，不引用实体行本身）。

## 11. 第 6 问：移除记录

建议：**最小范围不新增“移除记录”步骤。**

- 设计 02 第 6 节已经写明：删除必须显式声明，默认外键 RESTRICT，不隐式级联；取消保留记录，再次报名用重新激活；归档是可观察的状态变化。这些用例用第 9 节的守卫加状态字段就能表达，不需要物理删除。
- 物理删除牵连数据保留、外键、已有数据不丢（设计 04 的数据库演进与“潜在丢数据”风险），而数据库初始化与迁移还不是产品能力，在它之前加删除语义，等于先开了最危险的口子。
- 当出现“不能用状态表达”的真实业务时再加。届时的最小形态：显式声明、默认 RESTRICT、被引用时返回 409（沿用现有 409 白名单）；HTTP 方法仍由降级阶段选择，不由 SIR 作者写（第 1 节第 1 点）。
- 与第 3 问的关系：软删除（置已作废、已取消）正是守卫更新，两者合起来覆盖设计 02 的状态流转用例。

## 12. 算术一族（第 7 问，探针中新增）

起因：第 7 节实测，`now() + 900` 在词法层被拒，表达式没有任何算术；设计 02 第 9 节早就写了“有限表达式用于比较、逻辑组合和边界算术”，现状只实现了前两项。它同时卡住 15 分钟有效期、7 天有效期、名额与库存，所以按“一族”评估，而不是按用例补丁。

### 12.1 最小范围

1. **时长字面量与时间运算。** 时长字面量（单位：秒、分钟、小时、天）；`DateTime ± 时长 → DateTime`，`Date ± 天数 → Date`。这就够写“签发时间加 15 分钟”。时长是表达式里的类型，不能作为实体字段存储。
2. **数值加减。** `Int32`、`Int64`、`Decimal` 内部的加减，两边类型相同；溢出视为错误，不静默回绕（“边界算术”的含义）。不含除法与取余。
3. **使用范围。** 工作流表达式（绑定值、`validate`）。`find … where` 里的算术要翻译成 SQL，放到后续。

### 12.2 按三条规则打分

靠组合已有能力：否，是新的表达式类别；普通需求是否绕口：是（“15 分钟”写不出来）；一类业务受益：是（会话、优惠券、邀请码、预约锁定、任何带有效期的凭据）。

### 12.3 改动面（估计，实现评审时再核实）

表达式是封闭的集合，新增运算符大致触及：`Sir.g4`（词法的时长记号、表达式优先级层）、AST 二元表达式的运算符、`TypePass`（类型规则）、规范化表达式、降级表达式、`ExpressionRenderer`（`renderBinary` 对运算符做穷尽的 `switch`，新增运算符必须补分支）、`SirDeclarationWriter`。四个模块、七处左右。对照参考：把错误状态码集合扩展一项（401）是 `TypePass` 的集合、降级的 `HttpStatus` 枚举、降级里的 `switch` 三处、两个模块；封闭枚举扩展便宜，新增语法层级贵。

### 12.4 与第 9 节的衔接

名额类业务（设计 02 的报名用例：有剩余名额才能报名，一次原子操作占用一个名额）需要“守卫 `remaining > 0` 加语句内 `remaining = remaining - 1`”。这要求绑定表达式能读目标自身的字段并翻译进同一条 `UPDATE`。也就是说，第 9.2 第 4 条的限制只在“表达式不能译成 SQL”时成立；等 12.1 的算术具备 SQL 翻译能力后，可以放宽为“读自身字段的绑定整体下推到 `UPDATE` 语句里”。这是后续的一问，不在最小范围内。

## 16. 实现链第 1 步的具体方案（供评审，未授权实现）

范围只有第 15.3 节的第 1 步：字段 `unique`，以及按唯一字段 `load`。下面的语法是示意；改动面来自对现有同类功能的文件检索，数字用于评审，实现时再逐个核实。

### 16.1 要写出的东西

```
field name: String where notBlank, length(1, 64) unique;
...
load Account by name: input.name as acc else BadCredentials;
```

`load` 的 `by` 后面可以多出一个“字段名加冒号”，与现有 `create`／`update` 里“字段名冒号表达式”的写法一致，不会和现有的 `load … by 表达式` 混淆（表达式里没有冒号）。不写字段名时仍是按主键加载，旧文档逐字节不变。

### 16.2 语义规则

1. `unique` 只能用在实体字段上；不能用于主键、`version` 字段、`Optional` 字段（多个空值的唯一性在 SQL 里有歧义）。字段类型限于 `String`、`Int32`、`Int64`、`Uuid`（`Decimal` 的标度、`DateTime` 的精度会让相等比较有歧义，不纳入最小范围；`Ref` 上的唯一性是设计 02 第 143 行说的“一对一要求唯一外键”，是另一件事）。
2. 按字段 `load`：该字段必须声明了 `unique`；表达式类型必须能赋给字段类型；结果变量的类型与按主键加载相同。
3. 结果：零行，报 `else` 声明的错误；一行，得到该行；多于一行，说明数据违反了声明，按内部错误（500）处理，日志不写入键值。
4. 与 `version` 的衔接：带版本的实体做条件更新时，行锁路径要按主键读（`selectByIdForUpdate`）。因此“对带版本实体按字段加载后再更新”在最小范围内用诊断拒绝，不静默退化成没有锁的路径。

### 16.3 不做什么

- 不生成数据库唯一索引：数据库初始化不是产品能力，测试夹具的表结构自己加 `UNIQUE KEY`。生成代码用 `LIMIT 2` 查询做运行时保护，是对声明被违反时的兜底，不是唯一性的保证。
- 不处理“创建时键重复”的报告：重复键现在会变成数据库异常，对应 500。这是第 9.3 节里说的幂等键那一类，另有一问。
- 不改指令层。

### 16.4 改动面（以现有功能为样板的检索结果）

### 17.1 做了什么

- 语言：实体字段可写 `unique`（出现在类型、约束、`versioned` 之后，`@id` 之前）；`load E by 字段: 表达式 as v else 错误;` 按唯一字段加载。不写字段名时仍是按主键加载。`unique` 是上下文关键字，叫 `unique` 的字段名、标识符照常可用（有测试）。
- 规则：`unique` 只允许在实体字段上（输入和视图字段由语法拒绝）；类型限于 `String`、`Int32`、`Int64`、`Uuid`（`SIR-TYPE-001`）；不能与 `versioned` 同用（`SIR-VALID-002`）。按字段加载要求该字段已声明 `unique`，写主键名则提示去掉字段名（`SIR-VALID-006`）；键表达式类型必须与字段兼容（`SIR-TYPE-001`）；带 `version` 的实体先按字段加载再更新被拒绝（`SIR-VALID-006`），因为行锁按主键读。

## 18. 第 2 步的具体方案（供评审，未授权实现）

范围是第 12.1 节的最小范围：时间平移与数值加减。方案来自对现有表达式流水线的阅读（`Sir.g4`、`AstBinaryOperator`、`TypePass.typeBinaryExpression`、`TypeRules`、`ExpressionRenderer`、`WorkflowRenderer.renderPredicateNode`），没有运行代码，写法是示意。

### 18.1 要写出的东西

```
create Session as s { issuedAt: now(); expiresAt: now() + 15 minutes; revoked: false; }
validate token.expiresAt > now() else Expired;
update c { remaining: input.base - 1; }
```

### 18.2 语义规则

1. **时间平移是一种表达式，不是一种类型。** 形态是“表达式 加或减 整数 单位”，单位为 `second(s)`、`minute(s)`、`hour(s)`、`day(s)`（单复数都接受，上下文关键字，叫 `minutes` 的标识符照常可用）。左侧必须是 `DateTime`（任意单位）或 `Date`（只能用天）；结果与左侧同类型。时长不是 SIR 的类型：不能声明成字段、不能比较、不能单独出现，因此不会出现“存了一个时长字段却无法降级”的情形。量值是 0 到 2147483647 的整数字面量。
2. **数值加减。** `Int32`、`Int64`、`Decimal` 内部的 `+` 与 `-`，两侧类型必须相同（与 `==` 的现有要求一致），结果同类型；`Optional` 操作数不可。不含乘、除、取余。整数溢出不静默回绕：生成 `Math.addExact`／`Math.subtractExact`，溢出抛 `ArithmeticException`，按内部错误（500）处理；`Decimal` 无溢出。
3. **优先级与结合。** 加减高于比较、低于一元负号，左结合，因此 `now() + 1 day + 2 hours > x` 按预期解析。`-` 原来只作一元负号和常量前缀，现在也作二元减法。
4. **用在哪里。** 工作流表达式：绑定值、`validate` 条件、`return`。`find … where` 谓词里：不依赖 `item` 的部分（比较的值）可以用，例如 `item.expiresAt > now() + 5 minutes` 照常生成成 Java 值；依赖 `item` 的算术（例如 `item.a + 1 > x`）要翻译成 SQL，不在本步范围，Validate 明确拒绝而不是生成坏代码。
5. **语义细节要写明。** `DateTime` 在生成里是 `Instant`，“天”按 24 小时（UTC）平移；`Date` 是 `LocalDate`，按日历天平移。不提供“月”“年”，因为它们的长度不定。
6. **回写。** 规范化后的文本写成 `表达式 + 15 minutes`，单位统一写复数，所以 `1 day` 会被回写成 `1 days`，含义不变。

### 18.3 不做什么

### 19.1 做了什么

## 21. 第 3 步的具体方案（供评审，未授权实现）

范围是第 9 节定稿的最小语义：守卫挂在 `update` 上，只用于不带 `version` 的实体，绑定表达式不读目标自身字段。方案来自对现有更新、持久化、降级和生成代码的阅读（`AstUpdateStep`、`SpringBootWorkflow.UpdateStep`、`ConditionalUpdate`、`WorkflowRenderer.renderUpdate／renderPersist／renderPredicateChain`、`ValidatePass` 的 `SIR-VALID-004`），没有运行代码，写法是示意。

### 21.1 要写出的东西

```
load Credential by input.token as old else Invalid;
validate old.expiresAt > now() else Expired;
update old when old.used == false else Invalid { used: true; }
create Credential as fresh { owner: old.owner; used: false; expiresAt: now() + 7 days; }
persist old;
persist fresh;
return fresh;
```

这就是刷新令牌的轮换：旧凭据只有在“尚未使用”时才被标记为已使用，两个并发请求拿着同一个旧凭据，恰有一个成功。`when` 是上下文关键字；`persist old;` 不再带 `else`，失败的错误写在 `update` 上。

### 21.2 语义规则

1. **守卫是一个 Boolean 表达式。** 能引用：目标变量的字段（读存储中更新前的值，写作 `old.used`）、`input`、常量、`now()`、值侧的时间平移与算术。不用 `any`。
2. **形状。** 与 `find` 谓词一致：比较的左侧必须是目标的列（`old.字段`），右侧是不依赖目标列的值；可以用 `and`、`or`、`not` 组合。这条形状规则现在对 `find` 没有显式校验（左右颠倒会在生成时才出问题，是现有行为），守卫路径显式校验。
3. **目标。** 必须是 `load` 出来的变量，不能是 `create` 的变量（新建的行谈不上“从什么状态改”）；实体不能带 `version`（最小范围，`SIR-VALID-007`）；`else` 的错误必须在 `fails` 里声明（`SIR-FLOW-003`）。
4. **绑定表达式不得读目标自身的字段**（`SIR-VALID-007`）：绑定值在 Java 里按加载时的副本算出，守卫只钉住它判断的那些列；绑定若读了别的列，就会读到过期值再写回。可以读 `input`、常量、`now()`，也可以读别的变量的字段。
5. **与 `persist`。** 带守卫的 `update` 之后的 `persist` 不能带 `else`（现有规则已拒绝对不带 `version` 的实体写 `else`）。
6. **与 `atomic`。** 正交：守卫保证一行的“检查并写入”不可分，`atomic` 保证多步全有或全无。轮换需要两者同时用：守卫失败抛错，同一事务里的“创建新凭据”随之回滚。

### 21.3 生成

不需要新的 Mapper 方法。`persist` 对带守卫的更新生成 MyBatis-Plus 的 `LambdaUpdateWrapper`，一条语句里同时检查和写入：

```java
int oldAffected = credentialMapper.update(null, new LambdaUpdateWrapper<Credential>()
        .eq(Credential::getId, old.getId())
        .and(g -> g.eq(Credential::getUsed, false))
        .set(Credential::getUsed, old.getUsed()));
if (oldAffected != 1) {
    throw new InvalidException();
}
```

- `SET` 只含被绑定的列，值取自内存里已更新的对象（绑定值只算一次）；`WHERE` 是主键加守卫。这与版本路径不同：版本路径写全部变更列，之所以安全是因为版本把整行钉住了，守卫路径没有版本。
- 守卫谓词复用 `find` 的谓词渲染，把目标变量当作“被查询的行”（降级时把目标变量当作 `find` 的 `item` 变量传入，这是 `FindStep` 已有的做法）。
- 影响行数不是 1 就抛声明的错误。

### 21.4 不做什么

带 `version` 的实体用守卫；守卫里引用别的实体；乘除与对列的算术；守卫失败与“记录不存在”的区分（`load … else` 已覆盖不存在）；守卫失败时的重试。

## 23. 对前几步的真实库核验（2026-10-16，提交 `6f244fa`，CI #79 通过）

### 23.1 `Uuid` 主键：证实是缺陷，已修复

- **现象：** 以 `Uuid` 主键加载，500，`ReflectionException: There is no getter for property named 'id' in 'class java.util.UUID'`。
- **原因（两个）：** MyBatis 没有 `UUID` 的类型处理器，把它当成有属性的对象；`IdType.ASSIGN_UUID` 产出的是 `String`，不能放进 `UUID` 属性。
- **修复：** 凡是有实体存 `Uuid`（主键或字段），工程多生成一个 `persistence/UuidTypeHandler`（`@Component @MappedTypes(UUID.class)`，以规范文本存取）；`Uuid` 主键的 `@TableId` 改为 `IdType.INPUT`，服务在 `INSERT` 之前、主键为空时自己赋 `UUID.randomUUID()`。不存 `Uuid` 的工程输出不变（逐字节）。项目图为此多了一个项目级角色 `UUID_TYPE_HANDLER`。
- **验证：** 本机真实库——按 `Uuid` 加载、守卫更新、插入新的 `Uuid` 行、重放旧令牌得 409，全部符合预期；CI 上由新的 `TokenDeskBusinessConformanceIT` 覆盖。
- **范围说明：** 表里 `Uuid` 列按 `CHAR(36)` 的规范文本存取。用二进制列（`BINARY(16)`）不在本次范围内。

### 23.2 守卫更新“设成同值”：未发现问题，但依赖驱动默认值

`update ... when ... else ... { used: true; }` 对已经是 `used = true` 的行，在默认的 Connector/J 下仍返回 201/200（匹配到一行）。把连接串改成 `useAffectedRows=true`（驱动按“实际改变的行数”计数）后，同一请求变成 409。也就是说，守卫更新的语义依赖于“影响行数 = 匹配行数”这一驱动默认值。生成的工程的数据库连接串由部署方提供，生成器管不到；这是一条**部署约定**，不是生成器能强制的。新 IT 在 CI 的默认连接串下证明默认值成立。

### 23.3 按唯一字段加载：未发现问题

命中返回 200，未命中返回声明的错误（404），数据库里同一个键有两行（没有建唯一索引）时返回 500，日志是 `more than one Account row has the same name`，而不是悄悄取其中一行。这符合第 16 节的设计；新 IT 的 K1–K3 在 CI 上证明。

### 23.4 `Int64` 字段与整数字面量：证实是障碍，已修复

- **现象：** `item.qty > 0`、`input.amount - 1`、`input.amount == 5`，其中字段是 `Int64`，都报 `SIR-TYPE-001`（比较／加减两侧类型不一致），因为整数字面量一律是 `Int32`。凡有 `Int64` 字段的业务都会碰到，不只是双 Token。
- **修复：** 整数字面量（可带括号和负号）在比较或加减的另一侧是 `Int64` 时按 `Int64` 理解；`Int32` 的字段或输入仍不是 `Int64`，不会隐式转换。生成器本来就按字面量自己的类型写 `0L`，所以后面几层没改。
- **验证：** 本机真实库——`Int64` 的比较、加减、`find` 的 `item.qty > input.min + 1`（含大于 `Int32` 的值 10000000000）得到的行都对。

### 23.5 整数字面量超出范围：证实是缺陷，已修复

探针发现 `validate input.small < 5000000000 else Bad;` 通过所有静态阶段，生成的 Java 写 `5000000000`，编译时才报 `integer number too large`。现在 `SIR-TYPE-001` 在类型阶段拒绝超出所属类型范围的字面量。负号写在字面量前面，所以一个类型最小的值（`-2147483648`）无法写成字面量，这一点保留。

### 23.6 `find` 谓词的比较左右颠倒：证实是缺陷，已修复

`find Item where input.amount < item.qty ...` 通过所有静态阶段，生成时才以 `SIR-GEN-NODE-001`（`Find predicate left side must be item.<field>`）崩溃；`item.a == item.b` 也没有单语句形式。现在 Validate 阶段以 `SIR-VALID-001` 拒绝：比较的左侧必须是 `item.<字段>`，右侧必须是不读取 `item` 的值，并在消息里给出把 `0 < item.qty` 改写为 `item.qty > 0` 的写法。对列做算术仍由原有的消息拒绝，不重复报。

## 24. 第 4 步：错误状态码加入 401（2026-10-16）

**为什么存在：** 双 Token 里“令牌过期”“口令错误”“刷新令牌无效”在 HTTP 上的含义是 401，不是 400／404／409。原来 `error X http 401;` 被 `SIR-TYPE-001` 拒绝，作者只能把认证失败说成别的状态，客户端无法按状态码区分“需要重新登录”。这是第 15.3 节依赖链的第 4 步。

**做了什么：** 三处。`TypePass` 的允许集合由 400／404／409 变为 400／401／404／409（诊断文字同步）；降级的 `HttpStatus` 枚举多一项 `UNAUTHORIZED`，`lowerHttpStatus` 多一个 `case 401`；生成器原来就按枚举名写 `HttpStatus.<名字>`，没有改动。`docs/CLI_WORKFLOW.md` 里“只允许 400/404/409”的说明同步。

**不做什么：** 不加 403 及其他状态码（没有对应的业务；加一个只需要同样的三处，需要时再加）。这一步也不引入认证本身：生成工程里“没有认证身份”的 401 由 `ActorIdentityInterceptor` 直接写响应，与这里声明的错误无关。

**验证（本机，定向）：** `WriteSliceSemanticsTest` 新增一项（401 通过，403 以 `SIR-TYPE-001` 拒绝）；`GeneratorUnauthorizedStatusContractTest` 新增一项（声明 `http 401` 的错误生成 `HttpStatus.UNAUTHORIZED`）。旧状态码的输出不变。**CI：** [verify #81](https://github.com/HoloNova/Software-IR/actions/runs/38886724501)（提交 `e3b74e3`）success。

## 25. 第 5 步：`secret` 字段与 `matches`（2026-10-16，提交 `de563f6`，CI #82 通过）

### 25.1 为什么存在

登录要比对口令，而口令不能明文存、不能被读出来、也不能被拿去做别的运算。原来的语言里口令只能是普通 `String` 字段：存得下明文、能原样返回、能用 `==` 比对。双 Token 的行为 ① 和 ⑦ 因此停在“口令是明文比较”。这是第 15.3 节依赖链的第 5 步。

按三条规则打分：**新业务靠组合已有能力吗？** 不行——语言里没有“存摘要”这个动作，也没有办法在不暴露摘要的前提下比对。**一个普通需求在 SIR 里变得绕口吗？** 有：不加这个词，作者只能自己调用外部实现。**修复一类问题能让一类业务受益吗？** 能：所有“存了就不该再读出来、只需要验证”的字段（口令、PIN、API 密钥的哈希）都是同一类。

### 25.2 写法与语义

```
entity Account persistent {
  field name: String unique;
  field passwordHash: String secret;
}
...
create Account as account { name: input.name; passwordHash: input.password; }
...
validate account.passwordHash matches input.password else BadLogin;
```

- `secret` 与 `unique` 一样是上下文关键字，只在实体字段的类型之后有意义，叫 `secret` 的字段名照常可用；`matches` 是上下文的二元运算符，位置在 `containsLiteral` 同级（比相等紧，比比较松），叫 `matches` 的名字照常可用。`sir 0.2` 版本号保持，旧文档不受影响。
- **写**：给 secret 字段绑定的值（`create`／`update` 的绑定）由降级包进 `DigestExpression`，生成的服务存的是摘要，永远不是原文。
- **读**：secret 字段只能作为 `matches` 的左侧读取（`SIR-VALID-008`）。不能返回、比较、运算，也不能出现在 `view` 里，不能出现在 `find` 里（`matches` 比对发生在加载出行之后，由服务完成）。
- **声明**：只能是 `String`（`SIR-TYPE-001`）；不能同时 `unique`、`version`，不能带约束（`SIR-VALID-008`）。unique 的摘要没有任何调用者能构造出查找键；约束是对作者的值生效的，而存的不是作者的值。
- `matches` 的两侧都是 `String`，结果是 `Boolean`（`SIR-TYPE-001`）。

### 25.3 摘要方案

PBKDF2-HMAC-SHA256（JDK 自带，生成工程不增加依赖），每次随机 16 字节盐，600000 次迭代（OWASP 对该算法的当前建议），存成 `pbkdf2-sha256$<迭代次数>$<盐>$<哈希>`。迭代次数写在每条记录里，将来调高不会让已存的失效。比对用恒定时间。存储的文本不是这个格式（空、被截断、别的算法、迭代次数越界）时 `matches` 为 false，而不是抛异常——这样导入的旧数据只会匹配失败。

### 25.4 改动面（实测）

parser：语法两处（`secretModifier`、`matchesOperator`）、`AstField.secret`、`AstBinaryOperator.MATCHES`、builder。semantic：`NormalizedField.secret`（**必填事实槽位**，与 `unique`、`versioned` 同；现有“添加字段”的指令载荷须带它，是否改为可选仍留给负责人）、`TypePass`（secret 类型、`matches` 类型）、`ValidatePass`（声明规则、读取规则、view 规则、find 规则）、`SirDeclarationWriter`。lowering：`DigestExpression`、`BinaryOperator.MATCHES`、`ProjectArtifact.SecretDigest`、IR 校验两条。generator：`SecretDigestRenderer`、`ExpressionRenderer` 两处、导入收集。项目图：新的项目角色 `SECRET_DIGEST`。

### 25.6 已知限制（没有假装解决）

- **账号是否存在的时序差异。** `load … else BadLogin` 在账号不存在时直接返回，不做 PBKDF2，响应约快几百毫秒；响应体相同，但计时可以区分。堵上它需要“账号不存在时也做一次空摘要”，这是一个独立的语义（不属于 `secret`），这里没有做。
- **没有口令强度、长度、锁定、限流。** 强度可在输入字段上用约束表达；锁定和限流是别的能力。
- 迭代次数是常量，不可按工程配置。

## 26. 第 6 步：登录签发的凭据与 `requires authenticated` 的连接（2026-10-16，提交 `55898e7`／`70dc6cc`，CI #85 通过）

本节只是设计，来自对现有认证代码的阅读（`ApplicationRenderer` 的 `ActorIdentityRuntime`／拦截器、`buildActorIdentityTransportPlan`、`AstActorClause`），没有运行新代码。按负责人“改代码前先说明为什么存在”的规矩，这一步在实现前先写出设计。

### 26.1 现状（已核实）

- 能力里写 `actor Ref<User>;` 加 `requires authenticated`，生成工程里有一个拦截器：对这些路由调 `ActorIdentityAdapter.resolveAuthenticatedIdentity(request, context)`；没有身份或类型不对就直接写 401；有身份就放进请求属性 `actorId`，服务里的 `actor` 就是它。
- 这个 `ActorIdentityAdapter` 只有两种来源，由部署方的属性 `kcg.actor-identity.mode` 显式选择：`external`（部署方提供一个名字固定、且是唯一的 `ActorIdentityAdapter` bean，否则启动失败）和 `local-fixed`（只在本地 profile，固定一个身份）。
- 所以“拿登录签发的凭据去认证”这件事，**SIR 里没有任何位置能写**：凭据怎么变成身份，全在部署方手写的 bean 里。行为 ②（受保护接口认证）因此是唯一仍写不出来的一条。

### 26.2 要写出的东西

登录签发的凭据本来就是一行普通实体（第 23 节的 `Credential`：`Uuid` 主键、属主、有效期）。缺的只是一句话：“这个实体的行就是 `User` 的承载令牌”。建议新增一种顶层声明：

```
credential AccessToken for User {
  subject owner;        // AccessToken 的字段，类型 Ref<User>：令牌属于谁
  expires expiresAt;    // AccessToken 的字段，类型 DateTime：晚于现在才有效
}
```

含义：请求头 `Authorization: Bearer <令牌>` 里的令牌是 `AccessToken` 的主键（`Uuid`）；找到这一行、且 `expiresAt` 晚于现在，则身份是它的 `owner`。任何 `actor Ref<User>` 且 `requires authenticated` 的能力都用它认证。作废（登出）不需要新词：把 `expiresAt` 更新成现在，或删掉这一行，用现有的 `update`。刷新令牌是另一个实体，它的轮换已经是第 3 步的守卫更新，**不**声明为 `credential`，因此访问令牌和刷新令牌不会互相冒充。

### 26.3 语义规则

1. 声明的实体必须是持久实体，主键类型是 `Uuid`（令牌不可猜测，见第 23.1 节）。
2. `subject` 必须是该实体的 `Ref<User>` 字段，`expires` 必须是 `DateTime` 字段；两者都是引用，与 `unique` 的 `load … by 字段` 一样走引用角色，因此“每个引用角色都有样例”的两个契约测试要补。
3. 同一个 `User` 最多一个 `credential` 声明；有 `credential` 的 `User` 才能用凭据认证，其他 `actor` 仍走原来的 `external`／`local-fixed`。
4. 一个工程里，`requires authenticated` 的能力要么全部由 `credential` 认证，要么全部不是（拦截器背后只有一个 adapter bean），混用在语义阶段报错，而不是在启动时才发现。

### 26.4 生成

生成一个 `CredentialIdentityAdapter`，名字取现有 `external` 模式要求的那个固定 bean 名，所以**不新增运行模式**：部署方仍写 `kcg.actor-identity.mode=external`，启动检查“恰有一个 adapter”照旧（部署方又手写一个就冲突、启动失败，这是想要的）。它读 `Authorization: Bearer`，用实体的 mapper 按主键查，校验有效期，返回 `owner` 的主键；格式不对、查不到、已过期都返回空，由拦截器写 401。没有 `credential` 声明的工程输出不变。

### 26.5 改动面（估计，实现时逐个核实）

一个新的顶层声明意味着：parser（语法、AST、builder）、semantic（`ResolvePass` 声明与两个引用角色、`TypePass`、`ValidatePass`、`NormalizePass`、规范化节点与指令层 schema、`SirDeclarationWriter`、`StructureView`）、lowering（声明、`ActorIdentityTransportPlan` 增加凭据来源、IR 校验）、generator（`CredentialIdentityAdapter` 和 `ApplicationRenderer` 的接线）、项目图（声明角色）。规模大致是第 1 步（`unique`）加第 3 步（守卫更新）之和，是这条链上最大的一步。

### 26.6 替代方案

- **不加新词，adapter 仍由部署方手写。** 约 15 行 Java：读头、按主键查、比较有效期。SIR 作者（包括小模型）仍然写不出行为 ②，七条行为里留一条永远要靠外部代码。这违背“扩展性探针”的目的，所以不推荐。
- **把来源挂在 `actor` 子句上**（`actor Ref<User> from AccessToken.owner, AccessToken.expiresAt`）。每个能力都重复一遍，且“一个工程只能一种”的规则无处存放。不推荐。
- **JWT（无状态令牌）。** 需要签名密钥这类新的配置面和依赖，且登出作废要另设黑名单；与第 3 步以后“凭据就是一行”的路线不一致。不推荐。

### 26.7 验收与已知限制

验收：真实 MySQL 的 IT 里，登录签发令牌后用 `Authorization: Bearer` 调受保护接口得 200 且 `actor` 是令牌的属主；无头、格式不对、未知令牌、已过期令牌都得 401；把 `expiresAt` 更新成现在后同一令牌得 401。已知限制：每次受保护请求多一次按主键的查询（没有缓存）；令牌明文存储（它本身就是不可猜测的随机值，与口令不同；若要存摘要，需要另一种查找键，不在本步范围）。

### 26.8 实现结果与对设计的一处偏离

**偏离：语法位置。** 设计 26.2 写的是顶层声明 `credential AccessToken for User { subject owner; expires expiresAt; }`。实现时我读了引用角色与声明的代码，发现顶层声明要新增“声明种类”（符号、规范化声明、结构视图、项目图都要认识它），还要三个引用角色（含实体名，需要跨文件的“缺少 import”样例）。把同样的语义写成**实体的结尾子句**，所需的东西少得多，也不改变语义：

```
entity AccessToken persistent {
  identity id: Uuid generated uuid;
  field owner: Ref<User>;
  field expiresAt: DateTime;
  credential subject owner expires expiresAt;
}
```

“`for User`”可以省略，因为主体就是 `subject` 字段的 `Ref<User>` 指向的实体。只剩两个引用角色（`CREDENTIAL_SUBJECT_FIELD`、`CREDENTIAL_EXPIRY_FIELD`），都指向这个实体自己的字段，因此永远不会跨文件。`credential`、`subject`、`expires` 是上下文关键字，叫这些名字的字段或实体照常可用。语义规则 26.3 的四条一字不改：主键必须是 `Uuid`（`SIR-TYPE-001`）、`subject` 必须是 `Ref<实体>` 字段而 `expires` 必须是 `DateTime` 字段（不能是主键）、同一主体最多一种凭据实体、一个工程里“由凭据认证的能力”与“不由凭据认证的能力”不能混用（后两条 `SIR-VALID-009`）。

**生成。** 有凭据实体的工程多一个 `application/CredentialIdentityAdapter`：`@Component("kcgActorIdentityTransport")`（`external` 模式要求的那个固定 bean 名），并且 `@ConditionalOnProperty(kcg.actor-identity.mode=external)`——所以不新增运行模式，本地的 `local-fixed` 开发模式也照旧可用（它拒绝任何 adapter bean）。它读 `Authorization: Bearer <uuid>`（方案名不区分大小写；长度不是 36、不是合法 uuid、查不到、已过期都返回空，由拦截器写 401），按 `actor` 的实体选对应的凭据实体，用该实体的 mapper 按主键查，返回 `subject` 字段里的主体主键。没有凭据实体的工程输出不变。

**顺带修复的一个生成缺陷（本步发现）。** 引用字段用“一行的变量”绑定（`owner: user`，`user` 是 `load` 出来的行）会生成 `token.setOwnerId(user)`，类型不符，编译失败——这种写法此前没有任何夹具用过。降级现在把这样的绑定写成该行的主键（`user.getId()`）；`actor` 本来就代表主键，保持原样。

**改动面（实测）。** parser：语法一处、`AstCredentialClause`、`AstEntityDecl.credential`、builder。semantic：`NormalizedCredential`、`NormalizedEntity.credential`（**可选**槽位，现有指令载荷不受影响，与第 5 步的必填槽位相反）、两个引用角色、`ResolvePass`／`TypePass`／`ValidatePass`／`NormalizePass`、`SirDeclarationWriter`。lowering：`ProjectArtifact.CredentialIdentityAdapter`（含 `CredentialSource`）、引用绑定改写。generator：`CredentialIdentityAdapterRenderer`。项目图：项目角色 `CREDENTIAL_IDENTITY_ADAPTER`。两个“每个引用角色都有样例”的契约测试：`TypedReferenceSiteContractTest` 加了样例；`ProjectVisibilityTest` 把这两个角色列入“按构造就是本地的”（与 `UPDATE_TARGET`、`PERSIST_TARGET` 同类，理由写在测试里）。

**验证（本机）。**
- 真实 MySQL 手工：注册、登录得到令牌（库里一行：主体、约 15 分钟后过期）；不带头、`Basic`、格式不对、未知令牌、已过期令牌都是 401；带 `Bearer`（及小写 `bearer`）令牌得 201，库里该条笔记的作者是令牌的属主；`logout`（用现有的 `update` 把 `expiresAt` 改成现在）之后同一令牌得 401。
- 单元／契约：`CredentialClauseGrammarTest`（4）、`CredentialSemanticsTest`（7）、`CredentialLoweringTest`（3）、`GeneratorCredentialContractTest`（4）。各模块定向：parser 126、semantic 276、lowering 4／103、generator 99、project-graph 73、change 28、toolchain 238、kcg-cli 28，0 失败（已排除只能在 CI 跑的离线编译用例）。
- 旧输出对比：与上一提交打出的旧 jar 对 29 个夹具各生成一次，28 个逐文件字节相同，另一个是新夹具（旧工具链无法解析）。
- CI 侧新增：`BearerCredentialBusinessConformanceIT`（B1–B6：两个账号各自登录、令牌属主决定笔记作者、五种不合格的头都是 401、登出只作废一个令牌）和离线编译用例。IT 的各步骤先在本机真实库上手工跑过，IT 本身本机没有运行，以 CI 为准。

**已知限制。** 每次受保护请求多一次按主键的查询（没有缓存）；令牌明文存储（它是不可猜测的随机值；与口令不同，若要存摘要需要另一种查找键，不在本步范围）；受保护接口的 401 响应没有响应体（沿用原拦截器的行为）；`logout` 以“知道令牌”为凭据，不要求已认证（令牌本身不可猜测）；没有刷新令牌的专门语法——刷新令牌是另一个实体，它的轮换用第 3 步的守卫更新写（见 `TokenDeskBusinessConformanceIT`）。

## 27. 第 7 步：把双 Token 的组合升格（2026-10-16，负责人确认按建议做 B；实现见 27.6，工作区未提交，CI 未运行）

本节只是设计，来自对解析、符号解析入口和回写代码的阅读，没有运行新代码。这是第 15.3 节依赖链的最后一步，也是第 8.3 节“先组合、后升格、修饰定义为展开”里的“升格”。

### 27.1 现状：组合已经能写，写出来有多长

第 23–26 节之后，双 Token 七条行为都能用语言本身写出，真实库里验证过。一套完整的双 Token 现在是：账号实体（含 `unique` 的名字、`secret` 的口令）、访问令牌实体（`credential` 子句）、刷新令牌实体（`used` 标志）、登录、刷新（守卫更新轮换）、登出三个能力，加上它们的输入、视图和 `401` 错误。`valid/bearer-credential.sir`（访问令牌、登录、登出、受保护接口）加上 `valid/guarded-update.sir`（刷新轮换）合起来约 200 行。三条规则打分：**靠组合已有能力**——是；**普通需求在 SIR 里变得绕口**——是，“我要双 Token 登录”要写二百行；**能让一类业务受益**——是，凡是“由若干实体和能力按固定形状组成”的模式都一样（审计日志、软删除、邀请码）。所以升格有价值，但价值在**通用的“模式”机制**，不在“双 Token”这一个名字。

### 27.2 已核实的事实（决定了哪种升格便宜）

1. **展开只有一个插入点。** `ProjectSourceResolver` 把所有文件的顶层声明合成一个有序的 `ordered` 列表，再交给 `ResolvePass`。在这里往列表里加入展开出来的 `AstDeclaration`，后面的 Resolve／Type／Validate／Normalize 一行不用改。
2. **节点身份是确定性路径。** AST 的 id 来自 `ids.named(parent, kind, name)`，展开出来的节点可以用 `ids.named(模式声明的路径, "expanded", 角色名)` 派生，不用时间和随机数。
3. **展开节点不能被回写成源文本。** `SirDeclarationWriter` 把规范化模型里的每个声明写回所在文件（`SourceEditor` 按声明的 span 的来源文件分配）。展开出来的声明如果没有标记，一次编辑就会把它们作为普通文本写进源文件——那就变成了“脚手架”，不再是展开。所以规范化声明必须带“来源：某模式的展开”，回写要跳过它们；这需要给 `NormalizedDeclaration` 的七个变体（或它们的公共接口）加一个可选槽位，并改 `SourceEditor`、`StructureView`、项目图的来源。
4. **展开节点的诊断必须指回模式声明。** 展开出来的声明没有自己的源文本，它们的 `span` 只能借用模式声明的 span；所有 Validate 诊断因此会指向模式声明，作者看不到“具体是展开出来的哪一行错了”。
5. **名字冲突。** 展开出来的实体、能力（`Login`、`Logout`、`BadLogin`）与作者自己的声明同名时，现有 `SIR-SYMBOL-001` 的诊断也指向模式声明，原因不明显。

### 27.3 两种做法

**A. 语言里的展开（第 8.3 节确认的方向）。** 新增一种顶层声明（暂称 `pattern`／模式调用），在 `ordered` 列表处展开成声明。要做：语法与 AST（含参数：账号实体、令牌有效期）、展开器（把参数代入固定的声明骨架）、规范化声明的“展开来源”槽位及回写／编辑／项目图对它的跳过、诊断指回模式声明、名字冲突的专门诊断、模式本身的引用角色（账号实体）与契约测试样例。规模约等于第 1 步加第 6 步，并**第一次引入“没有源文本的声明”**，这会触及设计 02 的“稳定身份”与指令层的寻址规则（指令只能作用于模式声明，不能单独编辑展开节点，见第 14 节）。

**B. 工具链里的脚手架。** 新增一个 CLI 命令，例如 `kcg scaffold dual-token --account User --access-ttl 15m --refresh-ttl 7d`，把同一套骨架代入参数后，作为**普通 SIR 文本**写进工程的一个新文件。语言一行不改；没有隐藏节点，没有展开来源，没有回写问题；作者得到的是自己的、可读可改的声明。代价：之后模板改进不会传播到已经生成的工程；“双 Token”在语言里仍然没有名字（只有工具链知道）。

### 27.4 建议

**先做 B，A 留作后续并按需决定。** 理由：
- 骨架是 B 与 A 共用的（A 的展开器就是 B 的代入），先把骨架和参数做对、做验证，是 A 的前置。
- B 满足“二百行变成一条命令”这个现实需求，且完全不碰语言的稳定身份、回写和指令寻址——这三处正是 A 的风险所在，而它们是否值得为“少看见二百行”而改，取决于将来有多少个这样的模式。目前只有一个，不足以证明通用的展开机制值得它的代价。
- B 的产物自动通过现有的全部验证（它就是普通 SIR），双 Token 的真实库 IT 可以直接以脚手架的输出作为夹具，证明“生成的骨架确实是一套能用的双 Token”。

B 与第 8.3 节“修饰定义为展开”的方向有出入：那里要的是语言内的展开。我之所以建议先 B，是因为读完代码后发现 A 的成本集中在“没有源文本的声明”这一个新概念上，而这个概念在只有一个模式时没有足够的回报。**这一处请负责人确认或推翻**：若坚持 A，我就按 27.3 的清单做；若同意 B，我就做 B。

### 27.5 B 的范围（若同意）

1. 骨架：账号实体由作者已有的实体承担，脚手架只要求它有 `name`（`unique`）与口令（`secret`）两个字段，字段名作参数；生成访问令牌（`credential`）、刷新令牌、登录、刷新（守卫更新）、登出、所需的输入／视图／`401` 错误。名字带参数前缀以避免冲突，冲突时脚手架在写文件前就拒绝。
2. CLI：`kcg scaffold dual-token`，输出遵守现有的协议（JSON 结果、写入前预检、失败不留半成品），不覆盖已有文件。
3. 验证：脚手架输出对一个带账号实体的工程分析通过；真实库 IT 用脚手架输出作为夹具，跑完整的七条行为（登录、受保护接口、过期、刷新、重放被拒、登出、错口令与不存在的账号同样的 401）。
4. 不做：A 的任何语言改动；多账号实体；除 `dual-token` 以外的模式（骨架机制按“一个模式一个模板”写，但这一步只交付一个）。

### 27.6 实现结果（做的是 B）

负责人确认“按你推荐的来”，所以做了 B：`kcg scaffold dual-token`。语言一行没改。

**怎么做的。**
- 骨架是 `sir-toolchain-application` 里的一份资源文件（`scaffold/dual-token.sir`），里面是普通 SIR 文本，账号实体、两个字段名、前缀、两个有效期是占位符。
- `SourceEditor.scaffold(...)`（`sir-change`）把代入后的文本放到入口源最后一个声明之后——和 `edit` 放新声明的位置一样——交给**同一个正式语义分析**，只把新增的声明返回，并只保留命令可以提供的槽位（身份和派生槽位是编辑器自己的）。所以名字被占、账号缺字段、同一账号已有凭据实体，都以分析自己的消息被拒绝；没有为脚手架另写任何校验规则。
- CLI 把这些声明打印成一个 `KCG-CLI-COMMANDS-V1` 命令批，stdout 恰好是批，可以直接管道给 `kcg edit`；`edit` 保存的候选里它们就是普通文本。命令文档见 `CLI_WORKFLOW.md` 第 5 节。

**骨架本身先在真实库里验证过，再做成模板。** 手写的骨架（账号、笔记、受保护接口加上面的双 Token）在本机真实 MySQL 上跑完七条行为：登录得一对令牌、错误口令与不存在的账号同样的 401、访问令牌认证受保护接口且属主正确、刷新令牌不能当访问令牌、访问令牌过期后 401、刷新换新一对并作废旧的、重放旧刷新令牌 401、登出后刷新令牌 401。骨架在做的过程中暴露并修正了两处写法：`fails` 必须按名字升序；登出的返回需要自己的视图。

**测试。** `ScaffoldApplicationTest`（7）：返回的声明被 `edit` 接受、保存的候选能生成工程、同样的请求给出同样的声明、名字冲突被拒绝而前缀能避开、账号缺 `secret` 被拒绝、参数越界被拒绝、**提交进仓库的夹具 `valid/dual-token-scaffolded.sir` 恰好等于脚手架加 `edit` 现在写出的东西**（防止夹具和工具各写各的）。`KcgScaffoldCommandTest`（4）：真实子进程，stdout 是一个批、管道给 `edit` 成功、源目录不变、拒绝时没有批、命令行严格（缺选项、未知模式、重复选项、数字不合法）、帮助。`BusinessSliceHarness` 新增 `fixtureStatement`（让访问令牌过期这类测试时间内到不了的状态用）。各模块本机定向：parser 126、semantic 276、lowering 4／103、generator 99、project-graph 73、change 28、toolchain 246、kcg-cli 32，0 失败（已排除只能在 CI 跑的离线编译用例）。

**CI 侧新增** `DualTokenScaffoldBusinessConformanceIT`：用脚手架的输出作为夹具，在真实 MySQL 上逐条跑七条行为，并加一个 6 路同时刷新的竞争（恰有一个成功，其余 401，只多出一对令牌）。步骤先在本机真实库上手工跑过：竞争 6 路得到 1 个 201、5 个 401；IT 本身本机没有运行，以 CI 为准。

**没变的方向与已知限制。** 与第 8.3 节“修饰定义为展开”的出入已在 27.4 说明，负责人确认了 B。脚手架只有一个模式；一个账号只能脚手架一次（语言规则：同一主体只能有一种凭据实体，第二次的拒绝消息会这么说）；之后模板的改进不会传播到已生成的工程。若将来有第二个模式，再评估第 27.3 节的 A。
