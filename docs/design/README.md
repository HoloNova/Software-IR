## 2. 文档之间的权责

共享契约拥有字段名、身份定义和顶层状态；02 拥有业务语义；03 拥有编译阶段与目标映射；04 拥有数据库迁移与恢复；05 拥有本地部署；06 拥有平台任务与发布；07 拥有计划中的验收场景。其他文档引用这些定义，不再另创近义状态。

本组文档是对基础框架的细化。确需收窄或具体化的地方均写明推荐选择及代价，例如首轮只承诺相邻发布版本更新，不承诺任意跳版本更新。若后续修改一项共享契约，先修改其归属文档，再检查所有消费者及验收场景。

它们不改变仓库当前工作单、资格状态或 Accepted ADR。实施前按实际权威规则裁决差异，再制定工作单。本次仅对照源码与可执行测试修正设计表述，不降低产品要求，不估算未经调查的开发工期。实现状态统一分为已实现、部分实现、尚未实现、后续规划；执行通过/失败/未执行另行记录。

## 3. 已确认方向与本文推荐的区别

| 层级 | 内容 |
| --- | --- |
| 用户已确认 | 课程任务为验证线；生成与修改 SIR；源码为派生交付物；数据库更新不丢数据；网页下载完整源码；本地只需 Docker；未来可复用模块和搭积木 |
| 详细设计推荐 | Java 21 + Spring Boot + MyBatis-Plus + MySQL；Flyway；随包最小部署执行器；会话认证；相邻版本升级；平台关系数据库任务队列 |
| 后续能力 | 跨项目语义缓存、公共模块市场、拖拽画布、在线迁移、任意跳版本兼容、托管用户业务、完整离线分发 |

推荐方案足以用于逐项评审，不以大量待选项代替设计。依赖的精确版本、镜像摘要和性能阈值需要实施时在目标环境验证后锁定；这些是发布资格输入，不能在设计阶段编造为已验证事实。

## 4. 建议的评审方法

每一步只需要回答三件事：这个边界是否符合产品目标；其默认行为是否可以接受；其完成门能否证明它有用。出现不同意见时修改对应契约，不直接跳到修改模板或增加旁路代码。

优先评审 01 的用户交付、04 的保留数据承诺和 05 的 Docker 部署。这三项决定产品是否成立。02/03 决定如何稳定实现；06 支撑平台交付；07 决定何时值得扩大投入。
