# 第一步：产品边界、用户旅程与交付契约

日期：2026-09-08。状态：推荐设计草案。依赖[共享契约](00-shared-contracts.md)，下一步为[SIR 设计](02-sir-language-and-modules.md)。

## 1. 目标与成功定义

**实现边界：**本章为主设计目标。当前已有单文件编译、Spring Boot 文件生成和本地文件事务基础，完整课程业务为部分实现，网页下载及 Docker 独立交付尚未实现。[实现证据](implementation-baseline.md)与 G0–G7 的[验收阶段](07-validation-and-direction-roadmap.md)分别定义现状和完成门；本章用户旅程不是现有操作说明。

产品帮助学生把课程后端需求转化为可运行的 Spring Boot 工程。网页承担需求讨论、SIR 编辑、诊断、版本管理和下载；本地下载包承担构建、数据库初始化/更新与运行。

一次完整成功是：用户网页生成 -> 下载源码 ZIP -> 仅有 Docker/Compose 的机器部署 -> 按接口场景完成任务 -> 网页修改需求 -> 下载新版 -> 旧数据保留且新业务生效。平台编译成功只完成其中一部分。

完整源码包含业务代码、配置模板、测试、构建文件、迁移和部署执行器代码。用户能够阅读和自行开发源码；产品内的常规迭代仍通过修改 SIR，工具不承诺反向吸收用户手改 Java。

## 2. 首轮人物与场景

| 使用者 | 主要任务 | 产品应减少的负担 |
| --- | --- | --- |
| 学生作者 | 按课程要求完成后端，录入数据，继续改需求 | 安装 Java/Maven/MySQL、写重复代码、理解迁移工具细节 |
| 同组前端同学 | 查看接口说明并对接 | 猜字段、猜错误格式、手工补接口示例 |
| 指导或评审者 | 验证真实业务和技术贡献 | 只能观看一次演示、无法复现成果 |
| 平台维护者 | 排查生成失败、维护 Profile 与模板 | 把平台环境故障误判为用户 SIR 错误 |

第一验证题目为学生选课，第二题目推荐活动报名，用于检查模块是否真的可复用。首轮以本机课程演示为运行环境，不承诺公网生产托管。

## 3. 产品功能分级

| 级别 | 范围 | 排除 |
| --- | --- | --- |
| 必须交付 | 网页需求/SIR 输入、保存、生成诊断、只读预览、版本下载、完整源码、一键部署、受支持 UPDATE | 无实现的接口、只交付不可构建示例 |
| 课程主线 | 实体、CRUD、组合查询、分页、校验、关系、登录/角色/归属、简单状态动作和事务 | 任意 SQL/Java、通用业务流程引擎 |
| 产品可用性 | 错误定位、下载说明、接口文档、首次本地凭据生成、重复启动、失败说明 | 强制安装 KCG CLI、手工配置整个 Java 环境 |
| 后续扩展 | 受控模块包、表单组装、精确缓存、云端预热、可视化积木 | 首轮公共市场、在线零停机迁移、用户业务云托管 |

不能用“Agent 可以直接补 Java”填补范围缺口。无法表达的需求应列出已支持的近似方案及其差异，保持未支持状态，等待用户修改需求或后续扩展。

## 4. 网页信息结构

首轮提供一个项目工作页，包含四个任务区域：需求与 SIR、诊断与变更预览、生成任务状态、发布版本与下载。无需先做复杂 IDE 或拖拽画布。

用户可见的内容是业务变化，例如“新增邮箱，旧记录邮箱为空”“新增必填年级，旧记录回填 UNKNOWN”“删除成绩字段会被阻断”。模块 ID、IR 内部类名和锁协议放在可选技术详情中，不占据主要流程。

草稿与发布分开显示。继续编辑草稿不会改变已下载的版本；后台任务使用提交时冻结的快照。网页明确标识正在生成的是哪个草稿修订，不能任务完成后把结果归到用户刚改过的新内容上。

## 5. 首次生成旅程

1. 用户创建项目，填写课程要求与主要验收场景。
2. Agent 整理为业务模型和 SIR 草稿，明确角色、删除行为、关联和约束；有关键歧义时一次集中询问。
3. 编译诊断即时或通过检查按钮返回。每条错误可定位到当前 SIR；Agent 修订后再次编译，不直接修改生成代码。
4. 用户提交生成，平台冻结 sourceSnapshotId、Profile、模块版本和独立验收场景版本。
5. 平台依次编译、生成、构建、执行隔离业务测试并打包；进度显示阶段与失败类别。
6. 全部门通过后发布 releaseId。下载按钮指向该不可变包，不指向持续变化的工作目录。
7. 用户下载，解压，双击 deploy.cmd 或执行系统自带 shell 的部署入口。
8. 本地构建并初始化后显示接口地址、健康状态及本地产生的初始登录信息。

默认示例数据仅在隔离验证库加载。本地首次部署只初始化必要的系统数据和管理员身份，不能每次启动注入演示学生、课程或清空用户记录。

## 6. 需求修改与更新旅程

1. 用户基于某个已发布版本提出修改；保持 projectId、模块实例和声明身份。
2. 平台比较已发布快照与候选 SIR，展示 API、业务规则和数据库变化三个维度。
3. 支持的保留数据变更进入生成；破坏性变化在发布前阻断，报告受影响字段和原因。
4. 平台以新的 parentReleaseId 发布新包，保留全部旧迁移文件原字节。
5. 用户将新包解压到新目录，运行 update 入口；无需覆盖旧目录或复制数据库文件。
6. 本地按稳定项目/实例身份找到旧部署，检查当前发布与 acceptedBaseReleases，复用凭据和持久卷。
7. 构建新版成功后停止旧业务写入，重新做数据与结构检查，执行迁移，启动新版。

首轮只支持直接父版本更新。若本地为 r0001 而下载的是 r0003，其 acceptedBaseReleases 仅含 r0002，则明确要求先安装 r0002。网页保留中间版本下载。首次安装 r0003 到新空库仍可重放完整迁移链。

这是降低兼容性验证规模的推荐取舍；后续可以在明确验证兼容区间后开放跳版本，不能仅凭“迁移 history 是前缀”认定所有中间业务变化兼容。

## 7. 本地入口的用户语义

| 入口 | 意图 | 已有数据时的行为 |
| --- | --- | --- |
| deploy | 明确创建一次新部署 | 检测到同项目已有实例时先选择已有实例或明确创建第二实例，不覆盖 |
| start / stop | 启停当前已部署版本 | 保留数据与配置；不执行新结构迁移 |
| update | 把指定已有实例升级到下载包版本 | 必须匹配接受基线；缺卷/缺绑定时阻断 |
| status | 查看环境、版本和可定位失败 | 只读，不因检查发现缺文件而重建 |
| recover | 显式裁定中断步骤并执行受支持恢复 | 不猜方向、不清库；不能证明时给出阻断证据 |

第一次使用的常规路径是一键操作。只有错误、冲突、多个实例或数据库目标不明时才需要进一步选择，不为每一个下载和内部步骤重复询问。

“停止项目”没有删除数据的含义；首轮不提供与停止按钮相邻的默认清空功能。用户通过自己的 Docker 管理操作删除数据属于产品承诺之外，但后续 update 必须识别缺失并停止。

## 8. 用户能看到的状态

| 位置 | 主要文案 | 背后事实 |
| --- | --- | --- |
| 网页 | 草稿已保存 | 某个 draftRevision 已持久化 |
| 网页 | 正在生成 / 构建验证 | 某个固定快照的 jobStatus 与 stage |
| 网页 | 可下载 | Release 发布与包摘要已确定 |
| 本地 | 正在准备依赖 | 构建进行中，尚未修改业务数据 |
| 本地 | 数据库检查未通过 | BLOCKED，提供可执行建议 |
| 本地 | 更新中断，需要恢复 | RECOVERY_REQUIRED，保留数据与现场 |
| 本地 | 部署完成 | 数据库 READY、目标应用启动并通过健康检查 |

平台不知道用户是否本地部署，除非用户主动提供本地结果。本地健康检查证明应用与 schema 契约匹配，不能替代完整课程业务验收。

## 9. 下载与独立性契约

下载包不含用户本地数据库数据、密码或部署实例 ID；同一包可以在不同机器新建独立实例。包内包括版本、源码及第三方依赖说明。生成后正常构建不要求平台登录、授权回调或私有 KCG 二进制。

首次构建需要公共镜像与依赖网络。平台不可达时仍能构建和运行已下载包；网络完全不可用的离线交付不在首轮承诺内。预构建镜像是可选加速，不替代源码构建路径。

修改生成源码可以继续作为普通项目开发，但生成包摘要核验应明确报出偏差。受管理更新不自动覆盖这些改动，也不声明已合并人工 Java 修改。

## 10. 产品接口需求

界面调用平台的 typed API，不直接执行编译或拼接 shell。需要创建项目、读取/保存草稿、提交生成、获取诊断与任务状态、取消任务、列举版本和下载指定包；具体接口在 06 定义。

网页预览只判断声明层面的变化，明确标注本地数据检查待部署执行。它不能把“新唯一约束可生成”显示为“用户数据库一定无重复数据”。

自然语言修订提交带 expectedDraftRevision；旧 Agent 回答不能覆盖用户的新修改。自动修订有最大尝试次数与耗时边界，达到边界后返回当前诊断，不无限生成。

## 11. 完成门与产品决策

本步设计接受后，应有一个明确的任务集、支持范围和下载包定义。产品首版验收至少包括：

- 不熟悉 KCG-Code 的试用者，能从网页拿到包并在只装 Docker 的干净机器启动。
- 同组同学仅凭包内接口说明完成至少一条正常调用和一条错误调用。
- 下载新版本到另一个目录，完成一次保留数据的升级。
- 输入不支持的需求、损坏包或错误基线时，得到清楚失败，旧数据未被误处理。
- 平台断开时，已有源码包仍可构建部署；不以平台不可用为运行失败理由。

若用户主要卡在环境下载与启动，应先改善 05；若主要卡在需求表达与诊断，应先改善 02/06；若业务无法覆盖，则依据真实场景扩充 SIR。不要仅以生成文件数量或界面完成度判断产品价值。
