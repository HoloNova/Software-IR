## 1. 先用用户流程说明系统

首次：**SIR → 理解软件 → 生成完整源码 → 按需拉依赖、构建、启动和验证。**

修改：**已有软件 + 增加／删除／更新指令 → 修改草稿 → 使用同一套语义检查与生成能力 → 保存新 SIR、更新工程 → 按需构建与业务验证。**

“理解软件”包括解析、导入、名称绑定、类型和规则检查。“生成源码”是 Target Lowering 和文件渲染；它不是 Parser。“实际运行”属于独立执行能力；纯静态检查不因此联网、启动数据库或写工程。

语义不仅是接口功能，也包括功能依赖的数据、输入输出、流程、约束和引用。SIR 是可编辑、可重新打开的软件描述；Java 是其派生产物。指令修改软件描述，不直接对 Java 做字符串替换。

## 2. 当前问题及直接依据

| 已核对的实现 | 对架构的影响 |
| --- | --- |
| `sir-change/api/ChangeOperation.java` 的六个 sealed 变体，`internal/PlannerCore.java` 按操作分派 | 请求类别、范围检查、影响规划相互绑定；普通组合修改受到专用分支限制 |
| `ChangeSet` 要求恰一个操作，`ChangePlan` 不允许 CREATE/UPDATE/DELETE 混合 | 同一轮增加 Input、增加能力、修改另一能力无法作为普通组合处理 |
| `SemanticProjection` 在 Change 中逐一识别声明、字段、步骤、表达式和类型 | 变更模块重复维护语言知识；新增语义时要额外补投影。当前 Error 投影未含模型的 `httpStatus`，不能把旧投影视为完整基础 |
| `ProjectChangePlannerCore`、`LockedProjectPlanning` 固定多源成员、位置与单工作流范围 | 多源已有编译与存储，但不是通用多源编辑系统 |
| `NormalizedSemanticModel` 保存 binding、表达式类型、诊断及来源 | 已验证模型不能被直接修改后继续使用旧 binding；需要明确草稿与验证结果 |
| `GraphEdgeKind` 只有 DECLARES/LOWERS_TO/OWNS_ARTIFACT/GENERATES_FILE | Graph 可追踪生成归属，不是完整语义依赖图 |
| `CompilationStages` 已共享单源四阶段；`ProjectCompilation` 已逐文件解析并复用 Lowering/生成 | 可以迁移编排而不是另写第三套编译规则；单源、多源尚需统一结果合同 |
| 源码检查未发现 Semantic 中已有 SIR writer/printer | 指令修改后的可重新打开源文件是新交付，不假设已有序列化能力 |

上述结论来自阅读，不是本轮新运行的测试证据。当前单源/多源生成、已支持的 Change、版本保存与恢复继续有效；新架构尚未实现。

## 3. 六个逻辑层，以及一个入口编排

| 层 | 拥有的职责 | 输入 → 输出 | 不承担 |
| --- | --- | --- | --- |
| 源文件与解析 | 源清单、严格编码、语法、AST、当前源位置；语法渲染 | SourceSnapshot → AST；结构化源描述 → SIR 字节 | 业务合法性、框架映射、进程执行 |
| 软件语义 | 软件结构定义、身份、引用、类型、业务规则；统一结构接口 | AST → 已验证 SoftwareSnapshot；提供编辑草稿和语义结构定义 | SQL/Java 决策、网络/磁盘状态 |
| 通用变更 | Add/Delete/Update 的机械编辑、前后结构比较、变化说明 | 草稿 + CommandBatch → 新草稿；旧/新快照 → SemanticDelta | 按 Course/Workflow/Input 编写特判，目标文件规划、业务验证 |
| 目标实现 | Profile 支持、实现决策、物理映射；未来数据库变更规划 | SoftwareSnapshot + Profile + 显式旧实现信息 → Lowered IR | 依赖下载、探测现场、文件提交 |
| 文件生成 | 按 Lowered IR 渲染所有受支持的源码和构建声明 | Lowered IR → GeneratedFile 集合 | 重新理解 SIR、增删改准入、写盘 |
| 工程应用 | 版本、受管清单、文件差异、事务、CURRENT、恢复；源与生成物关联 | 候选源/编译证据 + 已保存基线 → 可核验计划/应用结果 | 再实现业务规则、下载依赖或业务判分 |

Application 入口编排调用上述公开接口。**构建与真实验证是独立执行端口**，由外围 runner 负责工作目录、依赖仓库、Maven、数据库、应用进程、资源限制和证据；不是第七个语义 Pass，也不是所有请求默认执行的步骤。

这些是职责，不是六个新服务或六个新 Maven 模块。优先保留现有九模块；只有确定的依赖边界无法在现有模块表达时，才在实施单中评审拆分。

## 4. 核心：语义层提供一个结构合同

### 4.1 类型化结构定义，而不是无类型 JSON 树

采用由语义层拥有的 **SoftwareSchema**：定义节点种类、稳定属性键、值类型、子内容、引用角色、集合顺序和缺省规则。通用值只允许受控的标量、节点、引用、可选值、有序序列和按键集合；不接受任意 Java 对象、脚本或 SQL。

节点的结构化访问通过 schema 的公开接口完成。语义业务代码和 Lowering 可继续使用强类型模型；需要的结构访问/转换适配也归语义层。**不能在 Change 内再维护一份 `instanceof` 投影清单；不能把 Java record 的全部字段反射成业务含义。**

推荐将结构分类和稳定键显式标记在语义模型定义上，由编译期工具产生schema及访问适配；未知字段导致缺项失败，而不是运行时反射猜含义。标量精度/枚举/引用等映射在Semantic定义一次。若现有record无法直接采用该方式，R1先给出最小等效的单一声明来源，不接受模型、descriptor、投影三份手写字段表。是否需要注解处理器及构建集成由R1探针冻结，不先假定已有代码生成工具。

每个模型字段必须在语义定义中明确属于以下之一：

| 类别 | 示例 | 比较与编辑规则 |
| --- | --- | --- |
| 软件事实 | 字段类型、约束、排序、HTTP 错误状态、workflow | 进入语义差异；明确可编辑槽位 |
| 身份与引用 | 声明身份、字段身份、已绑定目标、引用角色 | 类型化比较；不靠相似名称猜对应 |
| 来源信息 | 文件归属、span、语法节点位置、注释 | 单独保存/比较；不能把行号当业务变化 |
| 派生分析 | SymbolTable、推导类型、诊断、缓存 | 不由指令写入；候选分析重新产生 |

schema 的完整性检查覆盖现有 sealed 变体及其字段；新增未分类字段或结构必须在构建门报缺项。声明、引用、步骤和条件的有序性分别定义，不能把所有 List 排序后比较。首次建设需完整盘点现有字段，不能照抄旧投影遗漏。

### 4.2 草稿与已验证快照

- **SoftwareDraft**：可编辑、不可变的结构化软件草稿。结构可检查，业务上允许暂时缺引用；不携带可被当作有效证据的旧 binding/type 结果。
- **SoftwareSnapshot**：完成正式分析后的不可变软件快照，包含强类型业务模型、完整结构访问、正式绑定及独立 SourceMap。
- **SourceSnapshot**：可重新打开的具体源文件字节。语义等价不代表源字节相等。

草稿中的引用用schema定义的名称/引用角色或批内句柄表达；基线目标身份可作为预期约束，但旧AST binding表不成为草稿的有效绑定。源转换负责写出可解析的引用形式，正式Resolve再建立候选绑定；任何预期目标不一致都拒绝，不由Change补一套名称求解。

它们是编辑、验证与保存三种状态，不是三个竞争的软件真相。发布版本的持久起点是 SourceSnapshot；SoftwareSnapshot 从该源和冻结编译版本派生。草稿成功写出新源并正式分析后，才取得新的已验证快照。

现有 Normalized model 在兼容期仍是验证后的强类型模型。优先用语义层的单一 schema 接口覆盖它，而不是先推倒 Type/Validate、让 Lowering 消费任意属性包。公开模型演进必须在独立实施单中逐字段证明兼容关系。

### 4.3 “变更层不再补功能”的具体含义

新增一种语言结构：Parser 增加语法（确有新语法时），Semantic 提供结构定义及合法性规则，Target 提供实现与渲染。Change 只遍历相同结构接口，不增加 `AddX`、`ModifyX` 或业务策略。

新增普通业务：优先组合现有能力，只修改 SIR 或提交指令；不改编译器。系统不能以每道题一个节点种类来假装通用。

通用协议、集合算法、身份约束或 bug 修复仍可能改变内核。“免适配”不等于永不维护，也不意味着语义定义/目标实现自动生成。**不能把原来的逐功能分支改名为插件注册表，再说 Change 已解耦。**

## 5. 指令合同

以下为拟议 typed API，尚不是可执行 CLI 语法；文本表达只是该 API 的序列化入口，不引入规则语言。

### 5.1 固定三种指令

| 指令 | 参数和行为 |
| --- | --- |
| Add | 目标容器、schema 槽位、类型化新值，以及有序容器需要的插入位置；已有唯一身份不得覆盖 |
| Delete | 目标选择器和可选预期旧值；删除明确对象，不自动级联清理引用、孤儿声明或数据库 |
| Update | 目标选择器、类型化替换值和可选预期旧值；更新属性或整个子树，不暗中变成执行 Java 补丁 |

CommandBatch 绑定 schema/协议版本、软件身份、起始基线及源摘要，保存有序指令列表。按列表顺序作用于私有草稿；后指令可引用本批新增对象的批内句柄。对象身份由工具按现有规则取得，批内句柄不自动成为持久 SIR 身份。

每步检查 schema 形状、目标存在性、预期旧值和写入位置；最终整体进行业务检查。允许“先新增 Input，再新增引用它的能力”；中间缺少引用不自动落盘。结构错误、陈旧目标、非法最终软件都导致整批失败，CURRENT 和原源零修改。

不通过 `AddCapabilityWithInputAndModifyWorkflow` 之类组合名编码业务。一批混合增删改是普通能力，不把旧 ChangeSet 的“恰一项”当新合同。

### 5.2 目标定位与身份

持久声明/字段身份优先沿用已支持的显式 `@id`。未注解旧声明保留名称派生身份，不自动升级，也不按相似内容猜改名。当前局部 AstNodeId/变量身份不能被包装成已交付的永久 nodeKey。

选择器由**所属声明身份 + schema 槽位路径 + 基线绑定**组成。无持久键的有序子节点，只能在已绑定的草稿修订上按槽位定位；前序指令改变结构后，旧选择器需明确失效或用新返回句柄重取，不能默默命中另一项。第一版可以 Update 整个 workflow/条件子树，避免为表达普通修改强迫用户维护每个表达式的 nodeKey。

跨改名、跨文件移动、跨任意重排的稳定编辑需要独立身份证据。只有新身份能力通过后才扩大承诺，不为普遍的属性更新预先阻塞整个架构。

### 5.3 明确作用范围，不再重复语言检查

指令本身明确哪些对象被写入；可选 WriteScope 只描述允许写的身份/结构区域，由 Application 绑定，不定义“字段类型修改”“只读能力修改”等逐功能策略。领域合法性归 Semantic，Profile 支持归 Lowering，数据演进归目标迁移规划。

删除字段后仍引用它：Semantic 报错。更改字段导致 DTO、Service 同时变化：这是实现影响，不要求用户把派生文件逐一写入 WriteScope。删除字段即使 Core 合法，也不意味着已有数据库可执行 DROP。

完整候选 SIR 可作为另一种编辑入口：统一计算差异并显示其完整写入范围，由调用方接受该具体计划；不强行反推用户曾提交哪些指令。两种入口共享差异、生成和工程应用，不保留两套语言比较算法。

### 5.4 一次普通组合修改

例子：已有课程查询，现在增加“按名称搜索课程”，同时把原报名查询改为不区分报名状态。

```text
Add：声明集合中加入新的搜索Input
Add：声明集合中加入引用该Input的查询能力
Update：原报名查询的workflow条件
```

这是流程示意，不是已发布的文本语法。三项指令同批进入草稿，正式分析检查新引用和两项功能，生成器得到新DTO/Controller/Service及原Service更新，Application预览完整CREATE+UPDATE。失败不先留下一个无功能的Input；成功后的新SIR可以独立重开。换成商品/订单的同类组合，无需新增指令种类。

## 6. 从编辑草稿回到真实 SIR

**选择结构化源编辑，不采用对源字符串的全局替换。** SIR writer/printer 属于源表示能力；语义层提供结构与来源映射，writer 不判断业务合法性。读取未受支持的结构必须拒绝编辑，不用“其他文本”绕过完整性。

第一轮按已定位的声明/子树边界重渲染受影响声明；未改声明及文件原字节保留。声明内注释和格式的保存需要明确source trivia（注释、空白等来源材料）模型；格式变化在预览展示，受保护注释不得删除或丢失。无法证明保真时只返回受限预览/拒绝应用，不把预览自动当作丢注释许可。该来源模型与技术边界在迁移R2的只读探针中冻结，未过门不开放落盘。

写出后，**从候选真实源字节执行一次 Parse → Resolve → Type → Validate → Normalize**。这是候选的新分析，不是拿旧 binding 继续计算，也不是在后续阶段按名字重新 Resolve。

往返完成门：写出再读回的已验证软件事实与指令目标一致，正式引用指向预期对象；所有 SourceSpan 对应新源；未编辑源材料按预览合同保留。若语法不能表达某事实，不能只保存一份不可重新打开的内存模型。

多源保持显式清单、单 software、每文件位置和导入权限。文件归属单独保存；纯移动可表现为来源文档的 Update，业务 Delta 为空。源变化仍需新基线发布，不能只因 Java 相同返回“无需保存”。不增加第四种业务操作 Move/Rename；身份和物理实现可能使某些 Update 暂不可执行，但不能让它们变成 Change 内的新业务类别。

## 7. 生成、比较和工程应用

### 7.1 一个编译入口，共享规则

统一的纯内存编译服务消费 SourceSnapshot。单文件入口只构造一成员快照，多源入口按清单组织。原始诊断在各阶段保留，支持真正 stopAfter；兼容包装维持旧公开行为和版本拒绝。

候选生成仍采用现有完整 SIR 分析与完整 Lowering/Generator。**本轮不设计新增量编译系统。** 完整语义依赖失效机制尚未实现，不能先承诺只编译一个模块。

### 7.2 语义差异和文件差异分开

SemanticDelta 回答“软件变了什么”；Application 的 FileDelta 回答“实现文件需怎样更新”。二者都用三类差异，但不是一一对应：新增一个字段可更新多个文件；纯源移动可不改任何 Java；修改同一个能力可同时改变查询逻辑和公开接口。

Application 比较**完整**受管生成文件集合，计划允许 CREATE/UPDATE/DELETE 混合。来源解释来自语义正式绑定和 Lowering 的归属信息；共享/project 级文件也纳入完整比较，不能假定某个能力的 Service/Controller 闭包等于所有影响。Graph 继续记录机械来源，不冒充依赖求解器。

普通计划至少绑定：旧基线、指令及 schema 版本、候选源、已验证语义/编译/Profile 版本、全量候选文件清单、每个文件前后证据和当前输出根。用户手写的非受管文件不纳入自动更新；受管旧文件被手改则明确冲突，不靠字符串合并掩盖。

### 7.3 源与文件共同发布

工程应用需要能承载：只有源变化、只有实现变化、两者共同变化，以及混合文件变化。保持一个 CURRENT，发布版本同时绑定保存源及完整派生清单；不增加“源 head”和“Java head”两个正式版本。

复用现有锁、安全文件句柄、锚、预算和恢复原语，**不假定现有 UPDATE-only 或单声明改名日志可以直接装入通用计划**。新事务协议及老格式读取兼容需独立审定。旧 ADR-023/024 的 NoChanges、非空 UPDATE、源布局守卫在旧入口继续有效，不通过改文档放宽。

CURRENT=B0 只向后补偿，CURRENT=B1 只向前核验清理；未知方向保留拒绝。逻辑批次成功不是目录级多文件同时切换，也不是数据库事务。保存新源必须与更新工程的发布关系一起通过中断和重开验证。

## 8. 独立构建与真实验证

Target 的纯规划决定依赖、插件和版本，Generator 渲染 pom；实际下载由 BuildRunner 执行。BuildRunner 消费具体候选工程、冻结 Profile、仓库策略及资源合同，不读取 SIR 来猜依赖。

| 结果 | 证明什么 | 不证明什么 |
| --- | --- | --- |
| STATIC | SIR 和目标生成检查通过 | Java 可编译、业务正确 |
| BUILD | 对指定生成清单的真实工程构建成功 | 可连接现场数据库、业务正确 |
| START | 应用启动并就绪 | 原始需求满足 |
| BUSINESS | 独立 oracle 检查真实行为 | 任意环境/题目都正确 |

无环境记 NOT_RUN；失败结果与源/文件/Profile 摘要、测试版本和环境绑定。下载日志、启动日志和业务诊断分开，不混入编译诊断。

静态用户流程可生成/保存源码而不运行。要求“验证后更新”时，先在独立候选目录构建并使用隔离数据库验证，证据匹配候选清单后才允许工程发布；不得为了验证先修改正式业务数据库。发布后实际部署及其数据库变化仍由未来 G3/G4 的独立状态机负责。

现有 Q23 `check` 继续保持只读静态协议；两样本真实评测只是测试侧起点，不是已交付通用 runner。重活按 AGENTS 优先 CI，本机不运行全量或业务 IT。本轮文档提交不要求代码验证。

## 9. 减少重复工作，但不以缓存替代真实性

现有计划/应用重编译用于防计划陈旧。迁移第一轮保留此边界，先统一规则与结果，不同时引入缓存或局部编译。

目标编排可在**同一受控请求**复用同一不可变候选编译结果；跨请求计划仍是外部输入，执行时必须重建或取得经过独立认证的同源编译证据。旧基线的重开验证不能仅凭自洽摘要或调用方缓存跳过。

是否持久复用编译产物，另以源/编译器/schema/Profile 摘要、来源认证和陈旧反例评审。架构允许优化，但不把“两边全部重跑”写成永恒要求，也不把“只改一个对象”视为依赖已正确失效的证明。

## 10. 拟议接口与模块落点

以下名称仅说明职责；实际签名、预算、诊断、编码域在对应实施单冻结。

| 接口/数据 | 存放方向 | 存在原因 |
| --- | --- | --- |
| SoftwareSchema、SoftwareDraft、SoftwareSnapshot、结构访问与强类型适配 | `sir-semantic` 公共/内部 API | 只有语义拥有软件事实定义；Change 不另建投影 |
| SourceMap/源结构、SIR writer | `sir-parser` 源表示 API，与 Semantic 单向协作 | 保存合法源与真实位置，不把业务规则放 Parser |
| CommandBatch、Add/Delete/Update、选择器、SemanticDelta、编辑/比较内核 | `sir-change` | 固定机械操作，不持有框架/磁盘知识 |
| TargetLowering/Profile、完整 Lowered 与验证 | 现有 lowering 模块 | 保留实现决策与受支持范围 |
| GeneratedFile 集合 | 现有 generator 模块 | 纯渲染 |
| CompilationService、FileDelta/计划、版本应用 | Application | 编排并唯一拥有工程状态 |
| BuildRunner/BusinessVerifier 端口 | Application 的执行 API；具体 runner 在独立执行适配区 | 隔离进程、环境、日志与业务判分 |

目标 Change 内核只依赖语义结构 API；从它移出 Graph/Lowered 文件计划职责。该依赖收敛是迁移目标，当前 POM 仍依赖 Parser/Semantic/Lowering/Graph。不要求第一步就修改全部 POM，也不建立任意 ServiceLoader/脚本扩展。

Schema 内的引用和强类型检查归 Semantic；文本 writer 由解析层的结构 API 消费合法表示，不能反向依赖 Semantic 模块形成环。若现有 AST 无法承载必要的 source trivia，先评审 parser API 演进，不在 Change 内偷偷新增文本解析器。

## 11. 演进与旧能力处理

新方向是从专用候选规划器迁向统一结构编辑，不是继续扩大六类操作或为每个组合增加 Java 策略。旧组合原型草案可作为问题证据，但它的旧 Q24 实施范围不自动获准。

- Q22：继续暂停，后续用来源与业务分离的共同发布模型重审，不照搬专用移动计划/发布族。
- Q23：实现与证据保留，暂停 CI 验收推进；共享编译入口迁移时保持 JSONL/阶段/只读合同。
- 已验收 Q16–Q21：原入口、格式、拒绝与恢复继续保留，历史文件不改写。逐步建立适配和对照后才退役，不默默更改旧操作含义。
- 数据库演进：归目标实现及本地部署，仍待 G3；统一编辑能描述字段删除，不自动允许破坏数据。
- 完整发布/Docker/Web：通过同一入口消费结果，不建立第二套软件模型；仍未实现。

## 12. 迁移完成的判据

| 需要证明的结果 | 核心证据 |
| --- | --- |
| 新语义无需改 Change | 一个符合当前模型风格的新结构或受控 schema 扩展探针，其 Add/Delete/Update/比较使用原内核；同时语义和目标检查没有被绕过 |
| 完整识别已有事实 | 所有现有种类及字段分类、逐字段灵敏度；位置噪声不当业务；如 httpStatus、排序、分页等变化不能漏掉 |
| 普通组合自然表达 | 同批新增 Input、新增能力、修改旧 workflow；不预置未用声明、不写场景专用操作 |
| 编辑可以持久化 | 指令 → 新 SIR → 正式重编译的语义/引用一致，当前位置正确；源保真变化有明确预览 |
| 文件结果完整 | 应用结果逐路径/逐字节等于候选从零生成；共享文件和混合差异无遗漏 |
| 发布可以继续使用 | 源-only 发布、多源编辑、独立重开、连续两次修改；旧 handle 陈旧拒绝 |
| 恢复方向可靠 | CURRENT 前后、中断后再恢复、恢复再次中断；来源不明材料保留 |
| 实验有意义 | 同 SHA CI + 真实构建/HTTP/数据库及独立 oracle；静态、运行、业务证据分开 |

所有新架构实现门目前 **NOT_RUN**。本轮完成的是方案与文档一致性检查，不把现有 1049 项历史结果当作新架构通过。

## 13. 明确不采用的方案

不采用“保留特殊分支，只把名字改成增删改”；不把业务判断搬成 Change 插件；不建立用户可提交的规则 DSL；不直接改生成 Java；不反射比较整个 record；不全量重写现有编译器；不拆为微服务；不同时建设增量编译、第二 Target、数据库迁移和 Web 平台。

选择理由：统一的是软件结构接口与机械编辑算法；领域规则和实现仍在应在的层中。这样既使一类组合业务共同受益，也保留现有类型系统与生成成果。具体实施按[迁移路线](../history/roadmap/LAYERED_ARCHITECTURE_MIGRATION.md)分阶段授权，本方案和 Git 推送均不授权开工。
