# KCG-Code 项目负责人操作与交接手册

> 写给项目负责人。你不需要记住以前和哪个 Agent 聊过什么，也不需要依赖任何 Agent 的私人记忆：仓库和这些文档还在，就能继续往下做。

## 最简单的用法

1. 想知道项目现在能做什么、验证到什么程度：看 [项目状态](PROJECT_STATUS.md)。
2. 想交办一件事：直接在会话里说清楚目标和范围。新对话里让 Agent 先读 [AGENTS.md](../AGENTS.md)、[MAIN.md](../MAIN.md)、[项目状态](PROJECT_STATUS.md) 和[验证说明](qualification/README.md)（`MAIN.md` 第 0 节有冷启动清单）。
3. 做完后按下面的清单验收。
4. 要不要提交、推送，由你当时明确说了算。

不再使用“工作单文件”：以前的工作单（Q 系列）和阶段控制文档已归档在 [history](history/README.md)。

## 怎么验收一次交付

不要只问“做完了吗”，按顺序看：

1. **范围**：改动是否只落在你交办的目标里；有没有顺手加入新的产品方向、依赖或重构；有没有碰 `.claude/`、`.trae/`、`.codex/`、`.agents/` 等受保护内容；有没有用 reset、restore、clean 覆盖已有工作。
2. **证据，不看形容词**：新增或修改了哪些测试；哪条命令真的执行了；run／fail／error／skip 各多少；哪些没运行，是 `SKIPPED`、`BLOCKED` 还是 `NOT_RUN`。“应该可以”“大部分通过”不是验收结论。
3. **完成条件逐条闭合**：你交办时说的每一条，都要有代码、测试输出或文件链接对应。
4. **重活看 CI**：全量闸门和真实 MySQL 场景在 GitHub CI 上跑；CI 证据要给出 commit SHA、run URL 和 artifact，且覆盖待验收的源码。之后又有新提交，旧运行不证明新提交。
5. **核心代码要讲得清“为什么存在”**：你不应该遇到“不知道它为什么这样设计”的核心代码；解释写在代码注释或对应文档里。

## Git 授权

- 提交、推送和任何历史操作都由你**当时明确授权**；“确认”“继续”“验收通过”不自动等于 Git 授权，也不自动开始下一项工作。
- 提交范围只含本轮已审阅的内容，一个提交只做一件事（代码、测试、文档放在同一个提交里）。
- 作者写你本人，Agent 只写在提交信息末尾的 `Co-Authored-By`。
- 不自动 force-push、rebase、reset、checkout、restore、clean 或 stash；确需改写历史（比如整理提交记录）时，Agent 要先给你看备份方式、完整命令和结果，你确认后才执行。

## 汇报默认保持简短

详细证据写进项目状态、验证说明或对应报告；聊天里先说结论，再说证据，最后说需要你决定的事。只有测试或构建失败、需要扩大范围、出现两个会改变产品含义的方向、提交或推送失败、无法安全划分任务外改动时才展开。

## 如果中途换 Agent

让原执行者写清四件事：已经修改的文件、已经运行的命令和结果、当前第一个失败点、下一步建议及哪些猜测尚未验证。新 Agent 从冷启动清单开始，不要只把旧 Agent 的最后一段聊天复制给它——聊天里常缺代码版本、测试状态和未提交的修改。

## 如果文档互相冲突

按 [MAIN.md](../MAIN.md) 第 0 节的顺序：你的当前指令与 AGENTS.md → Accepted ADR → 当前代码和实际执行的测试 → 项目状态与验证说明 → 目标设计 → 历史材料。ADR 与代码冲突时，先停下普通开发，单独裁决，不让 Agent 私下选一个版本继续做。
