# R4 报告：版本应用与恢复（Claude 会话环境验证完成）

- 日期：2026-10-13。分支：`main`。授权：负责人 2026-10-13 回复"继续"后开始 R4；R5 未授权。
- 计划与进度：[R4 计划](R4-version-apply-plan.md)。前置：[R3 报告](R3-compilation-preview-report.md)、[R2 报告](R2-command-editing-report.md)。
- 结论：现在可以把一批"增加／删除／更新"指令改出的新 SIR 保存为下一个版本，**同时**把生成工程改成这个版本的样子；一次变更可以新增、更新、删除文件和目录，也可以只改源不改任何文件；变更中途被打断时，工程一定落在旧版本或新版本之一，不会停在中间；保存后可以重开当前版本继续修改。生成工程的结果与"候选从零生成"逐字节一致（目录树一起比）。

## 1. 怎么用

```text
当前版本 ─ 指令（增删改）→ 新工程源码 ─ 规划（只读）→ 计划 ─ 应用 → 新的当前版本 + 更新后的生成工程
                                                    └─ 中断？→ 恢复句柄 ─ 恢复 → 回到旧版本，或确认新版本
```

三个对外入口：`VersionPlanningApplication`（规划，只读）、`VersionApplyApplication.apply`（应用）、`VersionApplyApplication.recover`（恢复）。指令编辑用 `SourceEditor.edit(SourceSnapshot, CommandBatch)`。

应用时会在状态目录的锁下**重新规划**，并要求结果与调用方手上的计划完全相等才继续；整个过程持有同一把锁。

## 2. 新增了什么，以及为什么存在

| 部件 | 为什么存在 |
| --- | --- |
| `VersionPlan`、`VersionPlanningApplication` | 应用必须从一份可独立重建、可核对的计划开始。计划可含新增／更新／删除，可以没有任何文件操作（只改源），候选可以增删或挪动源文件。冲突（被手改的受管文件、被占用的新路径、文件变目录）在出计划前就拒绝 |
| `VersionPlans` | 把两份编译结果变成计划的**唯一**位置。规划用它建计划，事务恢复时再用它从保存的源码重建，所以"独立重建"是真的 |
| `VersionTrail`、`VersionBinding` | 新事务自己的日志和证据格式：零到 256 步，五种步骤（建目录、建文件、改文件、删文件、删目录）。旧格式的规则一概没放宽 |
| `JournalSlots` | 把旧事务的"双槽日志"机制抽成共用基类，旧事务保持原行为，新事务共用同一套已验证的机制 |
| `VersionTransaction` | 事务本体。先把备份、暂存副本、候选版本、历史关系、绑定全部准备好，再逐步改工程。提交点仍是已有的 `CURRENT` 指针：它还指着旧版本，恢复只向后（还原备份、把新建文件移回暂存、删掉新建目录、重建被删目录）；它已指向新版本，恢复只向前（核验、清理）。恢复前先用保存的源码把新旧两个版本重新编译一遍，证明绑定记录确实是它们产生的；任何物理身份与记录不符的对象视为被外部替换，原样保留 |
| `VersionReceipt` 与历史校验 | 事务结束后整个目录作为回执保留；历史校验器现在认识两种回执，旧回执的规则不变 |
| `VersionApplyApplication` | 对外入口：应用／恢复。半途中断时返回恢复句柄，**不会**自己恢复 |
| `SourceEditor` 的工程入口 | 版本存储只认工程形式的源码，而指令编辑器原来只能改单文件。现在能按文件改写声明，未改的文件字节不动 |

其他证据：

- 五类变更（混合、新 Java 包、只改源、只新增、只删除）应用后与从零生成逐字节一致，目录树一起比较；新 Java 包场景同时验证旧目录整棵移走，用户放在旧目录里的文件让该目录保留。
- 连续四个版本（改输入、只改源、换包、回到第一个版本）每一步都与从零生成一致；磁盘上只存 4 个不同版本，回到第一个版本复用它。
- 旧式更新与新式更新在同一个状态目录里先后使用（两种顺序都试了）。
- 6 个防护用例：中途被外部替换的文件、被占用的新建路径、被篡改的绑定、不对应的句柄、未完成事务期间再开一个、重复使用已结束的事务 ID，恢复都拒绝，且状态与输出目录保持原样。
- 完整链路：指令改源 → 保存为下一版本并更新工程 → 重开已保存版本 → 同一批里一次更新一次删除 → 再保存；已保存的文本与编辑出的文本逐字节相同。
- 业务集成测试（Query、Write、Relation、ChangeLoop、ProjectWorkflow）仍为 `NOT_RUN`：当前环境没有 Docker 和 MySQL。

## 4. 与计划不一致或需要你知道的地方

1. **旧代码并没有被改成"看到新记录就拒绝"**。计划里我写的是旧代码读到新格式会拒绝，实际做成了历史校验器同时认识两种回执，所以旧式更新在新式更新之后照样能用（已测）。旧格式本身的解析规则没有任何放宽。
2. **版本数量上限沿用旧值：每个状态目录最多保存 8 个不同版本、32 条关系**。也就是约 7 次更新后再更新会被明确拒绝（"baseline history count exhausted"）。要不要做清理／轮换，是一个需要你来定的产品决定，我没有擅自放宽。
3. **准备阶段的中断不会自动清理**：绑定写完之前被打断，工程没被碰过，但事务目录会留下，需要人工处理。这与旧事务一致，我保留了这个保守做法。
4. **新增的声明落在入口文件里**；声明用到的名字必须已经在入口文件里导入，否则读回分析会拒绝并说明原因。改文件头和导入仍然不支持。
5. **只覆盖工程（SIR 0.2）形式**。单文件的旧存储路径（旧的 Bundle 和旧的单源更新）没有改动，也没有并入新事务。
6. 整包搬迁、新增能力两个场景是抽样而不是全量检查点（矩阵很大），抽样包含全部边界检查点；混合与只改源是全量。

## 5. 明确没做

- 数据库迁移、热部署、缓存、局部编译。
- 版本清理／轮换（见上第 2 点）。
- 构建、启动与业务验证（R5）。
