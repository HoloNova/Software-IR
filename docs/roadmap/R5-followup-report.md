## 1. 为什么版本数量要设上限

先回答你的问题。历史记录不是可以随便丢的备份，而是**证据**：

1. **每次打开项目都要把历史全部读一遍并互相核对**（`ProjectPublicationHistory.validate`）：所有保存过的版本、版本之间的关系、每次更新的完成凭据，任何一项对不上就拒绝，不靠猜。所以打开的成本随历史长度线性增长，必须有上界，否则项目越用越慢。
2. **每次更新都会留下旧生成文件的硬链接**，用来证明"这个文件确实是我生成的、没被外部换过"，恢复靠它判断文件归属。历史越长，占用的磁盘越多。
3. **旧事务（Q21）定下的规则**是：达到预算就明确拒绝，不自动清理，也不假装历史无限（见 ADR-024 第 3 节）。自动删历史等于删证据，一旦删错，恢复就没法判断方向。

当前值：每个状态目录最多 8 个不同版本、32 次发布、累计 64 MiB。回到已有的版本不占新名额（版本 ID 相同），但每次发布都占一条关系。所以真正的问题不是"为什么有上限"，而是"到了上限怎么办"——以前答案是"没办法"。

## 2. 做了什么

### 2.1 状态目录换代（`VersionStateRolloverApplication`）

做法：**不改上限，不删历史**，在一个全新的目录里从当前版本重新开始。

```text
旧状态目录（8 个版本，已满） ──读取并严格核对当前版本──▶ 在空目录里登记同一份源码（版本 ID 不变）
        │                                                   │
        └── 新目录核对无误、旧目录再核对一次后，写一个 RETIRED 标记 ◀──┘
```

- 项目停在**同一个版本**（版本 ID 相同，因为它只由源码、生成文件和输出目录决定），新目录的历史额度重新从零开始。
- 旧目录唯一的改动是最后写入的一个标记文件 `RETIRED`。工具链对不认识的对象一律拒绝，所以旧目录从此无法被误用来更新——否则输出目录会被改走，新目录就再也对不上。
- 旧目录原样保留，是旧历史的证据，只用于人工查看；删掉它对新目录和输出目录都是安全的（互不共享文件）。
- 中途进程崩溃：旧目录在最后一步前保持可用；再用同一个请求重跑，如果新目录恰好就是"只含这一个版本的全新状态"，只补做最后的退役；否则明确拒绝并说明，不会动它。

由一次**独立设计评审**（三位评审者从崩溃安全、身份绑定、误用与路径三个角度读真实代码）塑造的要点：三个根目录既按字面又按真实路径比较（嵌套、符号链接、别名都拒绝），任何创建动作之前先检查；新目录必须不存在或为空；只认"新建登记"，不认"已登记"；旧目录的锁自始至终持有；"只读存档"的说法被推翻，改成明确的"退役标记"；超限报错现在会提示使用换代。

测试（17 个）覆盖：连续 8 个版本→第 9 个被拒→换代→再更新 5 次，每次都等于从零生成；历史里有旧式更新；全部路径关系；非空、半成品、有自己历史的目标；错误版本、被手改的工程、没恢复的半途更新、别处持有的锁；在每一步停止；旧目录的计划不能用于新目录。

### 2.2 锁缺陷（已存在，评审中发现，已证实并修复）

`StateRootLock` 先打开 LOCK 文件、再检查本进程是否已持有，被拒绝时又关掉刚打开的通道。在 POSIX 上，**关闭同一文件的任何通道都会释放本进程在该文件上的所有锁**。结果：同一进程里一个本该被拒绝的第二个调用者，会悄悄把第一个调用者的锁放掉，别的进程随即可以开始事务，而第一个调用者还以为只有自己。

我先写了会失败的测试（起第二个 JVM 去抢锁）确认缺陷真实存在，再修：检查和打开在同一把门里完成，被拒绝的调用者根本不打开文件；登记按"LOCK 文件本身的身份"而不是路径写法区分（符号链接、硬链接别名视为同一把锁——第一版修复漏了这一点，是代码评审发现的）；释放放在 `finally` 里。

### 2.3 工程形式的完整链路真实验收（`ProjectVerificationChainIT`）

SIR 0.2 的多文件课程项目，真实流程：保存的版本先过一遍业务检查 → 用**更新指令**把课程编码长度上限改大（会改生成文件）→ 候选做真实验证（Maven 构建、Spring Boot 进程、本次运行专属的 MySQL schema、按原始需求写的检查员）→ 通过"验证后更新门"发布 → 重开保存的版本，源码是改后的、磁盘上的工程与它一致。

反例：另一个候选是合法的 SIR、能构建、能启动，但把状态过滤放宽，会多返回只有取消报名的 ART101。它前三档通过，业务档失败；门拒绝发布，状态目录和生成的工程逐字节没变。拿一个候选的证据去开另一个候选的门，被拒绝。

## 4. 与计划不一致或需要你知道的地方

1. **上限没有放宽。** 8 个版本／32 次发布／64 MiB 不变；旧事务族和新事务族共用这些常量，改它们需要修订 ADR-024，我没有擅自做。换代是显式的、可审计的操作。
2. **旧目录被写入了一个标记文件。** 设计评审指出"只读存档"在现实里不成立：旧目录和新目录对着同一个输出目录，旧目录仍可更新，会让输出和新目录的版本对不上，而且没有恢复办法。标记是让旧目录无法再被工具链使用的最小改动；要撤销只需手工删掉它（这是旧目录回到可用状态的唯一办法，也意味着之后新目录不再可信）。
3. **换代必须在原机器、原路径上做。** 旧状态绑定了原始绝对路径、文件身份和硬链接、输出目录路径和工具链版本：直接复制或搬到别的机器上，旧目录打不开，因此换代也做不了。新目录是全新的、没有回执，可以用保留硬链接的方式（`tar`、`cp -a`、`rsync -aH`）搬走，前提是输出目录的绝对路径相同、同一个文件系统、同一版工具链，到了目标上先做一次 `inspect` 再用。
4. **崩溃安全的范围是"进程崩溃"。** 不声称覆盖断电后目录项是否落盘。
5. **未覆盖的评审意见**：评审还指出"只认新建登记"的守卫在单进程测试里无法触发（它防的是别的进程在检查和登记之间抢先建立同一个状态）。我保留了守卫，没有为它造一个并发测试。
6. **工程形式的链路测试里"错误候选"是用文本替换做出来的**，不是指令；"好候选"是真正的更新指令。验证与门并不关心候选怎么来。
7. 其余 R5 报告里的限制仍然成立（只有受控样本、没有 SLM 输出集、旧 harness 未迁移、进程树与脱敏的边界等）。

## 5. 给开发服务器迁移的提示

- 代码都在 `main` 上，`git clone` 即可，**不需要搬状态目录**（状态目录不在仓库里）。
- 开发服务器的资源比这里大时，可以直接用 `AGENTS.md` 里的闸门命令；本会话的闸门命令是 `env -u JAVA_TOOL_OPTIONS nice -n 10 taskset -c 0,1,2 mvn -B -o -Dmaven.repo.local=$HOME/.m2/repository clean verify`。第一次需要联机把生成工程的依赖拉进 `~/.m2`（仓库的 CI 里有"联机预热一次"的步骤）。
- 两个独立验证 IT 需要真实 MySQL 与参考环境变量，开启方式是 `-Dkcg.verification.enabled=true`，参数与 `verify.yml` 中该步骤相同。没有环境时它们只打印 `NOT_RUN`。
