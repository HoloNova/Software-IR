## 1. 为什么按这个顺序

Change 的耦合根因是它没有可直接消费的统一软件结构合同。先改操作名或开放多项计划，会保留重复语义判断，并撞上源保存与事务限制。因此先把软件事实定义清楚，再做可重新打开的编辑，之后才接工程应用。

优先复用 Parser/Semantic 的检查、Spring Boot Lowering/Generator、Q23 编译步骤、完整源快照及安全文件原语。旧入口和证据不因设计更新退役。

## 3. 每阶段的首个事实检查

### R1

列出现有全部声明、字段、表达式、步骤、类型、引用角色及 record 字段。包括 `httpStatus`、PATCH presence、分页、排序、关联投影、元数据/target 等；分类哪些是事实、来源或派生项。检查 schema 结构如何与现有强类型模型共用定义，确保不是第三份手写投影。

首次实施单冻结 schema/版本、不可变值、标量精度、集合顺序、身份、预算和完整性闸门。不能先用反射 equals 获得演示再补语义分类。

### R2

实际核对 AST 是否保存注释/空白与声明跨度，writer 能否保留未编辑原字节，以及 normalized 内容是否能合法写回。用单声明替换和“新增 Input + 新增能力 + 修改旧 workflow”生成只读候选；如有格式损失必须在预览明确展示。

受保护注释不能删除；无法证明保真时不开放应用，格式变化预览不自动成为丢注释许可。指令API/文本外壳、选择器陈旧规则、批内句柄和source map在本阶段冻结。先以当前可证明的身份编辑，不以字符串猜改名；需要新的 nodeKey/语言语法时，写清影响后另审，不能伪造稳定性。

### R3

检查 `CompilationStages`、`ProjectCompilation` 和现有 diagnostic mapper 的旧合同。统一的是编排与结果，不复制分析规则。纯计划需要实际文件证据，不能拿 Graph hash 自证来源。业务变化与文件变化分别展示。

target/Profile 的支持和物理映射信息明确由目标层提供；当前缺少数据库迁移时，相应应用步骤应阻断，不把合法候选当可执行数据库更新。

### R4

逐项核查已有 UPDATE/CREATE/DELETE、Rename、Q21 事务是否能复用哪些原语；冻结新的计划、Bundle关联、日志/历史识别及限额。现有 mixed rename 不自动抵扣任意混合业务事务。新门通过前不公开应用入口。

验证 source-only 发布后仍能继续编辑，以及旧证据/handle 的读取或陈旧拒绝。原 CURRENT 恢复方向不可改；数据库状态另管。

### R5

核对现有 conformance harness 和 Q23 真实试跑，评审 runner 的实际可复用面，不把测试代码直接宣布为产品服务。固定依赖仓库策略、JVM/进程资源、日志脱敏、数据库互斥与清理合同；按原始需求构造正反 oracle。

无需等待完整 Web/Docker 平台才能做隔离实验，但实验不抵扣未交付的平台或数据库功能。

| 数据库初始化/更新/漂移/恢复 | 未交付；现有业务 IT 用测试 DDL | 保持 G3 独立目标；不塞入通用增删改内核 |

| 路由/更多查询等零散项 | 未立项或当前 Profile 受限 | 有具体需求时扩语义/目标，检验无需额外补 Change |

## 5. 验证与提交规则

纯文档只做链接、术语、差异及 `git diff --check`/`git status --short`，不跑构建。后续代码本机只定向；全量双门和五既有业务 IT 由 GitHub CI 承担，新源往返/指令/混合发布证据须绑定当次源码。历史 Q21/Q23 数字不计入新门。

提交和推送只按负责人当时明确指令执行；本轮已有文档授权，后续阶段不继承它。不通过“确认验收”或旧手册默认流程推导新阶段或 Git 授权。
