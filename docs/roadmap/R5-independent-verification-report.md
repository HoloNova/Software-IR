- 结论：对一份具体的候选，调用方现在可以**明确选择**验证到哪一档——只静态生成，或者真实构建、真实启动、再由独立的需求检查员判断业务——每一档单独出结果，并绑定到这份候选。前一档没过，后面的档一律记"未运行"，不记失败。环境不可用（数据库连不上、被别的运行占着）也是"未运行"，不算候选的错。另外有一道"验证后再更新"的门：没有这份候选的、够高档位的、清理已证明的证据，就不允许发布新版本。

## 1. 怎么用

```text
候选 SIR ──静态生成──▶ 绑定到候选（源集合摘要＋文件清单摘要，与已保存版本的身份相同）
   │ 只写入这批文件到一个空的、专属的目录，并证明目录里只有它们
   ├─ BUILD ：真实 Maven 构建，得到唯一的可执行 jar
   ├─ START ：真实启动，连隔离数据库，调用方指定的路由返回 200 才算就绪
   └─ BUSINESS：独立检查员按原始需求判断；它只拿到地址，拿不到候选的 SIR 和生成文件
收尾（无论成败）：先停应用，再释放沙箱；报告里写明是否证明了"什么都没留下"
```

入口：`CandidateVerificationApplication.verify`（验证）、`VerifiedVersionApplication.apply`（验证后更新）。构建、启动、数据库、业务判断通过端口接入（`VerificationPorts`）；进程适配器在 `io.kcg.sir.application.execution`。

## 2. 新增了什么，以及为什么存在

| 部件 | 为什么存在 |
| --- | --- |
| `VerificationStage` / `StageStatus` / `StageOutcome` / `VerificationReport` | 把"每一档证明什么、没证明什么"固定下来：四档永远各有一个结果，PASSED／FAILED／NOT_RUN 分开，失败和未运行有稳定的原因码，报告可以算摘要。报告拒绝"前一档没过后一档却通过"这种不可能的组合 |
| `VerificationBinding` | 证据必须绑定到候选。它用的就是已保存版本的身份（源集合摘要＋文件清单摘要），所以证据能和"将要发布的版本"逐位对上，而不是靠调用方说"这是同一个" |
| `VerificationPorts`（沙箱、构建器、宿主、检查员） | 应用层不认识 Maven、Spring、MySQL。检查员的接口里没有候选的源和文件——能看到候选的检查员会把任何候选都判对 |
| `CandidateVerificationApplication` | 固定顺序与"后面全部未运行"的规则；把生成的文件**恰好**写进空目录并证明没有多余文件；数据库连不上时仍保留构建证据；端口抛异常只记"端口异常"，不复制异常文字（可能带密码）；收尾顺序固定且有证明 |
| `MavenProjectBuilder`、`SpringBootApplicationHost` | 真实进程：从空环境启动（只放行 `PATH`，固定 JDK、语言、时区），不读用户自己的 Maven 设置，调用方给仓库策略（本地仓库、联机或离线）。有构建、启动超时，超时就结束整棵进程树并说明是否证明已结束。旧的测试侧 runner 没有任何超时 |
| `ProcessLog`、`LogRedactor` | 日志按行脱敏后才落盘，有大小上限（超出部分读掉丢弃，不会把进程堵住），构建日志、应用日志、业务日志分开，引用里记大小和实际写入字节的摘要。过长的行整行替换成一句说明，不截断（截断可能留下密码的前半截）。应用日志在应用停止时才交出，因为它在此之前一直在增长 |
| `VerifiedVersionApplication` | 设计 08 的要求："证据匹配候选清单后才允许工程发布"。证据必须是这份候选的、到调用方要求的档位都通过、清理已证明；否则在读写状态目录和工程**之前**就拒绝。接受证据后仍走原来的版本更新，所有原有检查不变——过期的计划依然被拒绝 |
| 测试侧：`MysqlVerificationSandbox`、`CourseEnrollmentOracle`、`IndependentVerificationIT` | 产品没有数据库驱动也没有数据库初始化，所以隔离库和需求检查员留在测试里，复用旧 harness 已验证的参考环境、建库、互斥锁、测试 DDL／种子数据 |

- **编排（18）**：候选身份与已登记基线的身份逐位相同；构建看到的文件等于生产工具链从零生成的目录；完整通过时顺序为开沙箱、构建、启动、检查、停应用、释放沙箱；检查员拒绝只让业务档失败；构建失败后面全部未运行但仍释放；数据库不可达时保留构建证据且启动记未运行；端口抛异常不泄露异常文字；端口未配置是未运行不是通过；构建声称成功却没有产物或产物在候选目录之外是失败；候选目录不空就拒绝；清理证明不了会写进报告。

## 4. 与计划不一致或需要你知道的地方

1. **真实环境的 IT 只覆盖单文件形式的两个受控样本**（课程报名正确／漏过滤），和 Q23 试跑一样：这不是 SLM 输出集合，不是模型成功率。工程（SIR 0.2）形式的候选只在"验证后更新门"的测试里用真实静态生成加假端口验证过，没有对它做真实构建和启动。生成器对两种形式用同一套，预计可行，但没有实测，不宣称。
2. **旧 harness 和旧 IT 一行没改**，所以现在有两套相近的做法（旧的测试侧 runner 和新的适配器）并存。让旧 harness 改用新适配器是以后的事，需要你另行决定。
3. **进程树结束只覆盖仍存活的进程的后代**。一个已经退出的父进程留下的孤儿进程，系统里没有可靠的办法找到。对构建和应用来说，超时时父进程还活着，所以覆盖了主要情形；已退出的父进程留下的后代不在保证内。
4. **日志脱敏只处理调用方声明的字符串，且按整行精确匹配**；跨多行的密钥不处理；超过 64 KiB 的行整行丢弃。
5. **资源限制是单进程级别**：构建和应用各有时间上限、堆和元空间上限。没有用 cgroup 约束整体内存；本机预演也没有用 `systemd-run`（这个会话环境没有）。
6. **`VerificationReport` 是进程内的对象**，调用方能自己构造。"验证后更新门"防的是弄错和过期（不同候选、档位不够、清理未证明、旧计划），不是防调用方恶意伪造。
7. **应用端口固定为调用方指定的一个**，一次只能跑一个应用；端口被占会记未运行。数据库侧靠旧的互斥锁串行。
8. **报告摘要含主机相关的文字**（例如构建诊断里的绝对路径），所以不同机器的摘要不同；这是证据，不是可复用的缓存键。第一版不做缓存。
9. **适配器测试假定有 POSIX shell**；代码本身用的是标准库，但在 Windows 上没有验证。
