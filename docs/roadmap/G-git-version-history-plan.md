## G1 的设计（只用已核对的现成部件）

**规划**：输入是当前 SIR 的 `SourceSnapshot`、候选的 `SourceSnapshot`、输出根，不再有状态目录。

1. 用 `ProjectBaselineVerification.compile` 分别编译当前版本和候选版本（现在候选就是这么编译的）。
2. 身份相同则返回"无变化"。
3. 用 `FileDelta.compare` 对照磁盘，得出冲突；用现有的形状检查。
4. 用 `VersionPlans.compare` 得出计划。`VersionPlan` 需要去掉必填的状态目录字段（新增一个不含它的计划类型，旧类型保留到 G4）。
5. 对**全部受管文件**做整体核对：磁盘必须等于"当前 SIR 的编译结果"，否则报告"需要重新生成"。

**应用**：按计划逐个写文件，不用日志、备份和恢复。

- 新建或更新：同目录写临时文件，再原子重命名。
- 删除：核对内容与基线一致后再删。
- 目录：按计划新建；清空后的目录删除，里面有用户放的文件则保留，沿用 R4 已验证的规则。
- 每步前都校验路径守卫（沿用 `PathGuard`、`SecureFileAccess`）。
- **新增规则**：磁盘文件已经等于候选版本字节时，视为"已应用"，不算冲突。这使中断后重跑能够完成。
- 不一致或无法判断时，返回明确的"需要重新生成，请处理"诊断，不自行修复。

**Git 端口**（新增，放在 `api`）：

- 能力：检测仓库、必要时初始化、保存快照。
- 适配器放 `execution` 包，用 `ProcessSupport` 调用 `git` 命令，沿用现有的超时、进程树终止、日志脱敏。
- 应用前后各保存一次快照，只提交 SIR 源码和受管生成文件，不推送。
- 没有 `git` 可用时**拒绝应用**（负责人决定），不静默继续。

## 证据计划

不沿用 R4 的故障矩阵（它证明的是旧事务）。新路径要证明：

1. 应用后工程与候选从零生成逐字节一致，目录树一起比（沿用 R4 的五类变更用例）。
2. 在每个写入点中断后重跑，最终结果与一次成功的结果相同。
3. 被改过的受管文件、被占用的新路径、形状变化都被拒绝，且磁盘不变。
4. 工具链差异的整体重新生成：生成目录与编译结果不一致时给出"需要重新生成"，重新生成后一致。
5. Git 端口：新仓库自动初始化、快照包含且只包含预期文件、没有 Git 时的行为。
6. 权威验证在 GitHub CI（同 SHA）；本机只跑定向测试。
