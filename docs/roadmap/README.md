# 项目阶段控制与 Agent Prompt

这是一份面向项目负责人的辅助文档，用来判断当前阶段、下一步方向，以及把阶段工作交给 Agent。它不替代 `AGENTS.md`、`docs/roadmap/ACTIVE_WORK.md`、Accepted ADR 或资格文档。

设计目标和验收场景以 [主设计文档](../design/README.md) 为准，当前实现证据以源码、测试和 [实现基线](../design/implementation-baseline.md) 为准。

本文件与主设计是 `AGENTS.md` 权威层级中的“后续功能方向主入口”（G0–G7 阶段门）；它给出阶段进入条件和完成门，但不构成修改生产代码的授权——执行授权始终只来自 [`ACTIVE_WORK.md`](ACTIVE_WORK.md)。

G 阶段是产品和实现方向；Q 系列是仓库中的具体工作单。同一个 G 阶段可能包含多张 Q 工作单，但 Q 工作单不能跳过当前阶段的完成门。

## 你如何使用这份文档

1. 只推进一个 G 阶段。
2. 先确认当前 Q 工作单已经允许执行，再把对应 Prompt 交给 Agent。
3. Agent 返回后，只根据该阶段完成标志和实际测试证据判断是否通过。
4. 当前阶段没有关闭前，不进入下一阶段，也不因为某个模块已经提前写了一部分代码就宣布阶段完成。
5. 阶段完成后，再建立或确认下一张 Q 工作单。

## G0：现有链路资格收口

### 你需要确认

- Q4+Q5 执行中（已合并）：按 56 错清单补齐缺失类型与方法、完成两处真实编排、删除两个排除、对着真实 MySQL 跑出终态结果。
- Generator 是否只消费 `SpringBootLoweredModel`。
- 现有编译、生成、Project Graph、Change 和文件事务证据是否完整。
- G0 之外的 Web、数据库迁移和完整交付能力没有被误报为已完成。

### 交给 Agent 的 Prompt

```text
你负责完成 KCG-Code 的 G0：现有链路资格收口。

先读取 AGENTS.md、docs/roadmap/ACTIVE_WORK.md、当前主设计实现基线和当前工作单。严格按当前工作单执行，只收口现有单文件编译、Lowering、Generator、Project Graph、Change 和本地文件事务的资格证据，不提前实现 G1 之后的课程业务、数据库迁移、Docker 或 Web 平台。

完成当前工作单规定的实现、测试和资格记录；所有结论以当次命令输出和测试结果为准。若当前工作单仍处于 SPEC_REVIEW，先不要修改生产代码，报告当前阻断状态。

完成后报告：修改文件、实际运行的命令、测试结果、仍未验证的范围，以及是否满足 G0 完成门。不要提交 Git，不要扩大范围。
```

## G1：单文件课程业务切片

### 你需要确认

- 在现有单文件 SIR 链路上完成一个实体和查询的业务闭环。
- CRUD、分页、校验和基础关联逐步贯穿 Parser、Semantic、Lowering、Generator 和运行时验证。
- 真实 MySQL/HTTP 结果与生成工程行为一致。
- 不把测试建库设施描述成正式数据库初始化能力。

### 交给 Agent 的 Prompt

```text
你负责完成 KCG-Code 的 G1：单文件课程业务切片。

先读取 AGENTS.md、主设计的 02、03、07 和 implementation-baseline.md。直接在现有单文件 SIR 编译链上实现一个可运行的课程业务切片，从语义输入贯穿到 Lowered IR、生成代码和运行验证。优先完成一个实体、一个查询，再补齐该切片需要的 CRUD、分页、校验和关联语义。

所有新增语义必须贯穿 Parser、Resolve、Type、Validate、Normalize、Lowering、Generator 和测试，不得把业务判断藏进模板，也不得通过手写生成 Java 绕过 IR。不要实现 G2 的持久身份和多文件模块、G3 数据库迁移、G4 Docker 交付或 G6 Web 平台。

完成后以 BIZ-01..06、GEN-01/02 及对应反例为依据报告实际证据、未完成能力和剩余阻断。不要提交 Git，不要修改无关模块。
```

## G2：持久身份与受控模块

### 你需要确认

- 声明身份不再依赖名称变化。
- 多文件源清单、import/binding、模块实例和引用闭包有明确行为。
- 改名、移动、同名重建、重复 ID 和旧 Bundle 兼容均有验证。
- 不把模块市场和跨项目复用提前纳入本阶段。

### 交给 Agent 的 Prompt

```text
你负责完成 KCG-Code 的 G2：持久身份与受控多文件模块。

先读取 AGENTS.md、主设计的 00、02、03、07 和实现基线，确认 G1 已通过。直接实现设计中规定的持久声明身份、模块实例身份、多文件源清单、import/binding 和引用闭包，并保持 Resolve-once、稳定 SymbolId、确定性排序和结构化诊断。

重点验证新建、改名、移动、删除后同名重建、重复 ID、旧身份映射和旧 Bundle 不被静默误读。所有身份变化必须贯穿语义、Lowering、生成、Graph 和 Change 所需边界。不要实现数据库迁移、完整 Docker 交付、模块市场或 Web 平台。

完成后报告 LANG-01..05 的实际结果、兼容性限制、测试证据和仍需主 Agent 裁决的公共契约变化。不要提交 Git。
```

## G3：数据库生命周期

### 你需要确认

- 数据库 INITIALIZE、UPDATE、历史、漂移检测和恢复形成独立闭环。
- 旧 Schema、新 Schema、物理映射和持久身份之间的关系可验证。
- 连续更新保留业务数据。
- 数据库状态不能借用文件 Bundle/CURRENT 解释，文件事务测试不能抵扣数据库验收。

### 交给 Agent 的 Prompt

```text
你负责完成 KCG-Code 的 G3：数据库生命周期。

先读取 AGENTS.md、主设计的 00、04、05、07 和实现基线，确认 G2 的身份与模块门已经关闭。直接实现并验证数据库 INITIALIZE、UPDATE、schema history、漂移检测、数据保留和显式恢复；所有数据库状态、迁移证据和失败结果使用独立的数据库契约。

用真实数据库场景验证连续两次更新、字段和约束变化、部分 DDL 失败、重复执行和恢复。不得把文件 Bundle/CURRENT/Journal 当作数据库迁移状态，也不得用文件事务测试代替 DB-01..11。

完成后报告实际数据库测试、数据前后对比、故障恢复结果、未验证环境和剩余风险。不要提交 Git，不要提前实现 Web 平台。
```

## G4：完整源码包与 Docker 交付

### 你需要确认

- ReleaseManifest、完整源码包、构建文件、部署执行器、脚本和持久卷配置完整。
- 交付包可以脱离平台，在目标 Docker 环境中构建和运行。
- 初始化、更新、启动、停止、状态和恢复的责任边界清晰。
- 不能因为生成了若干 Java 文件就宣称完成交付。

### 交给 Agent 的 Prompt

```text
你负责完成 KCG-Code 的 G4：完整源码包与 Docker 独立交付。

先读取 AGENTS.md、主设计的 00、03、04、05、07 和实现基线，确认 G3 已通过。直接补齐完整源码交付包、ReleaseManifest、构建文件、bootstrap、部署执行器、Docker/Compose、启动脚本、更新脚本、状态和恢复入口，并让这些内容由明确的 Application/Packaging 边界组装。

在仅有目标 Docker 环境和公共依赖可达的条件下验证构建、初始化、运行、更新和持久卷数据保留。不要把 Web 平台、Worker、缓存或平台发布协调器混入本阶段；不要让 Generator 直接承担文件事务和部署状态写入。

完成后报告 GEN-03/04、DEP-01..08 的实际证据、独立部署结果、数据保留结果和未验证范围。不要提交 Git。
```

## G6：网页平台与可靠发布

### 你需要确认

- 网页编辑、草稿保存、生成任务、Worker 租约、构建隔离、产物下载和 Release 发布形成闭环。
- Agent 旧提案不能覆盖新草稿，过期 Worker 不能写回状态。
- 平台 Release、工具链文件 Bundle/CURRENT 和用户数据库状态彼此分离。
- 缓存只能优化成本，不能替代完整验证。

### 交给 Agent 的 Prompt

```text
你负责完成 KCG-Code 的 G6：网页平台与可靠发布。

保持平台只通过 typed Application 接口调用编译与交付链。平台、Release、文件 Bundle/CURRENT 和用户数据库不得共用未经定义的状态或原子事务。验证草稿 CAS、旧 Agent 提案、重复任务、Worker 过期、竞争发布、发布中断和恢复。

完成后报告 WEB/JOB/PUB/CACHE 场景的实际结果、发布边界和仍未实现的高阶能力。不要提交 Git。
```

## G7：独立试用与换题验证

### 你需要确认

- 至少使用第二个独立题目验证工具链，而不是只验证固定课程样例。
- 第二个题目也能经历首次生成和至少两轮需求修改。
- 数据保留、危险变更阻断、人工介入和失败重试均有记录。
- 是否继续发展模块拼装、共享缓存或其他扩展由证据决定。

### 交给 Agent 的 Prompt

```text
你负责完成 KCG-Code 的 G7：独立题目试用与方向验证。

先读取 AGENTS.md、主设计的 01、06、07 和前面阶段的验收记录。选择一个与课程主线不同但仍在支持范围内的题目，直接执行首次生成、部署和至少两轮 SIR 需求修改，记录每次编译、生成、部署、数据保留、失败恢复和人工介入结果。

使用同一套验收口径，不用单个成功样例证明通用能力。分别记录工具链正确性、Agent 修改效率、人工介入、数据保留和缓存收益；不得把缓存命中或模块复用率当作正确性证据。

完成后提交独立试用报告，并根据实际证据说明下一步是否值得进入模块市场、跨项目缓存或其他后续方向。不要提交 Git。
```

## 阶段完成后的最小汇报格式

每个阶段完成后，只需要向项目负责人报告：

1. 当前阶段和对应 Q 工作单；
2. 本阶段已完成的能力；
3. 实际运行的测试或验收证据；
4. 尚未验证或被阻断的内容；
5. 是否建议进入下一阶段。

“代码已经存在”“单元测试通过”“设计文档已写出”不能单独作为阶段完成依据；必须与该阶段的完成标志对应。
