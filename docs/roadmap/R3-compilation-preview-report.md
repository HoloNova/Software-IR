# R3 报告：统一编译与只读更新预览（Claude 会话环境验证完成）

- 日期：2026-10-13。分支：`main`。授权：负责人 2026-10-13 授权进入 R3；R4、R5 未授权。
- 前置：[R2 报告](R2-command-editing-report.md)、[迁移路线](LAYERED_ARCHITECTURE_MIGRATION.md)、[设计 08 第 7 节](../design/08-layered-command-architecture.md)。
- 结论：给定"旧版本"和"新版本"两份 SIR（单文件或多文件），可以得到一份**只读**预览，把三件事分开说清：源文件哪里不同、软件的行为哪里不同、实现文件需要怎样增删改。一份预览里可以同时有新增、更新、删除。预览不写任何文件、不保存任何状态；真正落盘与恢复是 R4。

## 1. 怎么用

```text
旧版本 SIR ─┐                        ┌─ 源文件差异（哪些 .sir 字节不同）
            ├─ 各自完整编译 ─ 对比 ─┼─ 软件差异（SemanticDelta：业务上变了什么）
新版本 SIR ─┘                        └─ 文件差异（FileDelta：哪些 Java/配置文件要新增、更新、删除）
上一次生成的输出目录（可选，只读）──→ 发现被手改、被删、被占用的文件
```

三种典型结果（测试里都有真实样例）：

| 情况 | 源 | 软件 | 文件 |
| --- | --- | --- | --- |
| 删一个查询能力、新增另一个、收紧一个输入 | 变 | 变 | 同时有新增、更新、删除 |
| 只加了一行注释，或把一个声明挪到另一个源文件 | 变 | 不变 | 全不变（`sourceOnly`） |
| 改了一个不会出现在任何 Java 里的约束 | 变 | 变 | 全不变 |

后两行说明为什么要分开展示：源变了不等于要改代码，软件变了也不等于要改文件。

## 2. 新增了什么，以及为什么存在

| 部件 | 位置 | 为什么存在 |
| --- | --- | --- |
| `CompilationService` | `application/internal` | 以前单文件和多文件各有一套编排：单文件有每阶段原始诊断和"停在某阶段"，多文件没有。现在多文件解析后走同一个降级与生成步骤，两种来源返回同样的结果。旧入口 `ProjectCompilation` 只做包装 |
| `CompilationInput` | `application/api` | 明确说明输入是"单文件"还是"工程"，不靠字节猜：单文件走旧入口（保留旧版本规则），工程只收 SIR 0.2 |
| `SourceDelta` | 同上 | 按精确字节比较源文件（新增／删除／改变／不变） |
| `FileDelta` | 同上 | 比较**完整**生成文件集合，给出新增／更新／删除／不变；每个文件记录它属于哪个声明，没有归属的是共享文件，同样参与比较，所以不会漏 |
| 磁盘证据 | `FileDelta.Disk`、`Conflict` | 计划要的是真实文件证据，不是图摘要自证：给了输出目录就逐个核对。要被改的文件被手改、要被删的文件已经没了、要新增的路径已被别的文件占用，都报冲突；没被计划碰到的文件即使被改了也只记录、不算冲突 |
| `UpdatePreviewApplication` | 同上 | 把以上串起来；输出目录只经无符号链接句柄读取，从不写 |

这次新增测试各自证明什么：

- **编译服务（5）**：工程可以停在任一阶段并报告停在哪；生成的文件与现有工程生成实际写到磁盘的文件逐字节一致；语义错误保留原始诊断，且旧入口得到的旧式诊断列表与服务一致；第一个解析失败的文件就停止；超大源在解析前被拒绝。旧的多源与工程更新测试（92 + 85 个）全部通过，证明旧合同没变。
- **预览（10）**：以现有工具链分别生成新旧两个目录作标准答案，预览的每个文件动作与之完全一致，且同一份预览里有新增、更新、删除和不变；共享文件参与比较；编辑器给出的软件差异与两份编译结果算出的差异完全相同；只加注释是纯源变化；相同版本无任何变化；被手改／已缺失／被占用的路径分别报冲突，没被碰到的文件被改不算冲突，且预览前后目录逐字节不变；坏的新版本、坏的旧版本、读不了的输出目录分别指出是哪一侧、哪个阶段；工程更新只触及受影响的文件；改源文件里一个不生成代码的约束时软件变而文件不变；把声明挪到另一个源文件时只有源变化。

## 4. 与计划不一致或需要你知道的地方

1. **没有新建 `CompilationService` 公共 API**：服务放在应用层 `internal`，对外只暴露预览入口。理由：它是编排细节，R4 才会有第二个调用方，现在公开是多余的承诺。
2. **输入只收两份来源，不读状态目录**：旧版本的"已生成文件"由旧版本源码从头编译得到，而不是从某个已保存的基线读取。基线、CURRENT、版本绑定是 R4 的内容，R3 不提前做。
3. **多文件解析失败时仍沿用旧行为**：第一个解析失败的文件就停止，不继续报别的文件。我曾想改成"全部报告"，但旧合同要求不变，已改回。
4. **预览与旧计划不互通**：`UpdatePreviewResult` 不能交给旧的 apply，旧的 `ChangePlan`、六类操作、UPDATE-only 规则、旧日志格式一律没动。
5. **多文件的语义差异第一次在多源模型上运行**：R2 只在单文件上验证过 `SoftwareDraft`；R3 的多文件测试证明它在多源模型上同样可用。

## 5. 明确没做

- 不写文件、不保存状态、不提交版本（R4）。
- 不做缓存或局部编译：每次都是两份完整编译。
- 不检查数据库迁移：目标层目前没有这部分信息，预览不把合法候选当成可执行的数据库更新。
- 不做构建、启动、业务验证（R5）。

## 6. 需要你确认的事

1. R3 的验收边界：只读预览 + 一个编译入口，是否符合你对"统一编译与只读工程计划"的预期。
2. 是否授权进入 R4（版本应用与恢复）。R4 会新增事务协议和 CURRENT 绑定，是风险最高的一段，开工前我会先做事实核对并给你一份更细的计划，不会直接动手。
