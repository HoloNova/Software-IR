# R4 计划：版本应用与恢复

- 日期：2026-10-13。状态：**进行中**；负责人 2026-10-13 回复"继续"，我据此开始 R4，并先写下本计划。R5 未授权。
- 前置：[R3 报告](R3-compilation-preview-report.md)、[迁移路线 R4 一节](LAYERED_ARCHITECTURE_MIGRATION.md)、[设计 08 第 7.3 节](../design/08-layered-command-architecture.md)。
- 目标（一句话）：把一个新版本的 SIR **保存**为新的当前版本，同时把生成工程**改成**这个版本的样子；中途断电或失败时有确定的处理；改完之后还能接着改。

## 1. 我核对到的现状（读代码得到，未运行）

| 事实 | 位置 | 对 R4 的含义 |
| --- | --- | --- |
| 工程更新事务（Q21）只支持"受管文件集合不变、至少改一个文件" | `ProjectUpdateTransaction`：`UPDATE transaction cannot create/delete managed paths`、`changes 非空` | 新增文件、删除文件、只改源不改文件都做不了，必须有新的事务 |
| 旧事务的日志状态机按"逐个替换文件"写死，文件数下限 1、上限 32 | `ProjectUpdateTrail`（`fileCount<1` 抛错） | 零文件（只改源）需要新格式 |
| 旧绑定记录只有"更新行"，且每行都要有备份和暂存两个槽位 | `ProjectUpdateBinding` | 新增（没有备份）、删除（没有暂存）需要新行类型 |
| 旧计划要求候选与基线的**源文件路径完全相同** | `LockedProjectPlanning`：`candidate source entry/member paths must equal baseline` | 把声明挪到别的源文件、新增源文件都被挡住 |
| 当前版本只有一个 `CURRENT` 指针，指向一个"保存包"（源 + 文件清单 + 图） | `ProjectBaselineStore`、`ProjectBaselineCodec.Bundle` | 保持一个 `CURRENT`；新版本也是一个保存包，不增加第二个"头" |
| 发布 = 把新包的指针硬链接成 `CURRENT.new` 再原子移动成 `CURRENT` | `ProjectUpdateTransaction` 第 97–104 行 | 这是现成、已验证的提交点，直接复用 |
| 历史关系（谁从谁来）与回执彼此校验：每条完成的关系必须有完成的回执 | `ProjectPublicationHistory.validate` | 新事务的回执要能被校验；校验器要认识新格式，同时旧格式照旧 |
| 状态目录里出现不认识的对象，旧代码一律拒绝并保留 | `ProjectBaselineStore.guardState` | 新协议写出的状态，旧代码会拒绝——这是想要的"旧格式不被放宽" |
| 底层原语齐全：无符号链接的文件句柄、锚点、暂存、硬链接备份、所有权校验、双槽日志 | `SecureFileAccess`、`ProjectJournalSlots`、`StateRootLock` | 复用，不另写 |
| 旧的故障测试在每个检查点注入中断，约 1 分钟 | `ProjectUpdateFaultMatrixTest` | 新事务沿用这种做法，且必须覆盖新增、删除、零文件三类 |

## 2. 要做什么，分五个小单元（每个单元测过再提交）

| 单元 | 交付 | 为什么存在 |
| --- | --- | --- |
| **U1 版本计划**（只读） | 在状态目录加锁后，重新验证基线与输出目录，编译候选，生成"新增／更新／删除／仅源变化"的完整计划和摘要；候选可以增删源文件 | 应用的前提是计划能被**独立重建并核对**，不能信调用方递来的结果。这一步和 R3 一样只读，风险最低 |
| **U2 新格式** | 新版绑定、日志、回执的编码与严格解码（带新的魔数）：行类型 UPDATE／CREATE／DELETE，文件数可以为 0，预算放宽到 128 | 旧格式不放宽（ADR 规定），所以另起一个版本；先把格式单独测透（规范化、截断、篡改、预算） |
| **U3 应用** | 事务本体：校验 → 备份（更新、删除）→ 暂存 → 逐个落位 → 发布 `CURRENT` → 清理 → 回执 | 这是"保存新 SIR 并更新工程"的主体。新增文件要同时创建缺失的父目录，并记下谁创建的，回滚时才能原样删掉 |
| **U4 恢复与故障矩阵** | 中断后确定处理：`CURRENT` 还指向旧版本就只向后补偿（还原备份、删除新建、恢复被删），已指向新版本就只向前（核验、清理）；对每个检查点注入中断并验证 | 这是风险最高的部分，也是唯一能证明"失败有确定处理"的证据 |
| **U5 入口与连续更新** | 对外入口（预览→计划→应用→恢复）；旧版本历史照旧可读；应用后再从 `CURRENT` 取出源码继续用 R2 的指令修改并再次应用；旧的句柄、过期计划被拒绝 | 证明"重开并继续修改"，以及新旧格式并存 |

最终证据要回答：结果是否**等于候选从零生成**（逐字节）、中断后是否落在 B0 或 B1 之一、旧测试是否全绿。

## 3. 我替你选定的默认值（有限调整，事后说明）

1. **新记录放在同一个状态目录族里（`project-transactions`、`project-history`），用新魔数区分**，不新建平行目录。理由：只有一个 `CURRENT`、一份历史，新旧事务才能连成同一条版本链。代价：旧代码读到新记录会拒绝，这正是要求的行为。
2. **文件数上限 128，绑定记录上限 256 KiB**。旧的 32 个文件放不下"新增一个实体"这类改动（一次会动几十个文件）。这是新格式自己的预算，旧预算不变。
3. **只处理"至少有一处变化"的计划**：候选的源与文件清单都与基线相同才算无变化，其余都要发布新版本，包括只改注释的源变化。
4. **冲突一律拒绝，不合并**：受管文件被手改、新增路径被占用，应用前直接拒绝（和预览里的冲突一致），不尝试字符串合并。
5. **不做数据库迁移、不做热部署**：和路线要求一致。

## 4. 风险与我不确定的地方

- 这是迁移里最大的一段，我估计新增代码量与现有事务（约 700 行密集代码）相当，测试更多。不估时。
- 创建父目录的回滚是新问题：旧事务从不新建目录。需要在故障矩阵里单独证明"回滚后目录树与原来逐字节相同"。
- 旧历史校验器必须同时认识两种回执；改它有回归风险，要用旧测试兜住。
- 这里没有 Docker 和 MySQL，所以数据库相关与业务集成测试仍然是 `NOT_RUN`，和 R3 一样。
